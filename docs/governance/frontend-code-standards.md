# Web 前端代码规范

**适用范围：**当前项目新增及修改的 React/TypeScript 管理页面。规范沿用 KnowSpace 的组件、状态、注释和质量要求，业务页面以[实施流程](../implementation-flow.md)为准。

## 1. 技术与目录

前端使用 React、TypeScript、Vite，按仓库、Webhook 配置、合并事件、评审任务和系统设置组织页面。路由与服务端状态管理分别使用 React Router 和 TanStack Query；只有出现真实跨页面客户端状态时再使用 Zustand。组件库和样式方案在工程骨架中确定，不继承 KnowSpace 的 Tiptap、AG Grid 或知识库页面。

正式代码放在 `frontend/src`，保留 KnowSpace 的职责目录，按需要建立：`app/` 放应用壳与 Provider，`routes/` 放路由，`pages/{domain}/{feature}/` 放页面入口、业务 Hook 和私有组件，`components/` 放跨页面组件，`api/client.ts` 与 `api/services/{domain}/` 放 REST 访问，`hooks/` 放跨页面 Hook，`store/` 放真正跨路由的客户端状态，`styles/` 放设计变量与全局样式，`types/`、`utils/`、`test/` 分别放跨域类型、纯函数和测试工具。

`pages/` 不创建 HTTP Client；`components/` 不依赖具体路由；`api/services/` 不处理 Toast、导航和页面状态；`store/` 不复制 URL、Query 或表单状态；`utils/` 不读取 React Context 或 Store。一个能力只在一个层级维护，不复制常量、类型或权限判断。

公共组件文件用 `PascalCase`，业务目录与 Service 用 `camelCase`，页面入口用 `index.tsx`；Hook 用 `useXxx`，Store Hook 用 `useXxxStore`。组件和类型用 `PascalCase`，函数与变量用 `camelCase`；布尔值以 `is/has/can/should/allow` 开头，事件处理函数用 `handleXxx`，回调属性用 `onXxx`。请求、响应类型可用 `XxxParams`、`XxxResponse`；`merge_commit_sha` 等契约字段只在 API 边界转换，不擅自改名。

| 文件类型 | 推荐范围 | 预警范围 | 处理方式 |
| --- | ---: | ---: | --- |
| 页面入口 | ≤150 行 | 151～250 行 | 抽取业务 Hook、配置或大块子组件。 |
| 页面私有组件 | ≤200 行 | 201～350 行 | 按独立交互拆分。 |
| 公共组件 | ≤300 行 | 301～500 行 | 保持外部 API，拆内部 Hook 和子组件。 |
| 业务 Hook / Store | ≤300 行 | 301～500 行 | 拆查询、Mutation 或领域动作。 |
| 工具文件 | ≤300 行 | 301～500 行 | 按领域语义拆分。 |

行数仅作职责预警，配置、Schema 和生成契约另行判断；超过预警上限的文件不再加入新职责。

## 2. TypeScript 与组件

- 开启 `strict`、未使用局部变量与参数检查、`switch` 穿透检查。未知 API 响应先验证；用 `unknown` 收窄外部值，不用 `any`、双重断言或非空断言掩盖缺失状态。有限状态用联合类型，契约值避免 TypeScript `enum`；类型导入用 `import type`。
- 使用函数组件与 Hooks；公共组件优先具名导出，一个文件维护一个主要组件。可变列表以稳定业务 ID 为 `key`。渲染逻辑保持纯净；请求交给查询层，Effect 只同步外部系统并清理订阅、计时器或可取消请求。
- 每个交互明确空、加载、成功、无权限、冲突和错误状态。异步请求须处理取消与旧响应覆盖新视图；任务和投递状态以服务端结果为准，不能把触发请求成功显示成评审完成。
- 公共组件 Props 表达真实约束，不把整个业务实体透传给纯展示组件。修改复用组件时保护 Props、`ref`、回调时机、导出路径和稳定语义标识；破坏性修改要列调用方与回归验证。`useMemo`、`useCallback`、`memo` 只在有实际成本或引用契约时使用；Hook 优先返回具名对象。

## 3. 状态所有权

| 状态 | 默认归属 | 要点 |
| --- | --- | --- |
| 仓库、Webhook 配置、合并事件、任务与投递详情 | TanStack Query | 查询键包含资源 ID、筛选和分页；变更后精确失效或更新缓存。 |
| 可分享的定位与筛选 | URL | MR、提交、任务、状态筛选和页码保持可刷新、可返回。 |
| 密钥录入草稿、筛选弹窗和确认对话框 | 组件或局部 Hook | 未提交草稿不被后台刷新覆盖；密钥不持久化。 |
| 真正跨页面且纯客户端的短期状态 | Zustand（如采用） | 只保存跨路由状态，按选择器订阅最小片段。 |

页面切换、筛选变更和卸载时取消或隔离旧请求，不让旧结果覆盖当前视图。任务可能因 Worker 异步更新，刷新策略以服务端状态与实际需要确定；无结果、部分覆盖、失败和飞书投递失败须分别显示。前端显示权限只控制界面，服务端仍负责授权。

## 4. API 与关键交互

组件不直接拼接 API URL、携带令牌或解析不同形状的错误。REST 统一经过 `api/client.ts`；Service 使用具名导出，一个函数对应稳定接口能力。非 2xx 响应转换为统一错误对象，保留错误码、请求 ID 与恢复信息；Client 处理基址、认证、超时、取消和必要的同源凭证。OpenAPI 契约稳定后生成或校验前端类型，接口变更同步更新调用方、测试和文档。

仓库与 Webhook 页面展示回调 URL、鉴权方式、接入状态和测试结果。Webhook Token 默认遮罩，管理员主动操作时由受保护的单项接口读取，列表查询缓存不保存明文；OCR API key 与飞书 webhook 不回显。轮换密钥使用明确的单向更新操作。按 MR 补触发、任务重跑和重发通知是不同命令，确认对话框展示目标与后果，不能混用状态或重复提交。出现 409 冲突时保留本地输入并提示刷新，不静默覆盖。

任务详情展示 OCR 的完成、部分完成、失败、跳过和豁免文件；只有确实完整覆盖且无发现时才能显示“未发现问题”。评论行号为 0 时提供文件级定位，不伪造 GitLab 行号链接。页面默认不展示原始 `thinking` 或未经审查的密钥与代码片段。

## 5. 视觉、可访问性与安全

管理页面以可扫描的列表、状态和操作为主。统一设计变量维护颜色、字号、间距、边框和焦点；桌面与窄屏均须可用。按钮和输入有可读标签，键盘可完成仓库配置、任务筛选与恢复操作；异步变化有适当可访问提示。具体组件库与 CSS 方案随工程骨架确定；格式化沿用 KnowSpace 的 Prettier 风格：双引号、分号、2 空格、尾逗号、LF。导入按第三方、项目路径、相对路径和样式资源分组。

不在 `localStorage`、URL、控制台、Toast 或埋点中保留密钥、Cookie、完整 webhook 或敏感代码。用户输入与 OCR 模型输出均按不可信内容处理，禁止直接插入原始 HTML。管理会话如使用 Cookie，应配合 HttpOnly、SameSite 与适用的 CSRF 防护；页面上的禁用或隐藏操作不代替服务端校验。

## 6. 注释规范：与 AI 项目保持一致

### 6.1 文件头与公开导出

新增和修改的注释使用中文，解释业务意图、设计原因和维护风险；代码、契约或状态变化时同步更新。**所有手写 `.ts`、`.tsx` 文件**，除生成文件和纯再导出入口外，必须在首个 `import` 前有 `@description` 文件头。普通文件至少说明维护主题；页面、业务 Hook、API、Store、公共组件、路由权限、SSE/缓存/错误基础设施还说明负责什么、不负责什么及权限或副作用边界。

```ts
/**
 * @description 文档列表页面业务编排
 *
 * 负责查询、筛选和页面动作组合；不负责 HTTP 请求实现或服务端授权。
 * 工作区切换后旧请求的结果不得进入当前页面。
 */
```

**所有手写的导出 React 组件、Props/Options 类型、自定义 Hook、Hook 返回对象、API Service、公共工具、Store、跨模块常量和配置，都要紧邻提供 JSDoc。**说明用途，以及实际存在的关键参数、返回、权限、错误、副作用或前置条件。文件内私有小组件和简单类型不强制。Props 字段逐项说明；跨文件 Hook Options、回调和复杂请求参数字段也逐项说明默认、省略和触发语义。`canEdit` 等权限属性需写明只控制界面，服务端仍是授权边界。生成契约与第三方代码不手工补注释。

### 6.2 复杂流程与长函数

三个及以上业务步骤、多个顺序依赖的异步调用，以及权限、空间切换、Query 失效、文档状态、SSE、竞态、错误降级和敏感信息处理，必须在职责最近处有中文块注释。线性流程用连续编号的 `// 1. ...`、`// 2. ...` 标出主要阶段；非线性规则解释原因和边界。一个阶段注释覆盖相邻完整逻辑块，不逐行复述。普通 JSX 不加区域标题；只有大型条件、权限分区和不直观响应式重排才说明。

| 函数有效代码行 | 注释与拆分要求 |
| --- | --- |
| 少于 30 | 不因长度强制分段；高风险流程仍须说明。 |
| 30～59 | 两个以上控制流或异步业务阶段时，连续编号标主要阶段。 |
| 60～99 | 连续编号划分主要流程，通常不少于三阶段，并评估拆分。 |
| 100 及以上 | 默认拆分；确需保留时写“长函数保留原因：”并继续分段。 |

有效代码行不含函数签名、空行、注释、纯类型及排版行。长度是维护风险信号，不能以无语义小函数或模板注释规避。Query 注释解释非默认刷新或启用条件；Mutation 注释解释缓存失效原因；涉及网络、计时器、存储或订阅的 Effect 解释触发和清理策略。

| 文件类型 | 最低说明 |
| --- | --- |
| 页面入口 | 文件职责、权限与数据来源、主要状态；导出组件 JSDoc。 |
| 业务 Hook | 导出 Hook/Options JSDoc；Query、Mutation、缓存与清理关系。 |
| API Client/Service | 会话、工作区、错误和取消；导出函数用途、参数、返回与安全边界。 |
| 公共组件 | 导出组件 JSDoc；全部 Props 字段与回调时机。 |
| Store | 导出 Store/Action JSDoc；状态来源、持久化、重置和跨页影响。 |
| SSE / 权限配置 | 游标/重连/取消，或菜单、页面、接口和权限的边界。 |
| 测试 | 文件头说明被保护行为；复杂场景说明业务边界。 |

TODO/FIXME/HACK 注明责任人或角色、日期和退出条件。自动检查将来只判断文件头、JSDoc、阶段注释等可确定结构；注释是否解释真实业务原因由代码评审判断。不得写低价值模板注释、敏感信息或过期说明。许可证、协议固定文本、第三方与生成文件保持原始格式。

## 7. 测试与质量

应用壳与高风险功能区提供 Error Boundary 和恢复路径。测试重点覆盖仓库配置保存、Webhook 鉴权与令牌按需查看、合并事件过滤、任务异步状态、部分覆盖、重跑/重发、错误恢复和窄屏布局。组件测试以角色、标签、可见文本定位元素；网络在 Service 边界模拟，时间与随机值可控，仅使用合成数据。性能优化依据构建报告与实测，不全局滥用 Memo。

工程骨架应提供本地和 CI 共用的格式、ESLint、TypeScript 严格类型、测试与构建入口。当前尚无前端工程和已运行的检查；命令建立并真实通过后才能报告门禁已启用。
