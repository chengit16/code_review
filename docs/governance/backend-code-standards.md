# FastAPI 后端代码规范

**适用范围：**当前项目新增及修改的 API、独立 Worker 与共享 Python 代码。规范沿用 KnowSpace 的编码、注释和质量要求，业务边界以[实施流程](../implementation-flow.md)为准。

## 1. 技术与职责

后端使用 Python、FastAPI、Pydantic、SQLite 与独立 Worker。API 接收 GitLab webhook、提供管理接口；Worker 确认已合并 MR、准备 Git 输入、运行 OCR、校验结果并投递飞书。SQLite 保存事件、任务、尝试和投递状态；进程内队列不能成为唯一业务记录。OCR、GitLab API、Git 与飞书均视为外部系统。

正式代码建议置于 `backend/`。保留 KnowSpace 的职责方向，目录只在有真实职责时创建：

```text
backend/
  app/                    FastAPI 创建、依赖装配、异常映射与配置
  modules/{domain}/
    api/                  Router 与请求/响应模型
    application/          用例、事务和外部调用编排
    domain/               不依赖框架的规则、状态与接口
    infrastructure/       SQLite、GitLab、Git、OCR、飞书适配
  worker/                 任务领取、重试调度与生命周期
  tests/                  领域、接口与外部适配测试
```

路由只做协议校验、鉴权与响应映射；用例负责业务顺序和事务；领域规则不依赖 FastAPI、数据库模型或供应商 SDK；基础设施实现持久化和外部适配。依赖方向为 `api → application → domain`、`infrastructure → domain`，由 `app` 装配。Worker 不导入 API 启动模块；真实共享实现出现后再提取。简单用例不机械建立空层或空接口，也不引入万能 `BaseService`、`BaseRepository`。

包、模块、函数和变量用 `snake_case`；类与类型用 `PascalCase`；常量用 `UPPER_SNAKE_CASE`。用例以动词加领域对象命名，输入可用 `XxxCommand`、`XxxQuery`，HTTP 模型用 `XxxRequest`、`XxxResponse`。避免无语义的 `Data`、`Info`、`Manager`。

| 文件类型 | 推荐范围 | 预警范围 | 处理方式 |
| --- | ---: | ---: | --- |
| Router | ≤200 行 | 201～350 行 | 按资源或用例拆分。 |
| Application 用例 | ≤250 行 | 251～400 行 | 拆查询、命令或独立业务能力。 |
| 领域模块 | ≤300 行 | 301～500 行 | 按聚合规则或状态机拆分。 |
| Repository / Adapter | ≤350 行 | 351～600 行 | 按外部能力拆分。 |
| 测试文件 | ≤500 行 | 501～800 行 | 按行为场景拆分。 |

行数是职责预警，不是机械拆分依据；Schema、生成契约和迁移另行判断。

## 2. Python、模型与接口

- 生产函数和公开测试辅助函数标注完整参数与返回类型；开启严格类型检查。外部未知数据先验证，不使用无范围的 `Any`、`type: ignore` 或静默吞错。有限状态使用 `Literal`、`StrEnum` 或领域值对象；不用可变默认参数；时间使用带时区的 UTC。
- Pydantic 请求/响应、应用用例输入、领域对象、数据库模型和外部 OCR JSON 各司其职。安全敏感请求拒绝未知字段；不要让 ORM 对象直接进入 HTTP 响应或 Worker 载荷。区分字段缺失、`null`、空字符串和空集合。
- 用 `create_app()` 集中注册 Router、Middleware、异常映射和生命周期资源。Router 声明稳定路径、请求/响应模型和已知错误；`Depends` 不进入 Application 或 Domain。OpenAPI 由实际路由生成，接口变更同步更新前端类型、测试与文档。
- Webhook 接口独立于管理接口。先限制请求体大小并验证 GitLab 鉴权，再解析事件、核对项目 ID 与目标分支；成功持久化后尽快返回 2xx。无效鉴权拒绝，合法但非合并事件明确忽略，不在请求内执行 Git 或 OCR。

## 3. 可信输入与安全边界

GitLab webhook 的 URL 标识、请求头和 JSON 字段都是待校验输入。签名方式验证原始请求体、时间戳和签名；旧版 Secret token 用恒定时间比较。`project.id`、`target_project_id`、MR IID 和目标分支须与已配置仓库匹配。Worker 再用只读 GitLab API 确认 MR 已合并，并核对合并 SHA 对目标分支的可达性；不得把当前 HEAD、`last_commit.id` 或未经确认的外部参数当作评审范围。

Git remote、仓库目录、文件名和 commit 参数不得拼成 shell 命令；限制允许的 GitLab 主机及 URL 形式。GitLab API 凭据、SSH 私钥、OCR 模型密钥和飞书 webhook 只从受控密钥存储加载，不写入 SQLite 明文字段、日志、异常、测试夹具或返回体。OCR 原始 JSON 和被审查代码是敏感工件，管理 API 限制访问并避免目录穿越。

后台管理操作须有服务端认证与授权；即使第一版只服务单管理员，也不能因为页面隐藏按钮就允许任意人修改配置。对外 HTTPS 入口只转发 GitLab webhook 路径，管理页与 API 保持在受控网络内。

## 4. 用例、事务与并发

一个写用例明确事务边界。webhook 接收时，在同一事务保存事件及去重事实；事件处理时，在同一事务保存任务与事件状态；OCR 结果和待发送通知的状态保持一致。数据库提交前不执行 OCR、Git fetch 或飞书请求，避免持锁和不确定副作用。

事件按至少一次投递设计：GitLab 重投、HTTP 响应丢失、Worker 重启及任务乱序均不得导致重复评审。事件投递 ID、合并业务键和 `repository_id + mr_iid + commit_sha + config_snapshot_hash` 分层去重；数据库唯一约束负责最终仲裁，进程内锁只用于减少竞争。同一仓库按 MR 接收顺序、同一 MR 按提交顺序运行，不同仓库轮转领取，避免单仓库长期独占。飞书投递有独立状态与重试，不因通知失败而重跑 OCR。

事务由应用用例控制，Router、Repository 和领域实体不自行提交。SQLite 使用短事务及明确的单 Worker 领取策略；数据库锁冲突设置有限等待和可见失败。出现异常后回滚并重新建立事务，不在未知状态复用连接。重试须有次数、退避、错误分类和人工恢复路径；不能捕获 `Exception` 后返回成功或无限重试。

## 5. 持久化、迁移与 Worker

Repository 按事件、任务和通知聚合提供语义化方法，不暴露万能过滤 DSL。列表使用稳定排序与分页，查询避免 N+1。SQL 必须参数化。数据库约束保护投递 ID、业务合并键、任务去重键及状态关系；工件路径保存相对受控数据目录的引用。

数据库结构变化通过版本化迁移管理，不依赖应用启动时自动建表代替。迁移在空库和代表性旧数据上验证；已共享的迁移不原地改写。SQLite 定期在线备份，迁移和清理工件前考虑恢复。数据库及工件不提交到 Git。

Worker 载荷只使用稳定事件/任务 ID，不复制完整 webhook 请求体或凭据；每次领取后从数据库重读状态。OCR 子进程固定版本、参数数组、工作目录、环境、整体截止时间及诊断工件；核验 JSON schema、输入 SHA、`manifest.terminal_state`、覆盖分组与预算，不只凭退出码判为通过。GitLab、OCR 和飞书 Adapter 各自处理超时、脱敏、有限重试及错误分类。

## 6. 可观测性与测试

请求、事件、任务、OCR 尝试和通知投递保留关联 ID；记录稳定错误类别、关键耗时和状态转换，不记录密钥、完整代码、模型 `thinking` 或 webhook 原始请求体。健康检查区分进程存活与是否能够承接工作；事件积压、评审失败、部分覆盖及飞书失败应可查询。

测试重点覆盖：非合并事件忽略、签名与旧版 token 校验、重复/乱序投递、不同合并策略、SHA 不可达、OCR `complete`/`partial`/`failed`/`skipped`、Worker 重启和通知独立重试。领域与用例测试使用合成数据；数据库集成测试验证唯一约束、事务及迁移；外部服务使用可控替身验证超时和错误。测试通过公开或稳定接口验证行为，不为覆盖率写镜像实现的测试。

## 7. 注释规范：与 AI 项目保持一致

### 7.1 模块与公开接口

新增和修改的注释使用中文，解释业务意图、数据责任、事务和维护风险；行为、契约或状态机变化时同步更新。**所有手写 Python 模块**（生成文件除外）以模块级 docstring 为第一条语句，`from __future__` 位于其后。简单包入口至少说明公开领域；领域模块、Application、Router、Repository/UoW、外部 Adapter、Worker、SSE 和跨域基础设施还说明负责什么、不负责什么、依赖方向、写入权及权限/事务/副作用约束。

**所有公开顶层类和函数必须有 docstring。**公开的 Application 方法、Worker Task、SSE 服务、模型 Adapter 和解析器进一步说明前置条件、返回事实、错误、幂等或事务要求。Domain Protocol、Repository/UoW 的类型级 docstring 统一说明方法集合契约；单个方法有额外非直观约束时再单独说明。具体 Adapter 的类级 docstring 解释 Session、锁、网络和副作用差异，避免每个实现方法重复接口说明。

公开 Pydantic Schema 字段以 OpenAPI 契约为准；只为不直观的默认、省略、安全投影和兼容语义补 `Field(description=...)`。Domain 值对象、Protocol 参数和回调中的状态、单位、时区、敏感级别及所有权语义应说明。生成文件、第三方与协议固定文本不手工改注释；Alembic 固定元数据保留生成格式，手写约束顺序、回填和不可逆步骤补中文说明。

### 7.2 必须解释的业务边界

三个及以上业务步骤、多个顺序依赖的外部调用，或工作区隔离、默认拒绝、事务提交、状态机、版本、Outbox、幂等、锁、重试、SSE、模型/对象存储失败、迁移和历史数据回填，必须在职责最近处添加中文块注释。线性用例用连续编号的 `# 1. ...`、`# 2. ...` 标阶段；非线性规则说明“为什么”和边界。一个注释覆盖相邻完整逻辑块，不逐行复述。

| 位置 | 应解释的重点 |
| --- | --- |
| Domain | 不变量、合法状态、拒绝原因和快照边界。 |
| Application | 可信上下文、授权顺序、事务步骤及审计/Outbox 同事务。 |
| Repository | 工作区过滤、锁、唯一约束、乐观并发与查询取舍。 |
| API | 协议映射、上下文注入、稳定错误码与字段边界。 |
| Worker | 幂等键、有限重试、死信或人工恢复与提交时机。 |
| 外部 Adapter | 脱敏、超时、重试、失败关闭。 |
| SSE | 序号、保留、回放上限、取消与最终事实。 |

| 函数有效代码行 | 注释与拆分要求 |
| --- | --- |
| 少于 30 | 不因长度强制分段；高风险逻辑仍须说明。 |
| 30～59 | 两个以上控制流、事务或外部调用阶段时，连续编号标出主要阶段。 |
| 60～99 | 连续编号划分主要流程，通常不少于三阶段，并评估拆分。 |
| 100 及以上 | 默认拆分；确需保留时写“长函数保留原因：”并继续分段。 |

有效代码行不含签名、docstring、空行、注释、纯类型及排版行。长度只是维护风险信号，不以无语义转发函数或模板注释规避。保存点、锁、竞态、临界值和防未来误删的安全限制可用行内注释。

| 文件类型 | 最低说明 |
| --- | --- |
| Router | 公开端点 docstring；身份、工作区与错误转换边界。 |
| Application | 公开用例/方法 docstring；授权、事务、幂等和副作用。 |
| Domain / Protocol | 公开类型 docstring；状态、前置条件和可替换边界。 |
| Repository / UoW | 公开 Adapter docstring；写入权、Session、锁/版本与提交。 |
| Worker | 事件版本、幂等、有限重试和失败恢复。 |
| 外部 Adapter / SSE | 安全、超时、能力差异，或序号/回放/取消。 |
| Migration / 测试 | 回填与恢复，或被保护业务边界及合成数据约束。 |

## 8. 质量门禁与反模式

开发骨架应提供本地和 CI 共用的格式、Ruff、严格类型、测试与迁移检查入口，只有命令实现并运行后才报告通过。依赖升级提交锁文件；破坏性接口或数据库修改须同步更新调用方、测试和恢复方案。

禁止 Router 直接操作数据库或运行 OCR，Domain 导入框架或 ORM，Worker 在数据库事务内调用外部系统，以及用前端显示状态代替服务端鉴权。不得把进程内队列、GitLab webhook 投递记录或 OCR 退出码单独当作最终业务事实。
