# Meta JiTTesting 对本项目的借鉴评估

> 评估日期：2026-11-13（北京时间）。关联事项：PI-20261113-001。本轮只进行公开资料与当前源码核对；以下试点、状态和数据结构都是建议，不代表已实现或部署。

## 1. 判断

值得借鉴，最有价值的方向是给高风险评审发现补充可执行的行为证据。建议保留 OCR 作为代码评审入口，逐步增加测试验证能力；暂不建设全仓库、多语言、多模型投票与自动合并门禁。

应区分两个使用层面：先在 Open Code Review 自身的受控后端测试环境验证方法，再考虑作为面向接入仓库的产品能力。后者需要逐仓库约定测试框架、依赖、执行边界和资源预算，不能认为能够拉取 Git 就能可靠运行测试。

## 2. 原文的关键内容和口径

Meta 2026-10-29 的文章描述了五个阶段：筛选高风险变更、生成针对差异的测试、多模型评估、确定性规则评估、筛选后交由工程师判断。两种生成方式分别围绕变更意图构造潜在缺陷，以及直接把变更视为待区分的变异体。执行安排包括利用夜间空闲资源，不应把 JiTTesting 理解为每次提交立即阻塞的检查。[来源一]

论文将“基准版本通过、变更版本失败”作为回归候选的重要证据，但行为差异仍可能来自合理需求。人工需要判断变化是否符合意图；测试失败和真实缺陷不能画等号。[来源二]

文章报告 60% 真阳性率及 2026 年上半年提前发现 74 个严重隐私问题。这是 Meta 特定流程和样本的结果，不是全部缺陷召回率，也不能当成本项目的预期指标。早期论文摘要和第 1 节报告 41 次联系中确认 8 个真实问题，即 19.5%；第 5 节有一处写为 7 个但仍使用 19.5%，存在内部数字不一致。两份材料属于不同阶段，不混算或据此推导本项目效果。[来源一、来源二]

## 3. 当前项目可以复用什么

| 当前实现 | 核对依据 | 对试点的意义 |
| --- | --- | --- |
| 合并前 MR 队列及版本失效 | `backend/ocr_manager/premerge.py` 的 `enqueue_premerge`、`finish_premerge` | 已有入口和版本语义；新验证任务应绑定准确范围，避免旧证据污染新提交。 |
| Worker 复核 MR 状态、头提交与差异基准，并执行完整范围评审 | `backend/ocr_manager/worker.py` 的 `review_premerge` | 无需重新设计 Webhook 接收和 GitLab 核验链路。 |
| OCR 预览、结果解析及覆盖判定 | `backend/ocr_manager/ocr.py` 的 `run_review` | 可以保留现有评审，验证结果独立记录；OCR 覆盖不是测试覆盖或行为正确性证明。 |
| 发现价值反馈与质量聚合 | `backend/ocr_manager/review_finding_feedback.py`、`review_quality.py` | 可借鉴现有来源身份和审计模式；当前反馈以评审任务为核心，接入合并前发现仍需明确关联契约。 |
| 触发条件、代码依据、后果、修复建议四项描述 | `backend/ocr_manager/finding_policy.py` | 已有结构化发现要求，下一步重点是附加执行证据，不能把增加提示词当作测试能力。 |

当前合并前结果仅在管理页展示，不是合并门禁，也不自动向 GitLab 或飞书发布，见 `docs/project-overview.md` 第 4.3 节。不能假设合并后的发布或反馈能力已经无缝覆盖合并前审查。

当前 `run_review` 的核心路径是 OCR 调用与结果校验，未见生成测试后在两版代码中执行并回收证据的阶段。`docs/implementation-flow.md` 第 4.6 节明确禁止执行被审查仓库的构建、测试及安装脚本；`git_repo.py` 的独立 worktree 只提供目录与版本隔离，不能据此认定具备执行不可信代码的安全隔离。

## 4. 建议先做的最小试点

建议流程：MR 固定范围 → OCR 评审与风险筛选 → 少量候选测试 → 独立受限环境执行两版 → 规则分类 → 展示行为证据 → 人工判断业务意图。

### 4.1 先限定对象与预算

- 首批只选一个有成熟、可重复单元测试环境的仓库和一种语言。Open Code Review 自身后端可以作为候选，执行时只使用临时数据库与外部服务替身。
- 按改动位置和行为选择鉴权、幂等、重试、提交范围、覆盖状态等高风险变更，不只依赖模型自报的严重级别。
- 先给每个候选限制少量测试、生成修复轮数、模型费用、总耗时和并发；具体额度由试跑测量决定，不在缺少基线时承诺吞吐。
- 优先从已有 OCR 发现生成复现测试以控制范围，但这只能增强已有发现的证据，不能证明能发现 OCR 漏掉的问题。后续另设不依赖 OCR 发现的风险测试分支，测量新增检出价值。

### 4.2 把运行结果与缺陷判断分开

| 观察结果 | 建议展示语义 |
| --- | --- |
| 同一测试在基准通过、在变更版本稳定失败 | 已复现行为差异，待判断是否违反需求。 |
| 两版均通过 | 本测试未复现候选，不证明候选不存在，也不等于完整评审通过。 |
| 两版均失败 | 无法归因为本次变更；保留既有问题、测试错误或环境问题的可能。 |
| 依赖缺失、编译错误、超时或执行不稳定 | 验证受阻或不稳定，不自动算成新 bug 或误报。 |
| 人工确认预期行为变化 | 当前测试断言与新需求不符，记录判断依据。 |
| 修复版本使原失败测试通过 | 已有修复复验的执行证据；部署仍是独立事实。 |

对于故意修复旧行为的 MR，新测试可能应该在旧版本失败、新版本通过。不能强迫所有新需求和缺陷修复都满足“旧版通过”才有价值；上述双版本筛选主要适用于保持既有契约的回归检测。

模型复核可以帮助解释失败，但不替代执行结果、需求依据和人工判断。重复执行可以排除一部分偶发失败，但不承诺消除所有不稳定性。第一阶段先用确定性检查和必要的单次语义复核，不照搬多模型评审团。

结果卡片先展示具体输入和两版行为，例如“相同事件重复到达，基准产生一个任务、变更后产生两个任务”，再请工程师判断是否符合需求；测试代码和完整脱敏执行详情供进一步展开。这借鉴论文第 5.1 节降低人工判断成本的做法，示例不代表当前项目存在该缺陷。

### 4.3 独立建模与执行

建议新增与评审关联的验证任务、尝试和测试工件，不篡改 OCR 原始 manifest 或把验证失败覆盖成评审失败。保存仓库、MR、基准与头 SHA、来源发现、测试内容摘要、执行环境版本、命令、两版结果、脱敏日志、成本和人工决定；记录结果时再次核对版本，过期证据只保留历史。

测试执行使用独立容器、虚拟机或受控 CI Runner，选择取决于部署条件。生成进程与执行进程分离；执行环境不提供业务数据库、GitLab/飞书/模型密钥或宿主私有配置，限制网络、文件系统和资源。依赖准备阶段也应纳入隔离与版本管理。HTTP 仍只接收并入库，耗时执行由独立任务承担。

## 5. 优先验证的项目场景

以下为建议场景，不是本轮发现的现存缺陷：

1. 同一 Webhook 重投不产生重复评审或重复投递。
2. MR 新 SHA 到达后，旧任务迟到结果不能变成当前结果。
3. 覆盖缺失、部分完成或豁免不能展示为完整通过。
4. 飞书投递失败的补偿不能重新消费 OCR 模型额度。
5. 反馈“有帮助”不能自动证明修复完成；问题处置与反馈保持独立。

可在受控副本中有意移除去重、版本校验或覆盖约束，检查现有及生成测试能否识别这些模拟错误。这属于测试有效性实验，不是在真实业务库制造故障，也不以实验结果宣称已找到生产 bug。[方法背景：来源三]

## 6. 推进顺序与衡量方式

1. **方法验证**：在受控仓库、小范围合成或经批准的历史样本上评估生成、运行和失败分类；固定一批留出样本用于比较，避免只挑成功案例。
2. **旁路试运行**：合并前页面显示测试证据，不阻塞合并、不自动提交修复；只对筛选后的候选请求人工判断，抽样复核被过滤项。
3. **根据效果扩展**：证明确有新增价值后，再扩展独立风险测试、更多仓库与通知渠道。自动门禁需要另行制定稳定性、精度和例外标准。

建议分别统计：符合条件的变更数、实际验证数、成功运行率、稳定行为差异数、工程师已判断数与待判断数、确认缺陷率、预期变化率、环境受阻率、每个确认缺陷的计算和人工成本、验证延迟。确认缺陷率只对有人工判断的适用候选计算，并同时公开未判断占比；“有帮助率”不是缺陷准确率，没有完整真实标签时不宣称召回率。
