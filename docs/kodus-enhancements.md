# 评审闭环增强实施记录

> 阶段实施记录：后续已补充发现反馈与问题状态的事务同步、就地处理与批量操作。第一期的“保持独立”描述应结合当前[操作指南](configuration-guide.md#6-评审发现的就地处理)理解；历史测试数量不代表当前重新验证结果。

参考 Kodus 的问题跟踪、效果衡量和上下文评审思路，继续使用 Alibaba Open Code Review 引擎。业务事实保存在 SQLite，外部调用仍由 Worker 执行。

## 第一期：待跟进问题

- 已完成：每次成功或部分完成的逐提交评审，把有效发现写入问题与出现记录；同仓库路径、类别和文字完全一致的开放问题自动关联，行号变化不产生新问题。
- 已完成：人工标记待处理、已修复、已忽略，保留操作者和处理说明；管理员可合并同仓库开放问题，合并后的旧指纹继续指向目标。
- 已完成：任务详情链接到问题页；问题页按项目、状态、严重级别分页查看出现记录和处理历史。已有当前结果在数据库升级后补建一次，不从历史尝试推断修复。
- 边界：已关闭问题不会被新评审自动重开；单次发现反馈的“已修复”与跨评审问题状态保持独立。未出现的发现不能自动判为已修复。
- 验证：后端 `uv run pytest backend/tests -q` 为 177 项通过；`uv run ruff check backend/ocr_manager backend/tests/test_review_issues.py`、`uv run mypy backend/ocr_manager`、前端 `npm run lint`、`npm run build`、`npm test -- --run` 通过。

## 第二期：效果统计

- 已完成：按项目与最近 7、30、90 天查看新增、确认修复、当前待处理及类别趋势，并区分生成的发现与 GitLab 实际成功发布的行内评论。
- 已完成：误报率只以人工标记的发现为分母；少于 5 条反馈时显示数据不足。OCR 没有稳定规则 ID，因此不展示无法核实的规则级归因。
- 边界：时间窗口按 SQLite 中保存的评审、发现和人工处理时间计算；历史补建的问题以补建时间为首次记录时间，不能据此推断实际修复日。
- 验证：后端全量 `uv run pytest backend/tests -q` 为 179 项通过；Ruff、mypy、前端 lint/build 与 5 项组件测试通过。

## 第三期：业务上下文

- 已完成：项目的“合并前审查”可以选择纳入 GitLab MR 描述，并指定最多 3 份仓库内 `.md` 或 `.txt` 文档。Worker 复核项目、目标分支、MR 头与差异基准后，从固定的 MR 提交读取文档；文档路径拒绝越界、符号链接和超限内容。
- 已完成：本次背景以单个 `--background-file` 传给 OCR；数据库只记录来源、字数及摘要，不在管理页展示全文。描述更新即使不改变 SHA，也会重新排队；运行期间描述变化或配置调整会使旧结论失效。
- 已完成：配置变更时已有当前预审重新排队；关闭事件使旧结论失效，并交给 Worker 复核 MR 是否已重新打开，防止乱序通知永久抹去当前结果。
- 验证：合成 GitLab、Git 和 OCR 用例覆盖背景来源、路径校验、OCR 参数、同 SHA 描述变化、运行期间变化及配置失效。后端全量 `uv run pytest backend/tests -q` 为 183 项通过；Ruff、mypy、前端 lint/build 与 5 项组件测试通过。真实 GitLab MR 与真实模型输出仍需按下列步骤验收。

### 真实测试 MR 验收

1. 在项目配置中启用合并前审查，选择“包含 GitLab MR 描述”，填写已提交到测试分支的业务文档路径，例如 `docs/review-context.md`，并确认模型与 GitLab 凭据可用。
2. 在 GitLab 项目 Webhook 中启用 Merge Request 事件，创建指向配置目标分支的测试 MR；描述与文档分别写入可辨认、无密钥的业务约束。
3. 在“合并前审查”查看当前版本详情：应有 MR 描述和文档两项来源摘要；OCR 原始运行目录中的 `background.md` 应包含两段背景，结果输入 SHA 应与 MR 头一致。
4. 只编辑 MR 描述、不推送提交：新的预审应排队，旧版本标为失效。随后修改项目的背景文档路径：当前结论再次失效并重新排队。
5. 关闭测试 MR：旧结果应立即失效；Worker 复核后不再产生可用结论。若随后重新打开，新的更新事件应生成当前预审。
