# 项目总览

> 整理日期：2026-10-23。本文依据当前代码与已存在的实施记录梳理，不读取私有配置或业务数据库，不代表重新完成真实外部服务验收。

## 1. 项目定位与边界

Open Code Review 管理平台负责把 GitLab 代码变更接入 Alibaba Open Code Review CLI（下文简称 OCR），保存评审结果、覆盖情况及问题跟进记录，并向飞书发送摘要。

核心边界：

- 评审引擎使用 OCR，平台负责接入、排队、配置、结果展示与人工闭环。
- SQLite 中持久化的事件、任务、尝试和投递是业务事实，页面状态不能代替服务端事实。
- GitLab Webhook 只触发入库；Git、OCR、连接测试和评审通知等耗时操作交给独立 Worker。
- 合并前审查与合并后的任务分别建模；当前不会阻止 GitLab 合并。
- “已修复”是人工处理决定，不代表平台已修改代码或验证修复；“误报”也不改变已发送的历史消息。
- 飞书通知和 GitLab 行内发布独立处理，失败时不应为了重发消息而重新调用模型。

## 2. 技术栈与进程

| 层级 | 当前实现 |
| --- | --- |
| 管理 API | Python 3.12+、FastAPI、Uvicorn。 |
| 持久化 | SQLite，包含队列、配置、问题、审计和迁移。 |
| 后台执行 | 独立 Worker；同一数据目录通过文件锁限制单实例。 |
| 独立监控 | `ocr_manager.alerts`，由 monitor 进程检测异常、维护告警与清理孤立工件。 |
| 外部集成 | GitLab API / HTTPS Git、OCR CLI、模型服务、飞书机器人。 |
| 前端 | React 19、TypeScript、Vite、TanStack Query、React Router、Radix Select。 |
| 验证 | pytest、Ruff、mypy、Vitest、ESLint、TypeScript 构建与 Playwright。 |
| 本机部署 | launchd 可分别管理 API、Worker、monitor 和定时备份。 |

```text
GitLab Webhook -> 管理 API -> SQLite 事件收件箱
                                |
                                v
                           独立 Worker
                  GitLab 核对 / Git / OCR
                                |
                   评审结果 / 问题 / 投递记录
                     |                  |
                 React 管理台      飞书 / GitLab 行内发布

独立 monitor -> 监测 SQLite、Worker、磁盘和备份 -> 告警及维护
定时备份     -> SQLite 副本 + 私有配置的成对快照
```

API 可用不等于 Worker 已运行。`GET /api/health` 的 `status`、`auth_mode`、`worker` 应分别解读；`worker=stopped` 时页面仍可能打开，但评审队列不会继续消费。健康接口不能代替 monitor、备份和真实外部链路验收。

## 3. 当前页面与权限

管理员主导航分为工作台、运维与审计、接入配置三个分组；只读账号仅展示工作台页面，写操作与敏感信息读取仍由服务端校验。

| 页面 | 路由 | 主要能力 |
| --- | --- | --- |
| 运行概览 | `/` | 全量运行汇总、待关注评审、独立通知异常、项目和时间范围内的效果统计。 |
| 评审任务 | `/jobs` | 快捷筛选、项目 / 状态 / MR 检索、高级筛选、当前页显式勾选重审、MR 补触发；窄屏显示紧凑任务卡片。 |
| 任务详情 | `/jobs/:id` | 发现与错误优先展示、覆盖证明、反馈、问题链接、尝试历史、通知及行内发布重试。 |
| 待跟进问题 | `/issues` | 问题搜索、状态与级别筛选、批量处理、详情侧栏、重复项合并和处理历史。 |
| 合并前审查 | `/premerge` | 默认每个 MR 的最新接收版本、项目 / MR / 状态过滤、历史版本与覆盖结论。 |
| 合并事件 | `/events` | 事件分页检索、异常恢复、按合并时间补审及申请状态。 |
| 项目配置 | `/repositories` | 基础接入、评审参数、发布审查、接入诊断四个页签。 |
| 系统设置 | `/settings` | `model`、`feishu`、`rules` 三个标签，分别管理模型、通知和规则。 |
| 访问权限 | `/users` | 账号、角色、停用、密码重置和多人登录模式。 |
| 运维与审计 | `/operations` | 运行监控、告警、工件维护、服务地址及管理操作审计。 |
| 配置历史 | `/config-history` | 项目、飞书与 Agent 模型配置版本查看和恢复。 |

事件中心、运行监控与配置历史均可从主导航进入；只读账号可查询事件但不能重试或发起补审。`/webhooks` 转到项目配置，`/feishu` 与 `/review-rules` 转到对应设置标签，`/effectiveness` 转到概览并保留筛选。

鉴权模式：

- `dev`：可信本机开发模式，不要求管理口令，不能公开整个服务端口。
- `admin`：共享管理口令模式。
- `users`：管理员和只读账号模式；启用后共享管理口令失效，最后一名启用管理员受保护。

## 4. 三条评审路径

### 4.1 合并后 MR

1. 接收合法的 MR 合并事件，校验项目、分支、鉴权与事件开关并入库。
2. Worker 通过 GitLab 核对 MR，确定提交范围，生成逐提交任务及配置快照。
3. 拉取可信仓库，在隔离目录执行 preview 和正式评审，保存尝试与覆盖结果。
4. 有效发现关联到问题跟踪，飞书摘要与可选的 GitLab 行内发布分别落库处理。

漏投和历史 MR 可在任务页手动补触发；任务重审可能使用当前配置形成新的任务，旧记录仍保留。

### 4.2 默认分支 Push

一次合法快进 Push 的 `before..after` 净差异作为一个范围任务，不拆成 MR 逐提交任务。首次创建分支、删除分支和强制改写历史不会自动评审。去重、范围和来源核对在服务端执行。

### 4.3 合并前 MR

项目独立启用后，MR 新建、重新打开或更新可触发完整差异审查。Worker 复核头提交与基准，可纳入 MR 描述和最多 3 份提交内 `.md` / `.txt` 背景文件；路径、类型和大小受限。提交、背景或配置变化可使旧结果失效。

当前合并前结果只在管理页查看，不自动发布到 GitLab 或飞书，也不是合并门禁。失效、失败、部分完成和未知覆盖不能展示为“未发现问题”。

## 5. 状态、反馈和批量操作

### 状态不要混用

| 对象 | 状态语义 |
| --- | --- |
| 评审任务 | 区分排队、运行、完成、部分完成、失败、跳过、取消；完整结论须以覆盖证据为准。 |
| 飞书投递 | 与评审结果独立；发送失败不代表 OCR 失败，重发不重跑评审。 |
| 问题 | 待处理、已修复、已忽略、已合并，记录人工决策与操作者。 |
| 发现反馈 | 有帮助、误报、已修复，与关联问题按服务端事务规则同步。 |

“有帮助”不是关闭问题；“误报”会把符合条件的待处理问题同步为已忽略；“已修复”表示人工确认。撤销反馈仅在满足最新决策归属等条件时恢复问题，不能覆盖别处的后续处理。详见[就地处理说明](configuration-guide.md#6-评审发现的就地处理)。

模型严重级别使用 `critical`、`high`、`medium`、`low`，不等同于任务执行状态。项目应在“系统设置 → 审核规则”说明认定标准，要求发现写明触发条件、代码证据和实际业务后果；不要只凭措辞强烈程度判断级别。

### 当前交互约定

- 任务、问题、合并前列表支持每页 25 / 50 / 100 条和跳页，条件保存在 URL。
- 当前页批量操作只影响显式勾选的编号，不隐式扩展到其他页；换页或换条件后重新选择。
- 批量重审逐项接受或拒绝，只取消成功项勾选，失败项保留；入队不代表评审完成。
- 问题批量更新是原子操作，发生状态冲突时整批不改；批量关闭不批改全部历史发现的反馈。
- 项目编辑切换页签保留内存草稿，各配置区域独立保存；保存基础接入不关闭窗口或丢弃其他草稿。
- 配置首次读取失败不能直接保存默认值；保存失败保留草稿，读取与保存错误分别展示。
- 任务高级筛选按需展开，生效条件可移除；问题出现与处理历史默认各显示最近 10 条，按需追加。

## 7. 部署与数据安全

- 本机 API 默认 `127.0.0.1:8781`，前端开发端口 `5173`，隔离浏览器服务 `8791`。
- API 与 Worker 使用相同私有配置和主密钥；已有环境不能重新生成主密钥，否则凭据无法解密。
- GitLab 回调入口与管理入口分别配置；对外只转发受控 Webhook 路径，管理页另行保护。
- 模型密钥与飞书地址不回显；GitLab Webhook Token 默认遮罩，管理员可主动读取或复制。
- SQLite、主密钥配置、备份和 OCR 原始工件按敏感数据保护；不写入 Git、截图和普通日志。
- 携带私有配置的成对备份默认保留 90 天且至少保留最近两份；恢复写入不存在的新目录，切换前停止相关进程，不覆盖运行中的数据库。

详细安装、进程启动、launchd 与恢复步骤统一见[部署说明](deployment.md)，不在本文复制真实环境配置。

## 8. 验证记录与后续维护

上一轮前端优化实际执行并通过：前端构建、Lint、27 项单元测试和 37 项隔离浏览器回归，覆盖 1280 / 390 / 320 像素布局。本次文档整理不把这组结果当作重新执行的测试，也不据此推断真实 GitLab、模型与飞书再次验收通过。

运行方式见[前端交互回归](frontend-interaction-checks.md)；后端命令见[部署说明](deployment.md#质量检查)。早期联调与测试数量保留在[实施进度](progress.md)及阶段记录中。

后续维护重点：

1. 按最终部署环境验收真实入站 Webhook、MR 更新 / 合并、重复投递与异常恢复；历史跑通不等于当前凭据和网络仍可用。
2. 定期演练数据库和主密钥的成对备份恢复，检查磁盘容量、保留期与 OCR 工件治理。
3. 升级 OCR 或模型配置前核对队列和配置快照，避免旧任务静默使用新配置。
4. 大规模问题历史目前仍由详情接口返回后在前端分段展示；若数据量持续增长，再增加服务端历史分页，而非仅继续扩大渲染条数。
5. 主导航移除不等于旧页面和 API 已下线；若后续要彻底移除配置历史或运维能力，需单独评估兼容、权限、审计和维护路径。
