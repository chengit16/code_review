## 1. 本次交付

| 能力 | 实际实现与边界 |
| --- | --- |
| 失败结果兼容 | 失败 manifest 的 `comments: null` 按空发现保存，仍为 `failed`；完整结果的空值、错误集合类型或非对象条目拒绝，不降级为零发现成功。 |
| 可信错误摘要 | 从受支持的 `ocr.llm-retry-report/v1` 提取最后失败请求的 HTTP 状态，保存安全中文摘要、错误类别与重试决定，不转发外部 `message`、请求、响应或模型推理。 |
| 有限整批重试 | 仅明确网络瞬断、429 和 5xx 有资格额外重试一次；永久错误、未知错误和整体超时停止自动整批重跑。已完成或复用部分覆盖的失败结果也不整批重跑。 |
| 尝试记录 | 合并后失败尝试保留开始时间、配置快照、范围、可信结果、已知用量、内部请求重试计数及结果路径；重启不重置次数。人工重评审保留原历史并按既有机制开始新周期或建立新快照任务。 |
| 共享预算 | 语言配置、provider 配置、预览与正式 OCR 评审共用一次截止时间，不再分别获得完整预算。Git 准备不包含在这段 OCR 预算内，配置及预览的独立短上限留待第二阶段。 |
| 受控诊断 | 持续排空 stdout/stderr，但每条流仅采集最多 40,000 字节；脱敏完整密钥及采集边界的密钥残片后，每份日志最多保存 20,000 字符，权限 `0600`。 |
| 中断清理 | 超时、取消与 Worker 退出均收集已有输出并终止进程组；先 SIGTERM，必要时 SIGKILL，不因启动器或管道先关闭而遗漏同组后代。 |
| 合并前保护 | 共用结果校验与重试策略；新队列冻结 `execution_policy`。取消或新 MR 版本失效后，迟到失败不能把旧任务重新排队。 |

核心代码分为 `review_failures.py`、`review_results.py`、`ocr_commands.py`，由现有 `ocr.py`、`worker.py`、`storage.py` 和 `premerge.py` 接入。前端仅补充可选类型，没有改任务列表或详情布局。事件处理、飞书与 GitLab 发布仍使用原有独立重试流程。

## 2. 新策略的实际行为

新快照包含：

```json
{"review_policy": {"version": 1, "max_attempts": 2, "retry_on_timeout": false}}
```

| 故障 | 平台自动处理 |
| --- | --- |
| HTTP 400、401、403、404 | 立即失败，提示检查模型名称、端点与权限。 |
| HTTP 429、5xx 或明确网络瞬断 | 最多两次完整尝试，首次退避 20～25 秒；若服务端明确要求更长等待，在允许的 300 秒上限内尊重。 |
| `Retry-After` 超过 300 秒 | 不提前重试，转人工处理。 |
| 整体超时、未知异常、配置或结果校验失败 | 不自动整批重跑，保留安全错误及可用工件。 |
| 已有完成或复用覆盖的失败结果 | 不自动整批重跑，避免重复工作和计费。 |
| `partial`、取消或失效 | 不通过本次分类器触发整批重试；保留原生命周期规则。 |

`retryable` 只描述错误类别是否允许重试，`retry_scheduled` 才表示本次是否真正排队；达到总次数上限时后者为 `false`。OCR 内部请求重试通过 `retry_summary` 单独记录，本次没有修改 CLI 的内部重试参数。仅当平台拿到带响应头的 HTTP 异常时才能读取 `Retry-After`；OCR 报告没有提供该头时，不猜测服务端等待时间。

失败尝试有可信结果时保留原始 JSON 与安全投影。没有可信最终 JSON 时，用量仍为未知，不凭 stdout、半成品或错误正文补造覆盖或费用。诊断日志可能包含外部工具输出，只在受限工件目录保存，不能视为适合公开传播的脱敏报告。

每个 OCR 命令可生成：

```text
configuration-1.stdout.log
configuration-1.stderr.log
configuration-1.execution.json
preview.stdout.log
preview.stderr.log
preview.execution.json
result.stdout.log
result.stderr.log
result.execution.json
```

配置命令按实际执行顺序编号。元数据记录阶段、退出原因、退出码、剩余预算和实际时长；没有输出或预算不足未启动时也生成空日志。清理最多包含 5 秒 TERM 宽限、1 秒 KILL 排空及最终等待，计入实际时长，不把清理时间隐去。

合并前按每次尝试保存独立工件目录，但本轮没有新增逐次数据库历史表，当前行仍保存最近一次结果；完整的界面与历史口径属于后续阶段。

## 3. 数据库、升级与历史任务

迁移版本为 `34 → 35`，仅为 `premerge_reviews` 新增可空 `execution_policy` 列；旧任务保持 `NULL`，不回填或伪造历史策略。全新库、带旧队列的旧库升级，以及迁移失败时 DDL 和版本号共同回滚均有自动化测试。

旧合并后任务仍受配置哈希校验约束：新代码增加策略快照后，尚未执行的旧快照不能静默采用新规则。合并前旧任务也会在访问 Git 和模型前失败，提示按当前版本重新审查。恢复逻辑对旧快照保留原三次计数上限，对新快照使用两次上限；这不代表允许旧快照绕过配置冲突检查继续执行。

上线前按[部署说明](deployment.md)操作：

1. 在无生产写入的副本演练升级和恢复；对数据库与私有配置做成对备份，确认凭据可解密。
2. 协调停止新增入口，处理在途与旧队列，选择 OCR 空闲窗口停止旧进程；不能直接重启而忽略未完成任务。
3. API、Worker、monitor 使用同一版本，迁移后检查健康状态和测试项目，再恢复入口。旧队列若未提前清空，必须明确人工重评审方案，不改数据库快照绕过校验。
4. 不自动重跑历史超时任务；404 类任务须先确认模型连接，再由管理员确认重评审。
5. 若需回退旧代码，旧版不能直接打开版本 35 数据库；停止进程，在新目录恢复成对备份，并先确认上线后新增记录的补偿，不降低数据库版本号、不覆盖活跃数据库。

本次未执行上述生产操作，没有修改生产参数、生产数据库或真实任务，也未重启服务。
