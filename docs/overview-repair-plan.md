# 运行概览修复与信息层级优化方案

> 关联事项：PI-20261108-004；关联基线：PI-20261108-003、PI-20261108-002。规划日期：2026-11-08（北京时间）。用户已认可“运行异常与代码问题分开呈现、压缩重复卡片”的方向；本文将其转为实施方案，**业务代码未修改，未部署**。

## 1. 目标与实施边界

首页服务两类相关但独立的工作：值班人员恢复评审链路，开发人员定位尚待处置的代码问题。采用 impeccable 的 Operate 模式，优先可信、易扫描、可行动，不做整站视觉替换。

交付目标：进入首页即可分清“系统是否在工作”“哪些运行异常需要查看”“有多少代码问题仍待处置”，再通过最近评审定位具体任务。执行成功、代码问题处置、通知投递仍分别表达。

- 保留现有灰白蓝、字体、设计变量、Ant Design 与 `ListTable` / `ListTime` / `IssueSummary`，不增加组件库、图表库或全局状态库。
- 首页只读与导航，不增加启动 Worker、一键重跑、一键修复、批量重发或自动关闭问题。写操作留在已有受权限与确认保护的业务页。
- 只改概览及必要的摘要、导航范围、刷新缓存和趋势呈现，不重做任务详情、复杂配置表单、问题状态机或 Worker 调度。
- 任务主列表的耗时 / 尝试、创建时间和问题处置继续默认可见；本方案不删减这些字段。
- 不扩大聊天授权，不触发 GitLab、OCR、模型或飞书调用；规划、代码修改、本地验证和部署分别记录。

### 3.1 工作区布局与视觉

- 桌面使用一个工作区容器，运行异常和代码处置为两个子区，运行异常占较宽一侧；不新增一排同等权重的大数字卡片。
- 运行异常最多五种类型，逐行列出；同一事实只在这里作为主计数，原顶部“待关注评审”大卡删除，异常总项数徽章删除。单一异常仍是紧凑一行，不拉成巨大红底。
- 红色用于确定的执行失败或需要恢复的阻塞；部分覆盖用警示色，普通问题入口使用现有链接色。严重级别始终有文字，不只靠颜色。不要把“已完成”改成“代码安全”或“评审通过”。
- 768px 及以下工作子区按顺序纵向排列；320 / 390px 下异常的类型、数量与入口允许换行，不截断单位与限定。最近任务保留紧凑卡片，不靠隐藏核心字段缩短页面。
- 单个子区为空或新字段缺失不能让其他已成功区域消失；独立请求分别容错。同一概览请求整体失败时保留其整份旧数据并标为过期，不虚构其中某个子区已单独刷新成功。内容不设置会截断长中文的固定高度，焦点顺序与阅读顺序一致，常用触控目标不小于 44px。
- 不新增装饰性动效；必要 loading 或展开反馈沿用组件，尊重减少动态效果设置。

## 4. 业务口径与入口契约

### 4.1 运行异常：按类型展示，不求混合对象总和

| 类型 | 计数对象与范围 | 目标入口 |
| --- | --- | --- |
| 评审执行异常 | 沿用 `task_view_clause('attention')`，同项目、MR、提交与基线的后续完整结果才可覆盖旧异常。 | `/jobs?view=attention` |
| 飞书通知失败 | 沿用 `task_view_clause('notification_failed')`，以有失败投递的任务去重；初审和符合当前来源条件的补充通知均保留。显示“N 个任务通知失败”，不冒充投递条数。 | `/jobs?view=notification_failed` |
| 合并事件需要恢复 | `needs_attention` 且项目启用的事件，单位为事件。 | `/events?status=needs_attention&actionable_only=true`，新增范围参数见第 5 节。 |
| 合并前审查失败 | 启用项目且合并前设置启用；先确定每个项目 / MR 最新接收版本，再筛失败，单位为 MR。 | `/premerge?status=failed&latest_only=true&actionable_only=true` |
| 合并前审查覆盖不完整 | 同上，最新版本状态为 partial，单位为 MR；与失败分行。 | `/premerge?status=partial&latest_only=true&actionable_only=true` |

不同类型可能关联同一业务链路，不能直接相加宣称唯一待办数；可不显示总数，首版采用此方案。Worker 健康是服务状态，不再加到异常任务数中。恢复入队或重发请求成功仍不代表执行完成。

### 4.2 代码问题：跨任务、全量、持久化问题口径

- 使用 `review_issues.status='open'` 的问题记录计数；一次问题多次出现只算一次，已合并来源不算，开放目标算一次；fixed / ignored 不在待处置数中。
- 范围与无其他筛选的 `/api/review-issues?status=open` 完全一致，包含已暂停项目的历史开放问题；不因项目停用、时间变旧、后续不再出现而自动移除或修复。
- 首页这一区不继承效果区的 `repository_id`、`days`；清楚标注“全部项目”。效果区仍按用户筛选显示自己的时间窗口，不从筛选后的 `open_now` 冒充全局数。
- 分级只统计开放问题：critical / high / medium / low，其余与空值归“未分级”，不推断为低危。分级之和必须等于待处置总数。
- 总入口 `/issues?status=open`；严重和高危分别使用 `severity=critical` 与 `severity=high`，不使用现有接口不支持的合并级别参数；未分级首版只展示数量，不创建无法精确过滤的伪链接。
- 最近任务的 `IssueSummary` 仍是该任务当前有效发现所关联的问题。多个任务可引用同一个开放问题，因此任务行数量不能相加成全局数；全局问题库也不等于“最近任务的当前发现集合”。
- 查询失败、旧后端缺少新摘要或关联未知时显示待核实 / 暂不可用，不补零。成功读取且确实没有开放问题时才展示零态。

### 4.3 运行概况与最近评审

保留仓库数、排队 / 运行、已完成 / 全历史及历史失败，但移至最近评审之后，以紧凑信息带呈现。不同历史终态不要求相加等于总量，按需说明部分完成、跳过与取消等独立状态。

实施时以任务列表的共享事实校验“排队 / 运行”的数量与目标筛选范围，尤其包含活动补审；当前源码概览使用初审原始 queued / running，而 active 视图还包含补审，不能直接用原始两项相加保证与入口一致。此处为源码发现的验收风险，本轮未再做运行复现。新增 `activity` 摘要，先应用同一个 active 条件确定任务集合，再结合 `list_status` 投影分组；同任务存在多个活动来源时按任务去重，运行优先于排队，`total` 与 active 列表一致。旧 `summary.queued` / `summary.running` 保持原语义，不为兼容字段静默换口径。

最近评审仍按原顺序只显示最近八条，不改成只看异常。增加可复用 `JobTimeFacts` 的耗时 / 尝试列，直接复用已持久化的尝试与起止事实；初审与补审分清，不把初审时间称为全任务耗时，缺失显示未知。创建时间不删除；手机同样可见，不将其全部放入详情。

## 5. 最小技术方案

### 5.1 概览摘要与导航范围

1. **扩展而不替换 `/api/overview`。** 保留 `summary`、`todo`、`recent` 和既有其他返回字段，新增 `issue_todo`（`open_count` 与固定分级 `severity_counts`）及 `activity`（`queued` / `running` / `total`）。成功摘要计数须为非负整数，不能用默认零掩盖缺失字段。建议新增具名 API 类型和 Service 文件 `frontend/src/api/overview.ts`，沿用 `apiRequest` 与取消信号，页面不另建 HTTP Client。
2. **共享查询基础。** 问题全局摘要与问题列表共用同一开放问题范围定义；同一读事务内聚合总数和分级，不逐条请求详情、不拉取问题正文。已有数据可聚合，预计不需要数据库迁移或历史回填；实现若发现必须迁移，先单独说明，不暗中扩展范围。
3. **一致性边界明确。** 运行聚合与新增问题聚合在概览读事务中完成；健康、最近任务读取、效果查询当前属于独立读取，不能宣传为全页原子快照。不要为强求一致性复制整套 `search_jobs` SQL；若抽取连接内复用入口，必须保护原分页事务与性能。
4. **补齐首页限定范围的目标入口。** 当前事件 / 合并前列表默认范围比首页启用范围广。为其搜索接口新增可选 `actionable_only: bool = false`；事件限制项目启用，合并前限制项目及设置启用，默认行为与旧 URL 不变。计数、items、total、状态分面应用相同范围；前端 URL 保留并显示“当前启用范围”条件，可清除查看历史，不把参数仅写进 URL 而后端忽略。
5. **旧后端兼容。** 缺少 `issue_todo` 时只将新问题汇总显示为“当前服务暂不提供汇总”，其余页面可用，仍可进入问题列表；不从最近八行或效果区偷偷补算。`actionable_only` 属配套前后端改动，正式发布必须用同版 API 验证其生效，不能把旧服务忽略参数当作正常范围匹配。
6. **缓存闭环。** 问题单条处置、批量处置、重开、合并，以及任务发现里的相关变更成功后，将 `overview` 纳入已有精确失效集合；保留既有 jobs / review-issues / review-effectiveness 等刷新。只标记反馈而没有改变问题状态时不能误减总数。已有事件重试的概览失效继续保留；页外数据变化由轮询或返回刷新收敛，不承诺跨标签实时一致。

### 5.2 健康、刷新与旧数据

| 状态 | 页面行为 |
| --- | --- |
| 首次无数据 | 对应区域 Skeleton / 加载提示；Worker 显示正在检测。不显示零数量或确定停止。 |
| 最近一次读取成功 | 标签与提示来自同一成功结果；running 仅说明 Worker 进程状态，不证明外部系统全部正常。 |
| 有缓存且正在刷新 | 保留稳定内容，显示正在刷新；上次成功时间不提前更新。 |
| 读取失败且有缓存 | Worker 当前状态未知；缓存事实明确写“上次检测”。概览旧数字标为上次成功数据，不清空伪造零。 |
| 读取失败且无缓存 | 当前区域不可用，提供重新读取；其他成功区域正常显示。 |
| 部分资源刷新失败 | 逐区保留成功 / 失败结果，不统一提示全部更新成功。 |
| 401 / 403 | 沿用现有认证与授权错误处理，不在页面内泄露额外信息或无限重试。 |

- Worker 状态标签和停止告警共用可信度判定，不能一个依据 `isError`、另一个直接读旧 `data.worker`。所有旧数据都携带其最近成功时间。
- 用各查询的 `dataUpdatedAt` 展示“成功读取于”，含完整日期与时区可访问入口；它是客户端成功读到的时间，不是业务事件发生时间或后端事实的精确截止时间。
- 健康、运行数据、效果统计分别有读取时间；页面不能以最新一份请求的时间盖住其他失败区域。
- 手动刷新使用 Ant Design Button loading 与可访问状态，聚合本次请求结果、禁止重复手动提交；首次加载与 `isFetching` 分开处理。局部完成或失败也会结束 loading，不因某个缓存错误永远锁住按钮。
- 自动轮询不重复播报所有数值、不抢焦点；手动完成与失败使用简短状态提示。沿用健康 10 秒、概览有活动约 5 秒 / 空闲约 30 秒、效果约 30 秒的现有基准，不为每一行新增轮询；页面不可见或卸载后不增后台工作。
- 健康确定停止时，管理员可进入 `/operations?tab=runtime`，读者角色不显示不可访问的管理入口，提供“联系管理员”说明；启动指引引用已有部署说明，不新增进程控制 API。

### 5.3 趋势图与组件拆分

- 保留 7 / 30 / 90 天、90 天按周聚合、项目筛选与 URL 参数；图、图例、数据表使用同一份 `trendBuckets` 结果。
- 当前服务端趋势按 UTC 日期分桶，本批标明这一范围并保持兼容；不要仅把横轴转换为本地日期而不同时调整聚合规则。任务创建时间与读取时间仍按既有显示时区，并可查看完整时区信息。
- 趋势数据表列为“日期 / 起止日期、新问题、人工标记修复”，周桶显示真实起止日期，最后不足一周不补造天数。零值可读，长时间范围不靠缩小到不可辨认的字号解决。
- 数据表默认折叠，展开入口用 Ant Design Button 或合适的展开组件，提供展开状态和目标关联；表格保留语义表头，支持键盘与读屏，不要求每根柱子都进入 Tab 顺序。
- 图表给出简短数值总结，触控和键盘可通过数据表读精确值；390px 以下减少可见日期标签，底层数据不减少，必要滚动只发生在局部容器。
