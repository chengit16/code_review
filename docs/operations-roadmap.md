# 长期运维完善任务

> 阶段实施记录：文中的范围与测试结果只代表当时状态。合并前审查、GitLab 行内发布与账号认证后来已实现，当前菜单与运维进程见[项目总览](project-overview.md)及[部署说明](deployment.md)。

按用户确认的顺序推进，每阶段验证后单独 Git 提交。管理台继续使用本机开发模式，评审引擎保留 Open Code Review。

- [x] 第二阶段：项目、飞书、模型配置版本与字段审计，按对象恢复且保留业务历史。
- [x] 第三阶段：保存前配置预检、项目接入状态与配置版本生效状态。
- [x] 第四阶段：队列、耗时、失败率、磁盘、备份与异常展示，人工确认的数据维护。
- [x] 第五阶段：发现反馈、反馈统计、项目通知阈值与审查规范配置。

## 边界

网络连通检查由 Worker 异步执行；保存前预检进行结构、来源与关联校验，不发送消息或调用模型。配置版本密文留在受限数据库，页面只返回字段摘要；恢复操作仍校验业务身份和待处理队列。报告下载使用固定字段投影，排除模型推理和凭据。维护操作先预览，保护未完成任务，并记录审计。

真实入站 Webhook 验收仍需用户提供 GitLab 可访问的 HTTPS 内网穿透地址。合并前阻止合并、GitLab 写回和多用户认证不在本轮范围内。

## 验证记录

- 第一阶段：后端 122 项测试、mypy、前端 lint/build 通过；报告下载验证管理鉴权、凭据替换与嵌套推理过滤，251 条历史记录验证超过原 200 条窗口仍可检索。
- 第二阶段：后端 125 项测试、mypy、前端 lint/build 通过；项目恢复保留事件，飞书和模型恢复成功，历史响应不含凭据，事务失败不留下版本。共享管理会话无法辨别具体操作者；将来引入用户角色后再记录用户身份。
- 第三阶段：保存项目时先执行无副作用的来源预检，连接测试与项目版本 ID 绑定；修改后旧测试变为待重检。真实 Git 与 GitLab API 连通性仍由 Worker 在保存后检查。
- 第四阶段：运维页面展示队列、重试、通知失败、近七天平均审查耗时、备份完整性及磁盘余量。旧工件清理须先预览且人工确认，仅清理已结束且通知不在途的目录，保留 SQLite 结论。备份目录默认位于数据目录的上级 `backups/`；其他部署布局可在后续扩展为独立配置。
- 第五阶段：任务详情可将单条发现标记为“有帮助 / 误报 / 已修复”并撤销；审核规则页按项目展示已标记反馈与误报率，分母不包含未标记发现。项目可设置飞书重点发现的最低严重级别，该设置进入任务配置快照，已有任务保留原阈值；卡片始终保留完整发现计数和评审结论。审核规范继续由现有项目规则、仓库 `rule.json` 与全局规则管理，避免维护两套互相冲突的 Prompt。新增测试覆盖旧库迁移、反馈鉴权和索引校验、在途任务保护、重审清理及卡片结论。
