# 任务处理状态与飞书卡片反馈同步调研

调研日期：2026-11-10（北京时间）。关联台账：PI-20261110-002。本轮只读调研与方案记录，不实施业务代码、不发布、不实发飞书。

## 1. 结论

- 任务列表外层显示“待处理、处理中、已处理”可行，可复用当前有效发现反馈摘要，不必增加可与发现事实冲突的任务完成开关。
- 新飞书卡片首次发送时增加处理状态、反馈进度及反馈入口可行，但保持现有 webhook 时，网页后续反馈不能直接更新原卡片。
- 网页反馈后更新同一张飞书卡片可通过应用机器人消息 API 实现，需要新增应用身份、群接收配置、消息映射和持久化同步队列。
- 本次核对的消息卡片 PATCH 接口仅支持发送后 14 天内更新。不能据此承诺永久可更新；其他 CardKit 路径本轮未验证，不作为已确认替代能力。
- 已发出的旧 webhook 卡片没有可直接承接的更新链路，不承诺原地迁移；保留旧消息，通过新应用发送新的状态卡片或独立进度通知，并明确关联任务。

## 3. 建议状态语义

按项目当前约定，“处理”指发现已阅读并提交有帮助、误报、忽略之一，不代表修复验证。

| 条件 | 外层或卡片展示建议 |
| --- | --- |
| 有发现，全部未反馈 | 待处理 · 已反馈 0/N |
| 部分已有反馈 | 处理中 · 已反馈 M/N · 待反馈 N−M |
| 当前发现全部已反馈 | 已处理（反馈完成）· N/N |
| 完整有效评审且零发现 | 无需反馈；保留“未发现问题”及原覆盖范围 |
| 部分覆盖，当前已发现均已反馈 | 当前发现已处理 · 评审覆盖仍不完整 |
| 反馈或结论缺失/不一致 | 状态待核实，不补零、不宣称完成 |
| 撤销、新补审发现、重新评审 | 按最新有效来源重算，允许退回待处理；历史卡不得冒充新评审结论 |

示例文案为方案，不是真实任务验收数据：

- 标题：`处理中 · 已反馈 3/5 · 待反馈 2`。
- 完成后：`已处理（反馈完成）· 5/5`。
- 正文单列原始评审：`评审发现：中危 2 · 低危 3`，不因反馈完成删去发现或改成“无问题”。
- 底部保留“查看完整评审”，可增加“处理待反馈发现”的跳转；当前 webhook 只支持链接跳转，不能将按钮点击直接当作已处理。

## 4. 飞书官方能力核对

以下公开 Markdown 正文已在本轮通过 HTTP 实际读取，不仅依据搜索摘要。普通 HTML 是前端壳，曾尝试的 `message/patch.md` 返回 404，改为官方卡片专属路径读取成功。

1. [自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)：自定义机器人无数据访问权限；成功响应示例为 `data: {}`，不提供可供本链路使用的消息 ID。自定义机器人卡片只支持按钮或文字链接跳转，不支持请求回调交互。
2. [发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)：应用机器人可发送 `interactive` 消息，返回 `message_id`；给群发消息需机器人在群内并有发言权限。支持发送权限之一包括 `im:message:send_as_bot`；需有效访问令牌。发送 `uuid` 去重只在文档规定的 1 小时窗口内有效，不能宣称无限期绝对幂等。
3. [更新已发送的消息卡片](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch)：使用 `PATCH /open-apis/im/v1/messages/:message_id`；更新身份必须与发送身份一致，更新前后均需显式声明 `config.update_multi=true`；仅更新未撤回、发送后 14 天内的卡片。单条消息更新 5 QPS；卡片内容不超过 30 KB。权限可使用文档列出的 `im:message:send_as_bot` 或其他适用项，不应为方便额外申请全量历史读取权限。

网页反馈触发服务端更新不要求用户先点击飞书卡片，因此适用主动更新接口，不应误用卡片回调的 3 秒响应或 30 分钟延时更新窗口。第一版仅同步显示，不需要额外暴露飞书交互回调；若将来在飞书内直接反馈，需另行设计身份映射、权限、验签及重放保护。

## 5. 选项与推荐

| 路线 | 能做到 | 做不到或成本 |
| --- | --- | --- |
| 保留 webhook，增加静态状态 | 新卡片首次发送包含进度；链接到实时网页 | 原消息不随网页反馈更新，静态状态会过期，应注明发送时快照 |
| 保留 webhook，追加进度通知 | 完成反馈后发送新的关联任务通知 | 不修改旧卡，可能刷屏；需聚合去重及失败重试，不能冒充原卡同步 |
| 应用机器人发送并更新原卡（推荐） | 新发送的同一共享卡片随网页反馈自动刷新 | 需要应用开通/发布、权限与群加入、新凭据及消息映射；14 天等平台限制仍须兜底 |

推荐在用户确认后实施第三条，旧 webhook 保留兼容，不静默替换或向真实群发送测试。需要管理员准备应用的 App ID、App Secret、已加入的群 `chat_id` 及对应权限；凭据仅通过安全配置入口录入，不粘贴聊天或写入文档。跨租户、外部群与发布审核是否允许，需用目标租户的真实配置单独确认。

## 6. 推荐实现边界

1. **以数据库反馈为准**：保存或撤销反馈时，同事务登记任务与反馈版本的同步意图；HTTP 请求不调用飞书。兼容旧单项、稳定身份、批量部分成功及重审/补审来源变化。
2. **独立同步任务**：Worker 读取最新有效发现，短时间聚合同任务多次变更；每个消息串行更新，只重试通知。反馈保存成功与飞书同步成功分别展示，不因飞书失败回滚已保存反馈，也不重跑 OCR。
3. **持久化消息身份**：至少保存通知目标、发送应用身份、群标识、任务与初审来源、结论版本、消息 ID、发送时间、期望/已确认反馈版本、同步状态、重试次数及脱敏错误。首次发送成功但本地落库失败需有不确定结果恢复方案，不能盲目无限重发。
4. **防旧结果覆盖**：反馈版本与结论版本独立；新反馈产生后旧在途更新可能短暂可见，Worker 应继续追平最新版本并在完成时校验，不能只以时间戳去重。重新评审不把新提交结论覆盖到旧卡。
5. **历史证据不改写**：优先新增一张“当前任务进度”汇总卡作为动态对象；初审及补审证据保留原来源和覆盖说明。若在原评审卡内增设动态区域，也只更新处理进度，不改原始发现、覆盖和版本事实。
6. **明确兜底**：过 14 天、撤回、机器人退出群、权限变更、令牌失败时标记过期/失败，保留网页为实时事实。可经产品确认后仅追加一次关联状态卡；禁止失败时每次轮询都补发。多群投递按每个目标独立跟踪。

## 7. 实施前验收清单

- 合成测试：未反馈、部分/全部反馈、撤销、零发现、数据不可用、补审新发现、历史修复仍未评价、重新评审及多目标映射。
- 事务与并发：反馈成功但同步暂失败、同任务高频反馈合并、旧版本在途、Worker 崩溃恢复、首次发送不确定结果、消息更新成功后落库失败。
- 飞书适配替身：令牌过期、权限失败、限流、超时、撤回、超过更新窗口、错误消息身份与共享配置缺失；不把外部错误正文或凭据写入日志。
- 目标租户测试群：单独授权后验证应用发送返回消息 ID、网页反馈后同消息更新及所有群成员可见；该外部联调本轮未执行。
- 桌面与手机：列表处理状态、详情反馈及飞书同步失败/重试提示一致。部署须备份及迁移验证，不能以单测或文档调研替代生效确认。

## 8. 创建权限自查与操作指引

补充日期：2026-11-10。以下是操作指引，不代表已检查用户账号或已创建应用；控制台名称可能因界面版本不同略有差异。

1. 使用所在企业的飞书账号登录 https://open.feishu.cn/app，确认当前企业正确。在企业自建应用入口查看是否可以创建应用；按钮缺失、禁用或被策略拦截时，请企业管理员确认创建权限，或由管理员创建并将你加入应用协作成员。能登录控制台不等于拥有发布审批权限。
2. 选择“创建企业自建应用”，填写名称、描述和图标，例如“Code Review 评审助手”。不要在群设置里再次创建自定义 webhook 机器人，两种接入不同。
3. 应用内进入“添加应用能力”，添加“机器人”。本阶段只需通知发送与主动更新，不需要订阅群消息、通讯录或配置卡片交互回调。
4. 在“开发配置 → 权限管理 → API 权限”选择应用身份权限，搜索 `im:message:send_as_bot`（以应用的身份发消息）。根据已核对的发送与卡片更新接口权限表，这一项可覆盖二者，不必再机械申请 `im:message` 全量消息权限。若控制台或接口提示附加约束，以实际可申请权限与已发布状态为准；不能将勾选待发布当作已生效。
5. 如需通过 API 获取机器人已加入的群列表，可额外申请 `im:chat:readonly`；这是获取群标识的辅助权限，不是发送与更新的必选权限。使用“获取用户或机器人所在的群列表”接口，应用身份下选择目标群取得 `chat_id`，不要采集群历史消息。若已有管理员提供的正确群 ID，则不必为获取 ID 额外扩权。
6. 进入“应用发布 → 版本管理与发布 → 创建版本”，例如 1.0.0，先设置小范围可用人员，写明仅发送评审卡片和更新自身消息。申请线上发布，按企业策略等待管理员审核；企业可能已配置免审，不能假设所有租户都必须逐次人工审批或都免审。
7. 发布后在飞书电脑端进入测试群，“… → 设置 → 群机器人 → 添加机器人”，搜索应用机器人。如果找不到，检查应用是否已发布、机器人能力是否生效、可用范围与所在企业是否正确；如群限制添加机器人，请群主或群管理员协助。外部群另需核对企业认证及对外共享能力，不以普通内部群流程保证成功。
8. 在应用“凭证与基础信息”取得 App ID 和 App Secret，只在后续受保护配置中保存；不发送到聊天，不截图泄露。准备目标 `chat_id`。这些配置就绪后仍需本项目实现应用机器人适配、保存 `message_id`、共享卡片及同步 Worker，创建应用本身不会让旧 webhook 卡片自动更新。
9. 后续在单独授权的测试群验证：应用发送新卡片，保存返回的 `message_id`；使用同一应用更新卡片，前后均设置 `config.update_multi=true`；确认多成员可见。发送成功不能替代更新验证，14 天更新窗口等限制仍适用。创建测试企业只能用于隔离测试，不绕过正式企业审批，也不会自动获得正式群访问权。

## 9. 个人创建与企业使用的边界

补充日期：2026-11-10。官方最新[机器人支持外部群和外部用户单聊](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/develop-robots/add-bot-to-external-group)正文实际读取成功。本节补充第 8 节的外部群认证要求，不将此前简写的企业认证表述视为唯一途径。

- 个人账号若已加入公司企业，并在开发者后台切换至公司企业创建应用，应用仍属于公司企业；创建、协作、审核和群添加受公司权限策略控制，适合作为公司内部正式服务。
- 在个人版或个人所属的独立租户下创建应用，不会因此变成公司租户下的自建应用。不能把 App ID、App Secret 交给公司就视为完成安装、授权或应用所有权转移。
- 当前官方对外共享文档允许企业/团队认证或个人实名认证。个人实名认证适用于个人版用户或未认证企业成员，文档说明仅中国大陆地区支持；需以实际账号控制台可见入口及要求为准。
- 对外共享在“版本管理与发布 → 创建版本 → 对外共享”配置“允许机器人被添加到外部群中使用”，并按所属租户规则发布。该路径面向外部群及外部用户单聊，不是向另一企业普通内部群任意安装应用的通用能力。
- 添加到外部群的操作者须属于应用所属企业/租户，且在应用可用范围内；还受群设置、公司对外沟通及安全策略影响。不能将此路线用于绕开公司审批，或未经允许把含私有代码的评审内容发送至外部群。
- 个人拥有的应用与公司生产服务存在密钥控制、持续维护和人员离职风险。建议个人租户只做合成数据测试；正式服务由公司租户持有应用、凭据与管理员权限。
- 经公司允许走外部群路线时，应用仍需保存自己发送的新消息 ID，并联调发送及原卡更新；不承诺旧 webhook 卡迁移，也不承诺消除原卡更新窗口。对外共享权限不等于项目已接入或已通过真实验证。
