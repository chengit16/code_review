# 后台配置与接入操作

> 当前使用说明；项目结构与功能边界见[项目总览](project-overview.md)，其他资料见[文档索引](README.md)。

本文依据飞书《Review后台配置操作手册》的四块配置流程编写，并按本项目的 Alibaba Open Code Review（OCR）评审引擎调整模型设置。配置保存在 `OCR_APP_DATA_DIR/app.db`，凭据使用 `OCR_APP_MASTER_KEY` 加密；修改后台配置后无需重启 API 或 Worker。

管理员固定导航为项目总览、评审任务、评审发现、合并前审查、运行监控、平台改进记录、项目配置、系统设置八项。合并事件从任务页“合并事件记录”进入，只读账号保留此入口；配置历史从运行监控进入。系统设置含评审模型、飞书通知、评审规则、访问权限四个标签，默认评审模型，URL 支持刷新和前后退。旧 `/events`、`/config-history`、`/users`、`/feishu`、`/review-rules` 地址保留原权限。完整改造边界见[易用性实施说明](usability-simplification-implementation.md)。

首页“项目总览”展示同一项目和 UTC 7 / 30 / 90 天窗口内的当前有效发现：评审反馈四类数量、已处理与待处理、处理完成率，以及待反馈严重级别和项目反馈概况。三类反馈 helpful / false_positive / ignored 都算已处理，未评价和旧 fixed 反馈算待处理；撤销后回到未评价。已处理不表示代码修复，也不改变评审执行或通知状态。首页移除“问题状态 / 问题变化”切换和不限时间的旧处置计数带，原 `/effectiveness` 地址仍保留项目、日期筛选跳转到首页。

反馈趋势与精确表格共用数值，按发现产生日展示当前反馈构成，不代表当日评价操作量。初审以完成时间、有效补审主发现以来源出现时间入窗；初审镜像、旧尝试、未提升候选和附加重复来源不重复计数。UTC 90 天按七天汇总，末桶保留实际日期。有效评价占比为（有帮助 + 误报）/ 发现总数，误报占比为误报 /（有帮助 + 误报），放在可展开的“反馈统计口径”；忽略不算有效评价但算已处理。误报评价分母少于 5 条时不展示比例，不推断模型准确率。

点击反馈数量、进度、级别或项目进入“评审发现”列表，携带相同项目、显式 UTC 闭开窗口和反馈/处理条件，筛选先在服务端执行再分页。默认列表查看全部时间的待处理发现，支持全部、待处理、已处理，以及项目、反馈、级别和搜索。列表一行是一条当前有效发现，同一历史问题可关联多条发现，各条独立反馈。点击摘要或整行打开详情，复用任务中的描述、修复建议、三个反馈按钮与撤销；提交携带稳定身份和来源版本。409 保留目标及输入，刷新核对后重新选择，不自动重试。反馈成功会刷新任务、列表、详情和首页。来源缺失明确待核实，旧服务缺聚合不补零。

管理员可以勾选当前页发现并选择批量反馈，确认框展示每条主身份、任务及冻结版本；成功项刷新并移出选择，失败项保留，需显式刷新重新核对。切换筛选或分页清除勾选，不扩大到其他页。读者不能写入或批量反馈。任务列表“发现反馈”筛选也按当前发现的未评价/已处理判断；旧 issue_state 地址保留历史处置语义，清除对应“历史处置”条件即可退出。

“历史问题与修复记录”从发现列表或发现详情进入，旧 `/issues?issue=...` 链接继续打开原编号和跨任务出现、处置事件、人工说明，不把 fixed / ignored 等旧问题状态映射成反馈。详情提供关联的全部当前发现入口；多个发现不会只挑一条代表整组。历史独立处置和原批量修复功能保留在辅助入口，不回填、关闭或删除旧问题。旧首页 sample_open 链接仍可打开只读样本，但已移除问题处置筛选及列，旧 sample_status 会提示停用。

全平台 Worker 健康和运行摘要独立标注。评审执行异常、飞书失败、事件恢复和合并前审查分别保留原范围，不相加成唯一待办；生成、发布和人工修复辅助说明留在“更多效果分析与统计口径”。

健康、运行数据与项目统计分别显示客户端成功读取时间，不是全页原子快照。健康读取失败时 Worker 当前状态未知，上次状态只作历史说明；手动刷新有进行中和部分失败反馈。Worker 确认停止时管理员可进运行监控，读者联系管理员。运行异常摘要仅非零项显示为辅助入口，不把不同对象相加为唯一待办数。

系统设置中的审核规则、模型和飞书编辑支持未保存提醒。切换标签、侧栏、浏览器前后退或退出时可取消离开并保留草稿；刷新或关闭窗口使用浏览器原生提醒。草稿和新录入密钥仅保留在内存中，确认放弃或关闭浏览器后不会恢复。保存中暂时禁用表单，避免新输入被保存响应覆盖。

### 平台问题与改进

管理员可从“运维与审计 → 问题与改进”打开平台台账，与 OCR 的“评审发现”分开使用。第二阶段在“优化历程”中建立主题、按顺序维护阶段，并从现有问题记录中显式选择关联；主题或问题状态不会因关联而自动变化。记录分别保存代码修改、本地验证与部署生效及各自证据。本功能需要运行包含第 41 版迁移的同版 API 与前端；代码实现不代表当前业务实例已升级，升级要求见[部署说明](deployment.md)。

1. 点击“新增记录”，先填写标题、关联项目或功能、现象或目标，即可保存尚未解决的问题。后续按需要记录排查、无效尝试、解决办法、关联文件和下一步。
2. “代码修改”“本地验证”“部署生效”分别选择；本地验证通过、失败、受阻或不适用时必须填写结果或原因；部署已生效必须记录环境和证据，部署不适用时说明原因。
3. 标记“已解决”需要解决办法以及通过的验证或不适用说明，不要求已经部署。手工填写的状态和证据不代表平台已实际运行检查或核验部署。
4. 打开详情，点击“编辑并追加进展”，填写“本次进展说明”后保存；每次保存追加完整快照和操作者。历史按页读取，可展开核对当时的结论，当前摘要改变不会覆盖旧快照。
5. 多人同时修改产生版本冲突时，服务端拒绝覆盖并保留页面草稿；先核对最新详情，再决定如何合并。新建失败或响应丢失时先核对列表；同一份草稿以同一创建键重试不会重复建档，不能把不同事项复用同一键。

搜索支持标题、现象、原因、解决办法和关联功能；类型、分类、进展及分页条件保留在 URL。关闭编辑窗口、离开路由、刷新或退出前有未保存提醒，草稿只在内存中保留。只读账号不能通过菜单、深链接或 API 访问此台账。不要在正文中粘贴凭据、私有配置、完整外部响应或敏感代码；本功能不是自动脱敏工具。

“复盘汇总”展示当前累计与独立的活动趋势：可按分类及活动日期查询，日期默认最近 30 个北京时间自然日、最多 366 天。日期只影响新增/追加进展活动，不裁剪当前累计或待办；台账、主题与阶段分别计数。已解决占比不是本期解决率，保存次数不是解决数量，本地验证通过也不等于已部署。未解决、验证待跟进、部署待确认和未完成主题各显示最久未更新的前十条及总数，可点击定位详情；分组可能重叠。详细口径见[第三阶段说明](improvements-phase3.md)。

“问题记录”和“优化历程”默认显示未归档内容，可切换“已归档”或“全部（含归档）”。详情中点击“归档内容”，填写原因并确认；归档期间只读，点击“恢复内容”并填写恢复原因后才能继续编辑。任何处理状态都可以主动归档，但不代表解决、验证或部署；主题归档不级联问题，历史与双向关联保留。复盘累计及待办包含已归档对象，历史追加次数包含归档与恢复，待办排序按最近记录操作时间。详细边界见[第四阶段说明](improvements-phase4.md)。

会话结束后的持续记录先追加到[问题与改进台账](problem-improvement-log.md)，尚未自动导入 SQLite 页面。按时间自动归档、聊天采集与历史批量导入不属于当前交付；本阶段提供主动归档与恢复，不创建后台清理任务。

## 1. 保存、测试并按需设为默认模型

编辑已有模型时，“自动获取模型”可使用已保存的密钥，API Key 留空即可；修改 Provider 或 Base URL 后须重新输入密钥，防止保存的凭据被发送到其他端点。获取失败时会区分上游 HTTP 状态、连接超时、网络或 JSON 格式错误，不回显网关响应正文或凭据。模型目录列出的模型不保证都支持 OCR 评审，选定并启用后仍需连接测试。

打开管理台的 **系统设置 → 评审模型**，点击“新增模型”，填写配置名称、OCR Provider 和 API Key 后点击“自动获取模型”，再从返回列表中选择模型标识。该功能通过服务端请求 Provider 的模型目录；自定义服务需填写无凭据的 HTTPS API 根地址，通常以 `/v1` 结尾。目录接口未开放、权限不足或返回格式不兼容时，可继续手动填写模型标识。使用 OCR 内置 Provider 时，Base URL 留空；连接 OpenAI 兼容服务时不能填写只返回网页的站点首页。平台会在隔离的 OCR 配置目录中建立自定义 Provider。自定义端点与计价按需展开；已有自定义端点默认展开。保存后在对应行点击“测试 模型”，明确确认可能产生费用；测试不会切换默认，验证后再按需点击“设为全局默认”。模型可在列表中编辑；编辑时 API Key 留空表示保留原密钥。系统同一时间只启用一个模型；首次启用可处理此前积压的事件，后续切换启用模型时须先让队列清空；编辑模型不受队列限制。编辑后尚未开始的旧配置任务会因快照变化失败，可按当前配置重新评审；已经开始执行的模型参数保持不变。

保存仅将草稿和加密凭据写入 SQLite，不访问模型服务，字段不完整也可以保存。管理台编辑模型使用 POST 更新以兼容不转发 PATCH 方法的内网穿透；服务端仍按模型 ID 合并字段，旧 PATCH 接口继续兼容其他客户端。保存时出现 HTTP 502 属于管理服务或访问代理链路故障，不代表模型校验失败；先刷新核对配置是否已保存，再决定是否重试，避免重复创建。本机可访问 `http://127.0.0.1:8781/api/health` 核对 API 与 Worker 状态；直连正常但其他访问地址失败时，继续检查该入口的代理转发。模型连接测试可针对任一已保存且完整的配置；列表区分全局默认、项目指定数量和连接验证。测试结果绑定连接字段，修改 Provider、模型、端点或密钥后旧结果失效；仅改名称、单价或默认状态不改变同一目标的连接证据。历史无指纹测试标为待重新验证。测试返回 HTTP 401 时先检查 API Key 是否复制完整、是否属于当前端点；测试返回 HTTP 502 时检查模型网关或其上游服务，不要与保存请求的 502 混淆。

使用阿里云百练模型时选择 **百练 / DashScope**，填写百练控制台创建的 DashScope API Key 和该模型的精确标识，Base URL 留空。可按百练当前公开计费页填写计费币种及每百万输入、输出 Token 的单价；两项单价可分别保存，也可以都留空或暂填待确认文本；只有两项均为有效非负数字时才估算费用。单价仅用于估算，不参与 OCR 评审任务去重，也不会修改已经开始的评审快照。详情页分别显示 OCR 返回的输入、输出及合计 Token；仅当本次评审保存了两项单价且 OCR 返回完整输入、输出用量时，才计算预估费用。缓存折扣、阶梯价、赠送额度和其他账单项目不在估算范围内，以百练实际账单为准。旧任务缺少运行时单价快照时不会按当前价格补算。

“运维与审计”中的“管理操作审计”按页展示记录。审计只保存操作者、路由、对象、结果和时间，不保存请求体、密码或密钥。

本项目使用 OCR CLI，不使用文档中的 Codex 登录认证或 Responses API 配置。模型配置采用先保存、后测试的方式：名称、模型标识、API Key 可留空，Base URL 和单价尚未填写完整也可保存，不进行保存前校验。实际测试或评审时仍须提供可用配置，自定义 Base URL 需为无凭据的 HTTPS 地址并兼容 OCR 的 OpenAI 协议。模型密钥不会出现在列表、审计日志或评审工件中。

评审问题说明默认通过进程配置 `OCR_APP_REVIEW_LANGUAGE=zh-CN` 要求模型使用简体中文。该设置独立于文件审核规则，不改变规则优先级；修改后需重启 Worker，已有结果不会自动翻译，按当前配置重新评审后才会生成中文结论。

## 2. 新增飞书配置

在接收审核通知的飞书群中添加自定义机器人，复制完整 Webhook URL。建议在机器人安全设置中启用签名校验，并复制同一机器人的签名密钥。打开管理台的 **系统设置 → 飞书通知**，填写配置名称、Webhook URL 和可选签名密钥并保存。

一个飞书配置可以关联多个仓库。修改该配置后，后续投递和连接测试会读取新值；删除配置会解除所有仓库关联，仓库及其评审历史仍保留。无需关联仓库即可在通道列表或编辑窗口测试。先保存，再点击“测试 飞书”并确认真实外发；打开页面不发送消息。编辑未保存时禁用测试，测试通过不代表正式通知已投递；保存后可从“关联项目”继续配置。

## 3. 新增仓库

先在 GitLab 项目的 **Settings / Access Tokens** 创建项目访问令牌，设置到期时间，并授予读取代码和调用项目 API 所需的最低角色及 `api`、`read_repository` scope。令牌创建后应立即复制。

打开 **项目配置 → 添加仓库**，先填写无凭据 HTTPS 项目或 Clone 地址与本次 GitLab Token，再显式点击“获取项目资料”。Worker 只向指定同源主机读取项目 API，带出名称、数字 ID、路径、默认分支和 Clone URL，供核对后保存；不会自动创建仓库。失败、超时或停止等待后仍可手动填写；等待期间人工修改草稿会使旧响应失效。下表为核对或手填字段：

| 字段 | 填写方式 |
| --- | --- |
| 项目数字 ID | GitLab 项目首页或 Settings / General 显示的数字 ID。 |
| 仓库名称 | 管理台显示名称。 |
| 仓库路径 | 完整命名空间，例如 `team/order-service`。 |
| Clone URL | GitLab 的无用户名、密码和 Token 的 HTTPS 地址，例如 `https://gitlab.example.com/team/order-service.git`。 |
| 目标分支 | GitLab 默认分支，例如 `main`。 |
| GitLab Token | 上一步创建的项目或群组访问令牌。每仓库建议独立。 |
| Webhook Secret | 保存仓库时由服务端自动生成，随后在项目配置列表查看。 |
| 飞书配置 | 选择第 2 步创建的通知通道。 |
| Merge Request 审核 | 需要审查已合并 MR 时开启。 |
| 默认分支 Push 审核 | 需要审查直接推送到默认分支的提交时开启。 |

保存后打开已保存项目的基础接入窗口，继续配置 Webhook 和连接验证；飞书配置可暂不关联，之后在仓库编辑窗口关联。编辑窗口预填仓库名称、GitLab 地址、数字 ID、仓库路径、Clone URL、目标分支、飞书关联和事件开关，并提供 Git 与 GitLab API 连接测试。GitLab Token 和 Webhook Token 不在编辑表单回填明文，前者可单向替换，后者可按需查看、复制或轮换。项目数字 ID 或 GitLab 地址录错时，可在收到合法 Webhook 或产生评审事件之前直接修正；有待处理事件或评审任务时，暂不允许修改仓库来源或分支。HTTPS Git 拉取通过临时 `GIT_ASKPASS` 读取项目令牌；令牌不写入 Clone URL、Git 命令参数或本地 Git 配置。旧数据库中的 SSH 项目可读取历史记录，但继续运行前需要在项目编辑窗口补录独立 GitLab Token；管理台新建项目只使用上述字段。

项目编辑窗口分为“基础接入”“评审参数”“发布审查”“接入诊断”四个页签，切换页签保留当前窗口内的草稿，不会自动保存。URL `repository=<编号>&section=connection|review|publication|diagnosis` 可直达项目和分区；分区切换不堆积浏览器历史。基础接入、评审参数、合并前配置分别保存，按钮明确各自范围；基础接入保存后窗口保持打开，不丢弃其他页签的内容。GitLab 行内评论开关为自动保存，旁边单独反馈保存结果。关闭窗口、离开页面或刷新时，未保存内容会触发确认；确认放弃后内存草稿清除，不恢复密钥草稿。

评审参数和合并前配置首次读取失败时，不提供可保存的默认配置，应先点击“重新加载”。保存失败与读取失败分别提示，保存失败保留草稿，可核对原因后重试。后台重新读取不会覆盖正在编辑的评审参数或合并前草稿。

### 项目接入清单与生效来源

项目配置中的“项目接入清单”按当前项目计算四项连接准备：保存接入、当前实际模型通过、Git 与 GitLab API 通过、所选通知通过或未选择通知。新项目不会清零其他项目；读取失败显示待确认并按项重试。达到 4 / 4 只表示连接准备完成，不是端到端评审验收。历史 Webhook 与任务另行展示，不冒充当前配置已试运行；真实试运行须明确提交，可能产生模型费用和通知。

“评审参数”顶部显示后续任务的已保存模型、全局继承或项目覆盖、超时及来源、文件和 Token 限制、页面规则配置及基础接入最近保存。未保存草稿不算生效，在途和历史任务仍核对各自快照。仓库规则文件要等对应提交执行时读取，摘要不预先证明内容；可跳转本项目规则和预览。运行监控维护视图另有脱敏只读部署摘要，区分需重启的进程配置、可热应用的任务数以及单任务内部并发，不以 API 进程值代替 Worker 应用证明。

## 4. 配置 GitLab Webhook

在 **项目配置** 页面复制统一回调地址，并从对应仓库行查看或复制 Webhook Secret。进入对应 GitLab 项目的 **Settings / Webhooks**：

1. URL 填写管理台给出的 HTTPS 回调地址，路径为 `/api/webhooks/gitlab`。
2. Secret token 填写该仓库的 Webhook Secret。列表默认遮罩，可按需查看和复制。重新生成后必须同步更新 GitLab。
3. 开启 Merge Request 审核时勾选 **Merge request events**；开启默认分支 Push 审核时再勾选 **Push events**。
4. 保持 SSL verification 开启并保存。

GitLab 必须能访问回调地址。`127.0.0.1` 只适合本机开发，正式部署应由受控 HTTPS 入口仅转发 `/api/webhooks/gitlab`。不匹配的项目、分支或未启用事件返回 HTTP 204；匹配项目的错误 Secret 返回 HTTP 401。默认只在 MR 合并后入队；默认分支 Push 只审查快进更新，并将一次 Push 的 `before..after` 最终净差异作为一个任务，首次创建分支、删除分支和强制改写历史不会自动审查。

## 5. 验收与安全

在 **系统设置 → 评审规则** 标签页选择“全局规则”或具体项目后，可添加按文件路径匹配的审核内容，并配置额外纳入或排除的路径。规则条目按页面顺序匹配，首条命中生效；“同时保留 OCR 内置语言规则”对应 `merge_system_rule`。项目页面规则优先于仓库提交的 `.opencodereview/rule.json`，全局页面规则是仓库文件之后的兜底。保存后仅影响后续任务；已有排队或运行中评审时，系统会拒绝修改适用规则。页面下方保留最近 50 个规则版本，删除配置也会生成历史版本；恢复旧版本会新增一条恢复记录，同样受待处理任务保护。核对仓库文件规则时使用 `ocr rules check <文件路径>`；核对页面项目规则时，可将任务运行目录中的 `managed-rule.json` 传给 `ocr rules check --rule <规则文件> <文件路径>`。

“规则生效预览”接收仓库内的相对文件路径。全局规则范围须先选择目标项目；项目规则范围自动使用当前项目。请先保存规则再发起检查。Worker 拉取目标分支，在固定提交的隔离目录运行 `ocr rules check`，页面显示命中来源、路径模式、规则正文和提交短 SHA；此操作不调用模型，也不创建评审任务。结果代表该提交及检查时已保存的规则，不代表尚未保存的编辑内容。

GitLab 测试投递后，在 **项目配置** 列表查看最近验证时间，并结合 GitLab Webhook 的响应状态核对结果。未匹配的项目或目标分支、非合并 MR、关闭的事件开关和重复投递不会创建评审任务；错误 Secret 返回 401。服务端只保留最近 500 条脱敏诊断元数据，不保存请求体、令牌或原始标头。

需要合并前审查时，在项目编辑窗口启用“合并前审查”，并在 GitLab Webhook 中勾选 **Merge request events**。可以勾选纳入 MR 描述，并填写最多 3 份仓库内 `.md` 或 `.txt` 文档路径，每行一份，例如 `docs/review-context.md`；路径对应待审 MR 的头提交，文件须是普通文本文件，不能是符号链接。新建、重新打开或更新 MR 后，Worker 会核对 GitLab 当前提交版本，以目标分支共同祖先和 MR 头提交运行完整差异评审；提交或描述变化会建立新版本，配置变更也会使旧结果失效并重新排队。详情页只展示业务背景的来源和摘要，原文仅保存在受控运行工件中。当前实现只在管理页展示合并前结果，不向 GitLab 或飞书自动发布，也不阻止 GitLab 合并。合并后的 MR 逐提交评审仍按原开关独立运行。

在 GitLab 项目的 Webhooks 页面发送测试事件，确认管理台的项目配置列表最近验证时间更新；随后合并测试 MR 或向默认分支推送测试提交。到 **评审任务** 查看状态、耗时与消费，确认飞书群收到通知。MR 合并任务按提交展示，默认分支的一次 Push 只展示一个范围任务；漏投或历史 MR 可在同一页面按 IID 补触发。默认不向 GitLab 写回。需要 MR 行内评论时，在项目编辑窗口单独开启“GitLab 行内评论”，并确认项目令牌拥有创建 discussion 所需权限；只有能在 MR 当前 diff 中定位到新增行的发现会发布，其余显示“已跳过”。行内发布失败可在任务详情独立重试，不会重跑 OCR 或飞书通知。Push 任务不向 MR 发布。

**合并事件**页面按项目、状态、MR IID 和接收时间检索持久化事件，分页和条件保存在地址栏。需要处理的异常事件可由管理员确认后重新排队；Worker 会再次向 GitLab 核实项目、MR 和提交范围。管理员也可提交最多 31 天的历史合并时间范围，申请由 Worker 后台扫描，页面上的申请状态只表示扫描进度，不代表 MR 评审已完成。只读账号可以查询事件，不能重试或申请补审。

合并前审查详情中，管理员可取消排队版本或停止运行版本；运行中的 OCR 收到停止信号前可能短暂继续消耗资源，但迟到结果不能覆盖已取消状态。最新终态版本支持重新审查，会创建新版本并再次调用模型，可能产生费用；旧版本和旧结论保留为历史。

开发模式 `OCR_APP_DEV_MODE=1` 仅适用于可信本机；正式环境必须设置 `OCR_APP_ADMIN_TOKEN`，并限制管理页网络访问。需要多人账号时，先在 **访问权限** 页面创建至少一名管理员，再启用“多人账号登录”。启用后共享管理口令立即失效，页面重新登录；可继续创建只读账号。管理员可调整角色、停用、重置密码或删除账号，最后一名启用管理员不能停用或删除。只读账号可查看运行结果，不能修改配置、重试任务或查看 Webhook Token。账号登录凭据只保留在当前浏览器内存中，刷新页面后需重新登录；审计表显示操作者，旧审计记录显示“旧记录”。需要回到原有本机或共享口令模式时，由账号管理员在同页关闭多人登录。`OCR_APP_MASTER_KEY`、数据库和备份都应按敏感文件保护。不要把 GitLab Token、Webhook Secret、飞书 URL、签名密钥或模型 API Key 写入 Git、截图、Issue 或日志。

飞书手册的 `service.env`、`projects.yaml` 和 `CODEX_*` 首次导入命令属于另一套实现；本项目当前通过管理台和 `OCR_APP_*` 进程配置接入，不会读取这些文件。运行服务和 Worker 的步骤见[部署说明](./deployment.md)。
## 6. 评审发现的就地处理

### 任务检索与重审

“评审任务”提供排队与运行、待关注、失败、部分完成及飞书失败快捷筛选；也可按项目、状态、MR IID、SHA 前缀、分支与时间检索。显式选择状态后会清除快捷视图，防止冲突条件导致意外空列表。列表直接展示状态原因、累计执行、首次排队、总历时和独立飞书状态；只有完整完成任务显示发现数与最高级别，失败、部分完成、跳过和取消不以零发现暗示通过。重审开始后不沿用上一次尝试的发现数。费用列为历史各次单价计算的“累计预估费用”，不同币种分列，缺少用量或价格时标记不完整，不是供应商实际账单。

管理员可勾选当前页终态任务后点击“重审所选任务”；提交前确认任务数与模型费用影响，每项入队或拒绝单独回显。补触发 MR 和手填任务编号的重审位于“补触发与高级操作”中。重新评审只安排任务，不自动修复代码；通知失败优先在任务详情点击“重发通知”。

SHA、分支与起止时间收纳在“更多筛选”，已生效条件显示为可单独移除的标签。任务、问题及合并前列表均可选择每页 25 / 50 / 100 条，并跳转到指定页；条数与筛选保存在 URL，刷新后保留。当前页重审只取消成功入队项的勾选，拒绝项保留，核对后可再次提交；请求期间不能改变选择、筛选或分页。未勾选任务且无操作结果时，不展示空的批量重审栏。

任务详情优先展示失败原因与评审发现；变更文件和排除范围、历史报告与对比、执行记录默认折叠。结束任务降低轮询频率，不影响独立 Worker 持续执行。

“耗时与范围诊断”区分首次排队、本次/末次执行、累计执行、重试退避、就绪后等待与总历时；三次各一小时应显示累计三小时，排队六小时但执行一秒不会合算为执行六小时。旧数据缺失和 Worker 中断时真实结束时间未知，不能把恢复时间当作精确运行时长；历史报告保留指定尝试事实，不套用当前取消状态。

固定范围预检只读 Git 对象，显示原始变更、确认仅换行、策略排除和 OCR 候选计数。自动换行过滤默认关闭，可在 **项目配置 → 编辑 → 评审参数 → 自动过滤纯换行文件** 勾选并保存。开启后，仅排除固定 Git 对象确认只有 CRLF/LF 变化、且双预览校验通过的路径；无法编码或未确认的文件继续纳入。逻辑、缩进、权限、类型及增删变化不免审。过滤后才检查 `max_files`，原始范围、策略排除和实际候选分别披露。开关保存期间如项目有合并前/合并后排队、运行任务或待处理事件，会返回冲突并保留草稿。新旧策略不能混跑，详见[过滤实施记录](review-newline-filter.md)。项目 `max_files` 是实际候选上限，超过时失败而不是截取前 N 个；`200` 仅为试点建议，未自动修改已有项目。Token 预算需代表性任务校准，并非精确费用硬上限。

“运行监控”的近七天指标按项目、状态、原始规模分组，展示成功累计执行及首次排队 P50/P95、样本数、本组超时占比、重试和已知 Token 下限；跳过不混入成功模型执行样本，小样本 P95 不代表稳定线上表现。单 Worker 并发没有改变，跳过依然可能排队。实现与发布边界见[第二、三阶段实施记录](review-performance-phase23.md)。

第四阶段增加“Worker 调度与执行槽”：同版 Worker 启动后显示模型、事件/Git、通知/行内发布三个槽及心跳，不需要额外开关。模型任务总并发仍为 1，后续跳过不越过前序评审，但通知和事件不再等待长 OCR。空记录不能证明本机已切换；心跳过期只提示核实，不自动重跑。正在通知或发布时重评审可能返回冲突，应等待发送结束后再操作。详见[第四阶段实施记录](review-performance-phase4.md)。

### 问题检索与详情

问题列表的“提交人”取该问题最近一次出现所关联评审任务中保存的 Git 提交作者；跨提交复用或人工合并问题后，按最新出现记录显示。详情的每条出现记录分别展示对应提交人。该字段供联系核查，不代表问题责任人、MR 创建者或代码行作者；默认分支 Push 范围评审对应结束提交的作者。旧任务缺少作者时显示“未记录”，不会用更早提交的作者代替，也不会在打开列表时调用 Git 或 GitLab 补查。

问题列表展示描述摘要，支持按描述、文件路径或精确问题编号搜索；百分号、下划线和引号按普通文本处理。桌面点击摘要或查看按钮打开侧栏，手机以全屏详情呈现。当前问题和筛选保留在 URL，关闭详情不清除筛选。合并重复项时先搜索并选择同项目待处理问题，再确认源和目标编号；不能跨项目合并。

出现记录和处理记录默认各显示最近 10 条，可逐次追加查看更早记录，不会删除历史。重复问题搜索在停止输入约 300 毫秒后提交，修改关键词立即清空原合并目标，防止用旧搜索结果误选。

在任务详情的 **评审发现** 卡片中，三个按钮只收集这条 review 是否有帮助：**有帮助** 表示认可、**误报** 表示判断不成立、**忽略** 表示本次不采纳但不判断对错。三者互斥，选中后再次点击可撤销；无按钮选中表示未评价。反馈只更新发现评价，不自动修改跟进问题，也不改变代码或重发通知。

任务列表的“发现 / 价值反馈”只展示当前发现的待反馈、反馈中及反馈完成，不再额外显示跟进问题的待处理数量。详情中选择有帮助、误报或忽略任意一项，即表示这条发现已处理，撤销后回到待处理；卡片的“处理状态”筛选按同一反馈口径工作，旧 `finding_state=open` 直达地址也显示未反馈发现。历史“已修复”反馈仍归未评价、待反馈。跟进问题链接只保留编号，代码修复及跨任务跟进状态在跟进问题页面管理；反馈不会写入或覆盖这些记录。反馈完成不等同首页的有效评价占比，也不表示代码已修复。缺失或矛盾数据标为待核实，不补零；部分覆盖、排除或豁免时提示“仅当前已发现范围”，不代表整次评审完成或代码没有问题。完整无发现仍展示“本次未发现问题”，不绘制人工完成标签。

卡片不再提供“已修复”反馈按钮。旧记录仍保存在历史中，但不计入价值评价统计；在发现详情中按未评价显示，并可重新选择有帮助、误报或忽略。新反馈接口也不接受提交“已修复”。卡片上的关联问题链接只显示编号，并进入 **历史问题与修复记录** 查看跨任务出现记录、处理历史及状态操作。

跟进问题页面独立管理 **待处理 / 已修复 / 已忽略 / 误报** 四种当前处置；修改前需确认，可填写处理说明，保存后共享同一问题的任务卡片同步展示状态。这里的“已修复”是人工处理声明，不代表系统验证代码；“已忽略”是不处理，不等于误报。问题处置保留审计，不会反向改写价值反馈。首页统计将发现反馈按发现条数统计、问题存量按唯一编号统计，两个维度分别筛选与下钻。

发现正文按明确标签分区，兼容冒号、【标签】和 [标签] 等历史格式；无标签正文统一显示为“问题描述”，正文中明确的行动建议集中到“修复建议”，不明确的文字保留原处。所有描述区（问题描述、触发条件、代码依据、实际后果、修复建议、补充）中的有序分项均逐条换行、续行对齐，包括前言后编号、场景①/②及中英文编号，不要求从一开始或连续递增，保留原编号。代码、版本号和单纯的场景引用不机械拆分。任务卡片、跟进问题详情侧栏、历史报告的新增/不再出现对比共用同一描述组件；历史记录在读取展示时同样整理，不批量写回数据库原文、指纹、反馈或问题状态，也不修改已下载的报告文件。

### 批量处理跟进问题

在 **历史问题与修复记录** 列表逐条勾选，或点击 **全选当前页**，然后选择 **批量标记已修复**、**批量标记已忽略** 或 **批量恢复待处理**。可以填写统一的处理说明，提交前会再次确认问题数量。仅修改当前页显式勾选的问题，不扩展到其他页；切换筛选或分页会清空勾选，已合并的问题不可选。列表每页默认 25 条，可切换为 50 或 100 条，接口每次最多接受 100 条。

批量修改与每条处理记录在同一 SQLite 事务内提交；任一问题不存在、已合并或状态出现冲突时，整批不更新。错误时保留当前勾选和说明，点击刷新后根据最新状态重新选择；重复提交相同目标状态不会重复生成处理记录。成功后会刷新关联任务卡片和评审成效统计。

批量“已忽略”表示关闭跟进，不会把所有关联发现的反馈改成“忽略”或“误报”，也不修改已发布的 GitLab 评论或飞书通知。问题处理与发现反馈仍分别保留各自的历史事实。

### 合并前版本与接入诊断

“合并前审查”默认每个 MR 只显示最新接收版本，可筛选项目、MR 和状态，勾选“包含历史版本”后分页查看旧记录。先确定最新版本再筛选状态，不会用旧成功版本替代当前失败版本。详情链接可刷新和分享。失败、部分完成、跳过、未结束、失效或缺少完整覆盖证明时，都不显示“未发现问题”；结果和上下文记录损坏时给出未知提示，不使整页崩溃。

进入“项目配置 → 编辑 → 接入诊断”，可核对已保存的事件开关、Git/GitLab 测试状态、最近 Webhook 验证、模型来源、飞书关联及最近接收事件对应的任务和错误。当前配置缺少有效测试时，不把旧测试成功显示为接入完成。打开诊断只读取本地事实，不自动调用 GitLab、模型或飞书；Git/GitLab 测试需主动点击，未生成任务时先核对事件过滤原因与 Worker 状态。

## 7. 备份恢复与保留

每日备份将 `app.db` 与包含主密钥的 `private.json` 成对保存，默认保留 90 天且至少保留最近两份。可以在备份命令中通过 `--retain-days 180` 调整期限。恢复命令仅写入一个**不存在的新目录**，不会覆盖正在运行的服务：

```bash
.venv/bin/python -m ocr_manager.backup --restore-from /path/to/backups/app-YYYYMMDD-HHMMSS.db --restore-to /path/to/restore-data
```

先核对新目录中的数据库与 `private.json`，停止 API、Worker 和 monitor 后，再将服务配置指向恢复目录。恢复目录与私有配置文件须仅当前用户可读。已删除项目的工件目录由 monitor 在工件锁释放后自动清理；“运维与审计 → 运行监控”保留手动维护能力，并要求确认后执行清理。

### 评审任务中的提交人

评审任务列表的“提交人”列和详情顶部展示该任务固定提交的 Git 作者姓名，手机列表卡片也直接显示。该姓名不是 MR 合并操作者，也不等于问题处理人；发现是否已处理以当前三类反馈为准，代码修复记录在历史问题入口独立保留。默认分支 Push 范围任务显示末端提交的作者，不代表范围内所有提交人。尚未读取 Git 或旧任务没有作者记录时显示“未记录”，不根据其他身份推断。

### 自动归档与会话台账同步

“问题与改进”顶部的“自动归档与台账同步”可展开查看来源是否配置、最近成功/检查时间、同步冲突及候选数量。管理员可启停自动归档并设置连续无更新天数（默认 30 天）；保存策略不等于归档已完成，由独立 monitor 下轮执行。只有处理、验证、部署和遗留均闭环的内容才自动收纳，恢复后重新计时。列表、主题与统计每 30 秒更新；已提交的历史仍可查看。当前会话先追加项目台账，再按 PI 来源编号同步到页面；不抓取其他聊天。来源与人工编辑冲突时须先核对，不能强行覆盖。服务器配置与故障处理见[台账维护说明](improvements-phase5.md)。


## 部分评审的人工补审灰度

补审默认可用，不需要功能开关或项目白名单；旧 `OCR_APP_REVIEW_RECOVERY_ENABLED` 和 `OCR_APP_REVIEW_RECOVERY_REPOSITORY_IDS` 已移除且不再影响行为。管理员打开部分审核任务即可确认剩余范围和预算，不会自动创建批次。`OCR_APP_REVIEW_RECOVERY_MAX_BATCHES`、`OCR_APP_REVIEW_RECOVERY_MAX_TOTAL_TOKENS` 继续约束每任务最多 1～10 批，默认 3，累计批准 Token 默认 100000。失败/取消仍占批准额度，幂等重放不重复占用；未知实际费用不当零。确认框冻结失败范围、模型/规则版本和本批预算，Worker 再核验原 SHA 与实际快照，不使用新分支头替代。

配置明细、45 版迁移、有效结论与初审事实的区别、独立通知、受控试点及回退操作见[部分评审完整恢复与上线准备](review-partial-rollout.md)。本文说明配置不表示已修改本机私有配置或已开启补审。

schema 48 起支持管理员显式调整单任务累计额度并追加原因审计；任务授权优先于环境默认值，但不覆盖原快照单批上限或重置历史。确认框不再预填 1000 Token，必须人工决定，超时沿用源快照；保存额度不排队。历史数字导入、预算前瞻解释及调整步骤见[补审预算说明](recovery-budget.md)。

历史任务的请求证据可通过[受控历史诊断导入](review-historical-diagnostic-import.md)批量补齐；导入只新增独立证据，不修改原结果或触发模型。

### 可配置模型任务并发（第四阶段后的扩展）

新版增加“运行监控 → 模型任务并发设置”，管理员可保存 1～10，默认 1。调高可立即使已排队任务并行并产生费用，调低等待在途任务结束，不强杀；同仓库串行、不同仓库并行，普通评审/预审/失败补审/模型诊断共用总上限。该设置不等于单任务内部 `OCR_APP_OCR_CONCURRENCY`，也不增加补审预算。页面分别显示已保存上限、Worker 已应用上限和执行中数量；停止或心跳过期的已应用值显示未知。首次使用需要同版迁移及整体重启，之后调整容量无需重启，详见[任务并发说明](worker-task-concurrency.md)。源码支持不代表当前实例已发布。


## 统一列表使用方式（2026-11-08 源码更新，需配套发布）

- 业务列表上方按真实业务状态切换；状态旁数量来自保留其他筛选后的全量范围，不是当前页条数。评审发现默认只看尚未反馈的待处理发现，旧问题列表在历史入口保留；合并前审查默认每个 MR 最新版本，历史开关在“更多筛选”。
- 常用项目 / 搜索放在首行，时间、归档等低频条件按需展开；已生效条件保持可见，可逐项清除或重置。筛选和分页进入 URL，平台记录与主题详情返回时保留各自范围。输入搜索需提交，未提交的编辑草稿仍不受列表刷新覆盖。
- 任务继续显示耗时 / 尝试、创建时间和问题处理；完成评审不代表问题已修复。平台台账的代码修改、本地验证、部署生效分别显示，不以主题完成代替问题或部署状态。
- 项目列表点击“接入信息”后才能查看 / 复制该项目 Webhook Token，默认不读取明文；编辑器的轮换和连接测试仍需显式操作。配置历史按完整历史分页，点击“查看差异”阅读脱敏变更；删除版本或已删除对象不可恢复，对象查询失败则保持待确认。
- 手机以带字段标签的逐行布局显示，不隐藏关键状态和时间；长原因 / 路径可展开，点击或聚焦短时间可看完整时间及时区。问题批量栏仅在选中后出现，全选只作用于当前页。
- 补扫申请和告警投递明确限定最近 100 条，不能当全部历史总量。聊天收件箱在“维护与聊天收件箱（低频工具）”中，展开后读取，关闭停止轮询；分类只筛选列表，不改变全范围待核实数，不新增会话绑定或扩大历史授权。
