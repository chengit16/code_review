# 问题与改进第四阶段：归档与恢复

实施日期：2026-11-06。为问题记录与优化主题增加可恢复的归档能力。本阶段仅完成源码和隔离验证，不访问或部署当前业务实例，不自动整理、删除或导入业务数据。

## 1. 使用方式与规则

- “问题记录”“优化历程”列表默认显示未归档内容；“归档范围”可选择未归档、已归档、全部（含归档），与文字、分类、进展、类型和分页共同生效。切换条件回到第一页。
- 问题 URL 使用 `archive=active|archived|all`，主题使用 `theme_archive=active|archived|all`；不指定时默认 `active`。筛选可刷新和分享，两个视图互不借用归档条件。
- 管理员在详情“归档管理”中操作，填写原因并确认。归档后当前内容只读，必须先恢复才能编辑；归档和恢复均追加版本，不允许无原因或静默覆盖。
- 任何处理状态都可主动归档，例如暂缓问题或暂停的主题；归档仅表示收纳，不是解决或验收，也不改变代码修改、本地验证、部署生效三个维度。
- 归档不删除当前内容、阶段、历史或显式关联，主题操作不级联问题。归档对象仍可通过原详情链接打开；问题反向主题列表、主题关联问题选择器包含已归档对象并显示标识。
- 当前归档元数据包括时间、操作者和原因。恢复后当前元数据清空，但历史中的归档事实与恢复原因永久保留。历史按“建立、追加进展、归档、恢复”明确区分操作。
- 未保存原因只留在内存；失败或版本冲突保留草稿，离开或关闭有提醒，提交中禁止重复操作。冲突后先取消、刷新并核对，不提供强制覆盖。

本阶段交付管理员主动归档，不添加按时间自动归档、后台清理、批量归档或永久删除。旧规划中的“自动归档”不解释为已经上线的定时任务；自动策略必须另行定义候选条件、预览与确认边界，不能仅凭时间推断问题已解决。会话处理记录仍按执行约定持续追加 Markdown，不等于自动同步 SQLite。

## 2. 接口、版本和事务

| 方法与路径 | 契约 |
| --- | --- |
| `GET /api/improvements?archive=...` | 默认未归档，支持归档和全部范围；原筛选继续生效。 |
| `GET /api/improvement-themes?archive=...` | 同样支持三种范围；反向关联查询显式使用 `all`。 |
| `POST /api/improvements/{record_id}/archive` | 问题记录归档或恢复。 |
| `POST /api/improvement-themes/{theme_id}/archive` | 主题归档或恢复，不操作关联问题。 |

写请求仅接受 `archived`（严格布尔值）、`expected_version`（正整数）和 `reason`（去空白后 1～2000 字符）。身份来自服务端管理员会话，不能通过请求指定操作者或归档时间。不存在返回 404；过期版本、重复目标状态和归档期间编辑返回 409；请求校验失败返回 422。所有列表、详情、历史、复盘及归档接口仍限管理员，只读账号不能直接访问。

归档与内容编辑共用同一版本及 `BEGIN IMMEDIATE` 短事务，当前元数据、版本递增和完整历史同事务提交；返回事实也在同一事务读取。原历史缺失、历史写入失败均整体回滚。不以同一请求重复追加版本；响应丢失后应先核对详情和历史，旧版本重试被拒绝。创建键重放仍只返回当前状态，不把归档对象重新激活。

第 41 版独立迁移为台账、主题及两类历史追加 `archived_at`、`archived_by`、`archive_reason`，历史另加 `action`；既有版本 1 标为建立，其余标为追加进展。旧记录均保持未归档，旧快照正文和关联不变。没有修改第 39/40 版迁移。

## 3. 复盘口径

- 累计、分类分布、阶段、关联覆盖和待办仍包含归档内容；新增已归档记录数、主题数，范围同当前分类。不能通过归档让未解决数量减少。
- 待办中的归档对象明确显示“已归档”，原链接仍可定位；分布跳转使用全部归档范围，避免统计有数量、列表看不到。
- 活动继续按版本计数，归档、恢复计入历史追加次数，不等于处理完成次数。页面明确说明此口径；创建重放、重复操作、冲突和失败不计入。
- 归档或恢复会更新实体 `updated_at`，因而改变“最久未更新”排序；该排序代表最近记录操作时间，不表示解决时间或问题消失。
