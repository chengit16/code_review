# 运行监控页重设计规划

> 2026-11-07；关联 PI-20261107-010。本文是待确认规划，不代表页面已改造、已验证或已部署。

用户已在后续请求中确认按照本方案设计运行监控页；本方案现作为设计基线，业务页面仍待实施。其他页面的问题清单与分批安排见 [全站体验重设计规划](whole-site-ux-redesign-plan.md)。

## 目标与边界

沿用现有灰白蓝主题、字体和导航。用户后续已授权采用 Ant Design，新增/重设计通用组件遵守[统一规则](governance/frontend-code-standards.md#8-ant-design-采用规则)，不机械重写全站存量组件。保留 `/operations` 管理员入口，将“所有功能纵向堆叠”改为“实时运行优先、按任务分区”。首版不改调度规则、评审策略、模型内部并发、重试预算或数据库结构。

与首页“运行概览”区分：运行监控服务于排障和操作，不再重复一份历史业务大屏。进入页面应能快速找到当前任务状态、并发设置和异常处置入口。

## 已核对的问题

1. `OperationsPage` 先渲染完整 `ReviewPerformance`，再渲染执行槽和并发设置。性能分组越多，最常用的运行状态和设置越难找到。
2. “排队 / 运行”只展示两者合计，无法判断是在等待还是正在执行；“重试 / 通知失败”又将累计次数和失败记录数混为主数字。
3. `monitoring.py` 中任务、重试及投递计数主要为全历史当前状态聚合，而平均耗时和分组为近七天；截图上不容易识别这些口径差异。
4. 失败或部分覆盖记录会触发通用异常文字，不等于系统当前宕机。历史评审问题与磁盘、备份等运维风险需要分组显示，不能直接映射为全局服务故障。
5. 每个性能分组展开一整组说明与指标，纵向占用高、横向难比较。未知值、样本不足和已知 Token 下限需要更清晰的解释。
6. 执行槽、并发配置分开显示且有重复长说明；已保存上限与已应用上限的重要区别不够集中。
7. 存储、清理、地址、告警配置、对账及审计都直接挂在同页，多个查询同时运行；页面顶部刷新也并不刷新全部子区块。

## 推荐信息架构

保留一个导航入口，使用四个可直达的标签页，标签与可分享筛选进入 URL。

| 标签 | 内容 | 默认行为 |
| --- | --- | --- |
| 运行与并发 | 运行指标、关注事项、并发控制、模型/事件/投递执行槽 | 默认进入；常用操作在前 |
| 性能分析 | 近七天固定口径、项目/状态/原始规模筛选、可比较的分组表 | 不混入实时状态卡；首版不伪造日趋势 |
| 告警与通知 | 告警开关与阈值、目标、告警与恢复通知历史及单条重发 | 已有设置和历史明确分区；不混成评审重试 |
| 维护与审计 | 存储/备份、旧工件与孤儿目录清理、服务地址、数据对账、操作审计 | 清理与诊断分区，危险动作不占首页 |

建议 URL 示例：`/operations?tab=runtime`、`?tab=performance`、`?tab=alerts`、`?tab=maintenance`。未识别标签回退默认值；浏览器刷新、前进与后退保留定位。维护页用段落锚点或折叠区定位对账和审计，不新增一排同级导航。

## 默认页布局

1. 紧凑标题栏：标题、当前标签最近成功获取时间、更新状态和“刷新当前视图”。不把浏览器本地接收时间称为服务端业务更新时间，不凭执行槽心跳认定 API/monitor 全部健康。
2. 四项可扫描指标：初审排队、初审运行、模型执行中/已应用上限、待关注评审。每项注明数据范围；补审单独标注，不把模型槽使用数当初审运行数。
3. 待关注列表：历史失败/部分覆盖与基础设施风险分组；显示具体数量和对应入口。不要仅因存在历史失败就把整个页面显示为红色故障。
4. 主区左侧是执行槽，右侧是并发控制；桌面约 2:1，窄屏将并发控制放到槽列表前面。并发设置不再被性能报告挤到下方。
5. 执行槽按模型、事件/Git、通知分区，最多十个模型槽用紧凑列表；显示槽号、状态、类型、任务/仓库和心跳，已有状态关联可用详情入口，不能猜测不同类型的跳转地址。
6. 并发面板同时显示已保存上限、已应用上限、模型执行中和排空状态。使用整数输入框与保存按钮，保留 1～10 校验、冻结版本、409 保留草稿及不自动重放。关键费用提示常显，详细原理折叠。

降低并发时显示真实情况，例如“已应用上限 2，仍有 4 个在途任务，排空中”；不能将分母上限改成运行数掩盖超限排空。心跳过期显示“状态待核实”，不自动认定任务结束或授权抢占。

## 性能分析布局与口径

- 使用紧凑表格比较项目、状态、原始文件规模、任务数、成功执行 P50/P95、首次排队 P50/P95、超时、重试及用量；次要列放行展开区，不将所有列挤进首屏。
- 项目、状态和规模筛选先对现有七天分组做本地过滤；近七天范围固定。任意日期、按天趋势、跨项目重算总体分位数均不在现有聚合契约内，后续有服务端支持再开放。
- 不对分组 P50/P95 求平均得到总体 P50/P95；不把原始 Git 文件数改称 OCR 选中文件数。
- 零样本显示“无有效样本”，时间记录缺失显示“历史记录不完整”或“未知”；样本数始终可见。小样本不将 P95 解释为稳定服务等级。
- 用量显示“已知 Token 下限”及未知用量任务数，不能把 0 当免费或完整用量；不跨币种合并费用。
- 统计口径放入可展开的“统计说明”，关键限制保留短标签，不让整段技术说明占据默认阅读区。

## 数据与交互边界

- 首版优先使用现有 `operations`、调度配置、告警、对账及审计接口，不新增数据库迁移。
- 当前 `operations.jobs` 是有效结论统计，实时初审执行应读取已返回的 `execution_jobs`，补齐前端类型和专项断言；不直接把有效结论数当原始执行状态数。
- 当前接口不覆盖所有预审队列统计，默认指标应明确写“初审”；只有补齐服务端统一口径后才能展示“所有任务总排队”等文案。
- 服务端 `alerts` 当前只有文本。第一版用已知数值及原文保守展示，不能解析任意告警文字猜动作。确需按码定位或区分当前/历史风险时，另加兼容的结构化只读字段并同步契约测试。
- 备份目前验证最近数据库副本的 `quick_check` 和同名私有配置存在性。文案为“副本检查通过”，不宣称完整恢复演练、全部工件或凭据恢复通过；备份时间和是否超过 48 小时分别展示。
- 按活跃标签启用昂贵查询与轮询；视图切换不清空未保存的并发/告警表单。保留草稿或提示放弃后再离开，先验证实际组件卸载行为。
- 当前标签刷新更新该视图相关查询，不覆盖草稿；并发配置轮询与执行状态可能不同步，用版本及待应用提示呈现，不假装同一事务快照。
- 局部加载、接口失败、旧数据过期与真正空数据分开呈现。不能请求失败显示 0，也不能缺失心跳显示正常。
- 不增加一键重试全部失败、自动补审、自动调并发或前端删除锁等高风险操作。清理仍需预览、二次确认与服务端重新核验。

## 分阶段实施

### 第一阶段：重排与可发现性

拆出运行、性能、告警、维护四个视图及 URL 标签；执行槽与并发提升到默认页。拆开合并数字、标注时间口径、缩短说明；补齐 `execution_jobs` 类型。保留现有操作权限和全部功能入口，不变更数据库或调度逻辑。

验收：默认页无需跨越历史分组即可找到并发设置；刷新和回退保留标签；未知和错误不显示为正常；改造前所有工具仍可访问。

### 第二阶段：表格与状态交互

性能分组表格、筛选及行详情；槽列表和并发待应用/排空/冲突状态；表单草稿保护、按需查询、局部刷新。需要精确告警定位时再评估最小结构化接口，不在界面用字符串猜测业务语义。

验收：保存、409、调低排空和十槽显示均清楚；失败跳转保持正确范围；分页或按需展示不截断样本；未激活昂贵区域不持续后台轮询。

### 第三阶段：回归与本机生效

验证桌面 1440/1024px、平板 768px、窄屏 375/320px，表格窄屏保留核心列并展开次要信息。覆盖键盘、空数据、加载/失败、无样本/历史缺失、旧 API 缺字段、十槽、草稿切页、取消离开、清理二次确认、权限及刷新一致性。

拟运行命令：

```bash
npm --prefix frontend run lint
npm --prefix frontend test -- --reporter=dot
cd frontend && npx tsc -b
npx vite build --outDir /tmp/ocr-operations-redesign-dist --emptyOutDir
OCR_BROWSER_FRONTEND_DIST=/tmp/ocr-operations-redesign-dist npx playwright test
```

若修改后端只读契约，再运行相应 pytest、OpenAPI、Ruff 与 mypy。以上是未来验收命令，本规划不声称已经运行。先构建隔离产物，业务实例是否发布单独确认；设计完成、测试通过和本机生效分别记录。

## 本轮交付与待确认

推荐上述四标签工作台，不推荐只压缩间距或更换卡片颜色。首版保持现有灰白蓝视觉，不加入当前没有可靠数据来源的 CPU/内存/模型额度趋势图；说明示意数据与真实运行事实的区别。

本轮仅规划，不改造页面、不调整并发、不部署。确认后先实施第一阶段，再在同一规划下补齐交互和回归，避免把整个运行监控与基础组件库迁移绑在一起。
