# 部分评审根因治理与补审方案

> 日期：2026-11-06。状态：基于本地业务 SQLite 与既有 OCR 工件形成的方案，供审阅；本文件不表示已改代码、改参数或部署。

## 1. 目标与结论

目标不是把“部分完成”改成可重跑，而是先把失败定位到可采取行动的层级，再减少失败率，同时保证已完成结果不重复计费或被不兼容结果覆盖。

本次读取到的三条当前 `partial` 任务（#321、#343、#381）呈现重复模式：OCR 1.12.9、四路内部并发、覆盖项标记 `timeout`，且失败项恰好组成整个审核分组。#381 还有六次 HTTP 504。这是模型/网关等待与分组截止时间需要分层诊断的信号，但不足以判断具体是哪一层网关、模型队列还是请求复杂度；可从预览读取 diff 行数，仍缺逐请求实际输入 token、成功请求时延和分组时间线，不能把“文件太大”定为根因。

建议并行推进两条主线：

1. **源头治理先行**：完善分组和请求级诊断；在隔离、有限样本上对照并发与模型/端点，取得可比较的覆盖率、耗时、费用数据后才调整项目参数。
2. **补审作为恢复保障**：优先验证 OCR 原生 session resume；若其不能满足提交模式、会话工件寿命和覆盖校验，则实现平台级按失败文件续审。不得把同一提交全量重评审冒充补审。

### 2.3 根因判断与未知项

**已确认：**

- 不完整是 OCR 真实返回的文件覆盖失败，不是平台把完整结果误判成 partial。
- OCR 的单文件/分组处理超过自己的时限；#381 同时出现计划阶段 HTTP 504。
- 内部并发 4、总 token 预算未设置上限（快照值为 0），失败项均为 timeout，无预算失败证据，不能归因于预算耗尽。费用治理仍需补齐有限预算；缓存读取 token 应单列，不把累计 token 简单等同于按全价计费。
- 当前结果 JSON 有 session ID，三个独立尝试的隔离 HOME 内也各有会话文件；平台每次尝试创建独立 HOME，没有现成证据证明后续任务会恢复旧 session。
- 当前工作区安装的 OCR CLI `review --help` 暴露 `--resume`，示例写的是 range review；平台当前 MR 正式评审命令使用 `--commit`。因此 CLI 有 resume 入口，但其能否支持这里的 commit 模式、只重试失败覆盖并保持 manifest 语义尚未验证。

**仍待确认：**

- `failure_phase=context` 的具体含义在当前 OCR 报告中是阶段标签，不能据此断言网络或上下文过大。
- #381 的 504 是被评审范围的计划请求持续超时，原因可能在模型服务、代理/网关期限或请求复杂度；无上游 trace/服务日志，不能进一步定因。
- diff 行数已比较；实际上下文 token、分组内每一轮读取量、阶段耗时和关键路径仍缺失，不能依据 diff 行数单独定因。
- 同一 6 文件组在 #321/#343 重复失败，而同项目也存在 16～31 文件全部完成的任务；这支持“特定分组/上下文或依赖读取问题”需优先验证，但样本不足以排除模型服务偶发性。
- 本机 CLI 帮助确认 `--timeout` 是并发子任务的分钟级上限，默认 15 分钟；平台 `_review_arguments` 没有传该参数，四个样本隔离配置也未发现 timeout 字段。平台 3,600 秒整体预算与 OCR 子任务时限不是一回事。应在隔离验证实际计时起点、重试和 plan/main 是否共享截止时间后，再决定是否显式透传这一参数。
- #381 六次 504 的响应头计时均约 60 秒，支持“存在稳定的分钟级响应期限”假设；需要网关与上游 trace 确认具体层级。错误标签为 context 的 6 秒、54 秒等残余等待，不能当作统一请求上限，也不能只凭计时确认其必为分组取消导致。

## 3. 推荐方案

### 阶段 A：补足可定位的诊断证据

为每个逻辑模型请求/分组保存受控、安全的结构化遥测，而不是保存 prompt 或原始响应：OCR 阶段（plan/main）、请求序号、关联文件 ID、尝试数、错误类别和 HTTP 状态、请求等待时长、重试间隔、文件输入规模档位、运行队列等待、OCR 与模型版本。对路径及 provider 信息按现有工件权限策略管理，普通 API 只返回安全摘要。

补充任务执行结束摘要：哪些失败文件属于同一逻辑请求，失败发生在 plan 还是 main 阶段，失败前/后完成了多少组，端到端各阶段耗时，token/费用完整度。现有 retry report 已能提供不少请求级字段，应先利用而非再造一套重复数据；缺失的逐文件耗时和输入规模通过新 OCR 兼容能力或探针补充。

新增原因类别建议为“上游 HTTP 504”“OCR 分组截止”“请求 context 超时（具体触发源未知）”“工具匹配超限”“版本中缺少依赖文件”“整体预算耗尽”。同一次任务允许多个原因同时存在；主原因用于排序，明细保留证据来源与已确认/待确认，不能仅因 `partial` 状态或终态校验阶段就显示“结果校验失败”。列表直接展示如“完成 40/45；1 组超时；存在 504”，详细信息从 SQLite 安全投影读取，避免列表逐行解析大工件。

### 阶段 B：做小样本源头对照，禁止盲调生产

选一组固定 SHA、规则快照和失败文件代表样本，在隔离任务中进行受控对照：

1. 先保留当前基线，再对同模型/端点的并发 4 与并发 2 做交错顺序对照；必要时加并发 1。首轮至少 3 次配对运行仅作为方向验证，记录覆盖率、延迟明细、token/费用；P95 需要更多样本，不能用三次运行宣称已改善线上 P95。
2. 如仍失败，再用另一个已验证可用的模型/端点对照，保持输入与 effort 一致；不把切换模型后的结果与原始结果合并成同一策略结论。
3. 对单文件失败查看 diff/token 档位和 OCR stage；只有证据显示输入复杂度相关，才考虑按复杂度分组或设置经验证的单文件时限。不得通过截断 diff、自动豁免或仅加大整体任务时限掩盖失败。
4. 另设工具层对照：对 PCRE2 匹配上限、仓库中不存在的 `node_modules` 读取和外部依赖路径分别验证。可考虑给搜索设置时间/输出上限并提供受限的字面检索降级、对同一不存在路径返回明确且可复用的失败信息；能否由平台配置或必须修改 OCR，需兼容性确认。工具失败可能被模型正确绕过，不单凭一次失败将整组标坏；也不能把工具失败都包装成模型超时。不得在被审查仓库安装依赖或执行构建脚本补齐缺失内容。
5. 对每个实验记录单次预算和停止条件；不自动对历史任务发起模型调用，不在没有用户确认成本的业务实例跑探针。

重试层面先核验 OCR 对 plan/main 的实际重试能力：#381 的单个 plan 逻辑请求已执行 6 次、约 6 分钟，仅延迟重试间隔不能解决每次约 60 秒的稳定期限。若 OCR 支持配置，采用共享剩余预算的有限重试、指数退避和抖动；对连续稳定失败考虑端点级冷却且保留公平调度，不能直接叠加平台整批重试。若本版不支持控制，要明确需要上游修复/适配或固定新版验证，不凭空添加 CLI 参数。

阶段 B 的决策门槛建议：完整覆盖率与耗时/费用共同评估，并保留初审发现的人工抽检，不能通过降低分析质量或漏审换取“完成”。候选配置只在同输入对照未明显增加故障、成本可接受后进入项目级灰度。旧任务不得静默沿用新参数；模型、规则或版本更换必须形成新快照，不能把新旧结果拼成同一标准。尚未验证执行参数变更的兼容性时，连并发/时限调整也不能绕过 OCR 的 runtime hash 校验。

### 阶段 C：实现可审计的补审

首选路线是验证 OCR `--resume` 对固定 commit/range、相同 OCR 版本、provider/model、规则与配置快照的兼容性及覆盖语义。验收需确认续审只重做失败 coverage，已完成 coverage 被复用，不改变输入 SHA，并返回完整、互斥的 manifest 覆盖集合。session ID 本身不构成恢复证明。原生恢复可能返回原始全量 selected，其中已完成项进入 reused；这与平台按失败子集执行的 selected 口径不同，不能用同一个子集校验规则误判。

用临时 Git 仓库、隔离 HOME 和本机合成模型 HTTP 端点，正式执行“先成功一组、再注入故障、恢复后只处理失败组”的 CLI 探针。记录端点请求计数、处理文件身份和最终 manifest，不连接真实模型、不使用业务 session。仅 `--preview` 或 `--help` 不能证明断点复用成立。覆盖 commit/range、取消、会话不完整、跨 checkout 目录、配置冲突和特殊路径；必须确认 session 的路径命名与模型/规则签名语义。

若原生 resume 不适合 commit 模式或不能稳定复用已完成结果，则平台实现“父任务 + 补审批次”：

- 父任务保留原始 SHA/base SHA、规则与模型快照、首次结果及原始通知；补审创建子尝试/批次，只包含原结果 `coverage.failed` 中经校验的文件 ID。
- 子任务执行前验证原始 base/head 和项目有效性（不能改用当前分支 HEAD），失败集合来自可信父 manifest。失败子集模式下，preview/正式 manifest 的 selected 必须严格等于获准集合；原生 resume 模式下，校验全量输入 selected 不变、复用项来自可信已完成集合、新增执行不越过待恢复集合。集合漂移即停。#337 式提交不可达/不再属于目标分支时明确阻断，不自动放宽安全校验。
- 子集筛选与审核规则分别冻结：原规则不改写，批次另存范围选择覆盖层及其摘要。若实现必须合成额外排除规则，需复用已验证的路径转义和优先级探针，证明对待审核文件的语义规则未变；保留 OCR 实际生成的新摘要，不能伪造父 hash 或绕过原生 resume 的配置冲突。无法证明兼容时不允许聚合。
- 对同一固定配置可聚合原完成、复用、豁免和补审完成集合；发现以稳定身份去重，但保留来源尝试。若模型/规则/版本变化，不聚合为同一审核结论，改创建全新任务快照。
- 每次补审幂等，记录操作者、父任务、文件集合 hash、原因、尝试、费用和投递关系；限制最大批次数/总预算，停止后仍明确显示 partial。
- 通知是独立业务：续审后的补充消息引用原任务及本次补审，不撤销已发送的部分结果；通知失败只重发通知。

UI 仅在有可信失败文件清单且没有正在运行的批次时显示“继续审核剩余部分”。确认框展示文件数、估计费用（未知就明确显示未知）、模型/规则快照及“仅失败文件/整批重审”差异。存在配置漂移或缺失工件时禁用续审并解释原因。

### 持久化、队列与接口边界

建议新增独立恢复请求/批次表，保留 `parent_job_id`、`source_attempt_id`、源结果摘要、固定输入/配置摘要、待处理 item ID 集合、幂等键、状态、执行身份、尝试及聚合版本。实际表名和迁移版本在实施时按届时仓库基线确定，不预占其他开发的迁移编号。

API 建议提供资格/历史查询及 `POST /api/jobs/{job_id}/continuations` 一类独立入口，沿用管理员权限与审计；HTTP 只校验落库，Git、session 校验和 OCR 全部由独立 Worker 执行。资格查询不承诺提交当前仍可用，Worker 执行前必须复核。重复提交在短事务内复用同一活动请求，不能只靠前端禁用按钮去重。

补审领取复用现有执行槽、进程组栅栏、取消、仓库锁和工件锁，不再启动第二个 Worker；新 webhook 任务与恢复任务公平排队。补审期间保留原 partial 结果可读，单独显示“补审排队/执行中”，不调用现有会清空当前结果的全量 `retry_job` 路径。恢复批次失败不抹除父结论。

原始 OCR JSON 及 session 不改写。聚合结果另存版本与来源，覆盖按原 `item_id + fingerprint` 关联；failed 项已有的临时发现也要保留来源并处理重复，不只合并完成文件的发现。原生 resume 可能返回全量用量，必须验证增量/累计语义后计费，防止把初审 token 再加一次；不能承诺绝对零重复费用。

恢复引用的 session、规则与结果工件必须有保留引用和过期上限，清理器不得删除运行中引用，项目删除/取消必须终止执行并保留必要审计。隔离 HOME 不可全局共享，恢复也不能复制无关凭据或旧私有配置。旧记录只做资格评估，首次不自动补审全部历史任务。

首版只开放合并后任务的人工补审；共享 OCR 适配仍回归合并前固定 SHA、取消及版本失效，合并前恢复等其历史/版本模型具备后单列实施，不把本轮空样本视为已验收。

## 4. 实施顺序与交付门槛

| 阶段 | 交付 | 放行条件 |

## 5. 自动化验收要求

- 子批次只引用父 manifest 的失败 item ID；攻击性/损坏/重复/过期 ID、commit SHA 变化、rule/model/OCR 快照变化均拒绝或转新任务。
- 子集模式的 preview/manifest 与批准集合不相等时不调用或不合并；原生 resume 则验证原始 selected 与复用/新执行边界。completed/reused/failed/waived 四组互斥，其并集必须等于 selected。
- 两次相同请求只创建一个活动补审批次；并发点击、Worker 重启、取消、部分失败与重复 webhook 不丢历史、不重复发起模型任务。
- 补审结果只补入新增可信发现，稳定去重不丢来源；仍有 failed coverage 时父视图保持 partial。
- 已发送初审消息不删除；补充通知失败只重试投递，不重新运行 OCR。
- 模型费用按尝试分别保存；没有可信 usage 时显示未知，不当作零费用。
- 真实模型调用不属于隔离自动化测试；外部链路成本和质量需单独试点验收。

### 第一步：先让每次失败可解释

**改动落点：**新增独立诊断解析模块及契约；由 `review_results.py` 在保存结果前调用，接入 `review_observability.py`、`tasks.py` 和前端任务详情。不要把当前只对 failed 生效的 `result_failure` 直接扩大成 partial 的自动重试入口。

**实现内容：**

1. 校验 retry report 版本，按白名单提取逻辑请求 ID、阶段、请求序号、HTTP 状态、计时及退避；按 manifest 失败项和 groups 建立关联，限制报告大小、条数与字段长度。不能直接按逗号拆 `file_path`，真实路径可含逗号；有歧义时关联标记未知，不能猜测。
2. 保存覆盖失败数、可信失败组、错误列表、证据层级和缺失字段说明。plan/main/request/context 的含义保留原字段来源，不把推测的链路根因写成事实。重复错误聚合显示，但计数不丢失。
3. 先投影现有报告能提供的证据。逐组完整时间线、实际上下文 token、成功请求 P95 如 OCR 没有输出，就标记未知并登记上游能力缺口；平台不能从 stderr 文本或失败请求时间伪造这些指标。
4. SQLite 安全结果投影、尝试历史、报告导出和页面保持一致。列表使用有界摘要，详情按需展示；不得向普通 API 增加完整工件、推理、工具参数或外部错误正文。
5. 历史结果默认不批量回填。提供明确的只读诊断/报告路径供管理员复核；如后续要持久化历史摘要，应单独设计带来源、版本和审计的回填操作。

**交付门槛：**合成用例覆盖 partial＋504、context timeout、工具错误共存、未知 schema、逗号路径、损坏报告、超长输入及无请求详情。原有完整/失败/取消/跳过判定和自动重试策略不回归。页面能够解释“完成 40/45，1 组超时，模型请求存在 504”，不会把所有失败统一归因为 504。

### 第二步：验证能否真正只做剩余部分

**改动落点：**新增与 `ocr_filter_probe.py` 同样隔离的恢复探针及测试，不修改原过滤探针的已验收语义。新探针入口和结果格式在实现时确定。

**实验步骤：**临时仓库提交两个独立文件组；本机合成 HTTP 端点控制第一组完成、第二组失败；保存真实 CLI 输出和隔离 session；恢复端点后用相同输入与配置执行 resume，检查已完成项是否复用、失败项是否完成、旧发现是否保留、调用请求及用量是否重复。再测试 commit/range、跨目录恢复、配置变更拒绝、会话损坏、取消和重复恢复。固定短预算，清理进程及临时目录，不等待生产 15 分钟期限。

**路由决策：**

- 原生 resume 的固定输入、复用、覆盖及费用语义全部通过，就以原生续审为首选。
- 原生不通过，但可靠失败子集选择可验证，就采用独立批次审核与平台聚合；同时验证规则优先级、特殊路径和保留跨文件上下文，不通过伪造临时 commit 绕过输入约束。
- 两条路线都不通过，不发布补审按钮；只交付诊断，登记需要 OCR 上游修复的能力和失败证据，重新估算工期。

**交付物：**版本化的兼容矩阵、脱敏探针报告、可重复执行命令及自动化断言。`--help` 中有 resume、退出码为零或 preview 成功都不算通过。合成端点验证的是编排正确性，不证明真实模型质量或零重复费用。

### 第三步：建立独立补审后端，不改全量重审语义

**改动落点：**新增恢复领域契约、用例、迁移与 API 模块；在现有 Worker 调度和执行槽接入，聚合逻辑单独模块化。具体迁移版本按实施当时基线分配。

**按以下顺序实现：**

1. **资格查询：**从原尝试及可信结果确定剩余 item ID、源快照和恢复方式；返回是否可补审及明确原因。前端不传任意文件路径决定审核范围，执行前再核对 Git、配置和工件。
2. **排队事务：**持久化幂等键、父任务、源尝试、源聚合版本、批准集合及预算；同父任务最多一个活动恢复请求。并发请求以数据库约束和事务裁决，唯一索引/约束在迁移测试中验证。
3. **领取与执行：**复用现有单模型槽和执行身份，隔离目录与 HOME；恢复工件复制只包含必要 session 及已验证配置材料，禁止共享个人 HOME。使用原 base/head，不重新取目标分支头。
4. **完成聚合：**根据第二步确定的原生/子集路线校验输入和覆盖；事务比较源聚合版本，拒绝迟到或失效结果覆盖新版本。父原始结果只读，另存聚合版本和发现来源；父任务详情同时展示原始结论与恢复后结论，列表使用与之匹配的有效结论。迁移、反馈/问题跟踪、统计、导出与通知消费者必须统一使用有效结论入口，不能某页显示 complete、另一处仍按旧 partial 计数。
5. **失败与取消：**补审失败只结束自己的批次，保留初审可读；取消、项目删除、全量重审和补审互斥，复用进程组终止与锁。无可信最终 JSON 时用量未知，不能填零。
6. **保留与清理：**恢复请求对源工件持有有界引用；同步验证监控清理、项目删除与恢复执行的竞争，结束后按保留策略释放。过期工件明确禁用恢复，不回退为全量执行。

**交付门槛：**临时 SQLite 和合成外部响应测试覆盖管理员权限、重复点击、并发创建、领取互斥、Worker 重启、提交不可达、快照漂移、覆盖冲突、聚合失败回滚、迟到结果、取消/删除/清理竞争、旧库升级回滚及历史不变。

### 第四步：接入页面和独立补充通知

**改动落点：**前端 API 类型和任务详情/列表、后端通知投递及报告导出；兼容既有飞书与 GitLab 发布记录，不复用旧投递身份。

页面保留“全部重新评审”，新增“继续审核剩余部分”和补审历史。确认框显示原始输入、剩余数、策略与费用未知提示；同一任务的执行按钮互斥。补审中仍可看原结果，完成后展示“初审 40/45 → 补审新增完成 5 → 当前 45/45”，而不是将原尝试改写为 complete。若仍有失败项，明确继续 partial。

每个可信聚合版本最多创建一份本地补充投递身份；待发送初审、已发送初审、补审完成和重发之间按版本隔离。飞书响应丢失后的外部重复风险明确披露，不能承诺机器人端绝对幂等。GitLab 发布若存在，必须先定义新发现与旧评论的对应及去重；未支持的目标保持关闭，不默认重发所有旧发现。

**交付门槛：**权限、确认、冲突提示、刷新持久化、320/390 像素与桌面、初审通知在途、补充通知失败、发现反馈与重复发现等回归通过。OpenAPI、报告字段与前端契约同步。

### 第五步：用受控试点解决源头问题并上线

诊断和恢复探针通过后，才安排真实端点调查：先核对有权访问的网关超时/排队/限流日志与关联请求，再对固定 SHA 的代表性样本做并发 4/2 的交错对照；每次记录原始配置、变更项、已知 token/缓存、费用完整度和发现质量。预算上限、样本数、停止条件和回滚配置必须在执行前写明，不能默认调用全部历史任务。

若证据为约 60 秒固定网关期限，优先修正对应链路或选用经验证能满足时限的端点；若为长工具链/分组期限，验证分组策略、工具失败处理和 CLI 子任务时限。任何调整必须形成新快照；执行参数改动是否允许复用旧结果由兼容矩阵裁定，不通过修改 hash 绕过冲突。

发布前成对备份、在副本演练迁移、协调在途任务并同版部署 API/Worker/monitor/前端；功能默认关闭，先一个项目人工开启。上线读回真实页面、实际排队和一次人工恢复记录，检查模型调用只覆盖允许范围、费用没有重复累计、投递独立重试。观察样本不足时只报告观察事实，不宣称根因已消除。回退关闭新入口并保留恢复历史，数据库恢复须处理新写入，不能降低版本号或让旧进程打开新库。
