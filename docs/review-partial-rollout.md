## 2. 当前产品流程

1. 打开合并后 partial 任务，读取可信失败集合和当前源版本；初审失败诊断继续可追溯，不冒充当前有效覆盖。
2. 管理员选择“继续审核剩余部分”，确认框冻结 head/base、模型版本、OCR 版本、规则摘要、失败路径、Token 与超时上限。费用未知明确标注未知，不展示伪造金额。
3. 提交仅持久化排队，不在 HTTP 中执行 Git/OCR/飞书。网络响应不确定时保留同一幂等键和原命令，不自动换键重试；版本冲突保留本地输入，刷新后重新确认。
4. 唯一模型槽轮转初审、补审、合并前审查及模型诊断。Worker 使用原 SHA、新隔离 checkout/HOME、原模型/规则快照；全量预览与子集预览、正式覆盖必须与批准范围精确一致。任何工件、提交、配置或范围漂移拒绝执行/聚合，不回退全量。
5. 有进展的 complete/partial 补审，同一事务保存批次、聚合、新发现出现、经完整证据链重放验证的有效版本与独立通知。没有进展、迟到、取消或失败不覆盖既有有效结论。
6. 列表、状态筛选、相邻导航、首页、运行异常、发现数量、反馈汇总和默认报告使用有效版本；`status`、原始结果和初审通知保持原事实。历史单次报告不夹带后来的补审发现或累计费用。
7. 补审历史、操作者、预算、状态、错误码、用量和起止可读。活动补审和全量重审服务端互斥，页面同步禁用；只读角色可查看、不能创建/停止/反馈/重发。

### 有效状态与费用的明确口径

- `status`：初审执行事实；`effective_status`：当前可信结论。不能用后者推断初审当时成功。
- `effective_conclusion`：列表有界摘要；`effective_document`：详情完整白名单发现与稳定来源。候选历史不自动回填或提升。
- 主身份 `j{job}:a{attempt}:c{index}` / `j{job}:a{attempt}:r{recovery}:c{index}`；精确重复只保留一个主身份，额外出现保留来源。新反馈必须带源尝试和版本，绝不调用旧评论下标接口处理补审。
- `cumulative_usage`：所有初审尝试及所有已经开始的补审，包含失败、取消和旧根尝试。排队未执行不计费；无可信结果计未知而非零。按逐次历史单价分别累计 CNY/USD，不混币种。
- `initial_cumulative_usage`：单独保留初审累计；版本报告用量只统计源尝试和截止该版本的已开始补审，不代表全部实际账单。
- 现有时间字段仍为初审时间，界面明确“初审累计执行”；补审时间见独立历史。近七天状态按有效结论分组，成功执行分位数仍只采用初审本身完整成功的样本，不能把补审完成当作初审成功耗时。

### 独立通知

- 每个可信版本一份唯一 Outbox 身份，仅列本批次新增发现，覆盖与累计发现数来自该版本。不撤销初审消息，也不重新发布全部历史评论。
- 初审通知 pending/sending 时等待；sent/failed 或没有初审投递时可处理独立补充消息。
- 本批零新增不等于全任务零问题；卡片明确累计发现数，不因遗漏旧发现发布绿色“无问题”。
- 通知使用独立执行令牌，最多五次自动尝试和有界退避。Worker 重启遇 sending 标为失败、外部结果未知，需管理员核对后只重发通知；不会重新调用 OCR。
- 真实飞书网络响应丢失仍可能在外部产生重复，无法承诺机器人端绝对幂等。任务全量重审或源证据失效后待发通知 superseded，不复活旧源。

## 3. 新配置和迁移

以下是配置说明，**本轮未写入实际 private.json 或环境**：

| 配置 | 默认值 | 约束与含义 |
| --- | --- | --- |
| `OCR_APP_REVIEW_RECOVERY_ENABLED` | `0` | 明确布尔值；默认关闭新的执行和通知领取 |
| `OCR_APP_REVIEW_RECOVERY_REPOSITORY_IDS` | 空 | 逗号分隔的正整数仓库内部 ID；进程启用时必须非空，只选一个项目起步 |
| `OCR_APP_REVIEW_RECOVERY_MAX_BATCHES` | `3` | 1～10；同一父任务全部补审的最大批次数，失败/取消也占用，幂等重放不重复计 |
| `OCR_APP_REVIEW_RECOVERY_MAX_TOTAL_TOKENS` | `100000` | 1～100000000；同一父任务全部批准 Token 上限之和，不是实际费用额度，失败/取消不自动退还 |

批次 Token 还受原快照非零预算约束；超时必须为正且不超过原快照及 3600 秒。配置改变必须生成新快照，不允许伪造 hash 聚合；这些限制不是模型侧绝对账单保障，真实试点另设金额及请求停止条件。

迁移 43 是恢复表，44 是稳定出现/反馈，45 是有效指针、独立通知、持久化轮转与操作者。**不修改已共享的 43/44 迁移，不自动回填旧候选、不自动重审历史、不自动生成旧通知。** 源尝试、根配置、批次或中间聚合被修改/删除会清有效指针；显式读与再次补审逐版重放源摘要、批准集合、覆盖和发现，损坏时拒绝，不能用覆盖单调性代替可信来源。

3. 在新目录副本执行当前 `Store.migrate()`，核对 user_version=45、quick_check=ok、foreign_key_check 为空、初审/尝试/投递计数不变、新有效/补充投递均为零，并重复迁移验证幂等。不可让旧进程打开新 schema。
4. 总开关保持 0，同版发布 API/Worker/monitor 与隔离构建后的前端；核对实际进程启动时间、OpenAPI、新页面及唯一 Worker/模型槽。健康 200 不代表补审功能验收通过。
5. 经真实试点边界确认后仅一个仓库开启，设置较小的批次和总 Token 上限；管理员选一条输入/工件/配置仍有效的任务，人工确认范围再排队。核对 selected 恰好为原失败项，已完成文件没有再次执行，初审/补审/通知身份与费用均独立。
6. 核查一次部分进展、一次停止、一次通知失败后仅重发、一次刷新和只读访问。读取 SQLite 和页面的一致事实；观察期结束前不扩大白名单。

## 5. 真实根因试点协议（尚未执行）

这一步不能由补审按钮或合成端点替代。当前仍缺**可访问的网关/上游日志、固定样本和费用金额上限**；本轮不访问未知外部服务、不自动试跑 #321/#343/#381，不宣称 timeout/504 已根治。

### 执行前必须填定

| 输入 | 约束 |
| --- | --- |
| 网关/上游关联 | 只读取有权访问的 trace、排队、限流和超时配置；保存脱敏 ID/类别与时间，不保存 prompt/响应 |
| 代表性样本 | 从一个项目选 1～2 个固定 head/base；包括失败分组和成功对照，不能用当前 HEAD 替代 |
| 成本边界 | 明确本轮金额上限、每次 Token/超时、最大运行数、费用未知时立即停；Token 预算不等于金额预算 |
| 对照变量 | 固定规则、模型、端点、OCR 版本，按并发 4/2 交错顺序；端点对照另开实验，不能同时变多个因素 |
| 停止条件 | 达总预算、连续两个不可归因故障、覆盖漂移、敏感信息风险、发现质量明显下降或用量未知立即停 |
| 验收标准 | 逐次保留覆盖/失败组/HTTP类别/耗时/token/缓存/已知费用与完整度/人工质量核对；样本不足只描述观察 |

### 可证伪的调查顺序

1. 以 #381 的约 60 秒重复 504 为线索，关联最外层代理、模型网关及上游 trace，核对哪一跳的截止时间触发；没有 trace 时“具体层级未知”，不能把时间相近当因果。
2. 将分组截止、整体预算、计划请求重试及 context 标签分别对齐。现有请求报告主要列失败，不能据此计算成功 P95、实际上下文 Token 或完整分组关键路径；缺口需 OCR 上游补结构化 telemetry，平台不从 stderr 猜造。
3. 对重复失败的六文件组检查实际上下文读取、缺失依赖和搜索上限；使用安全工具类别及规模计数，不复制代码/工具原文。不能直接归因文件过大，也不能一律归因 504。
4. 按有限对照结果决定优先修正具体网关期限、端点排队或分组/工具链；任何参数变化形成新快照，不在本轮静默全局降并发、延超时或换模型。
5. 形成脱敏实验记录，分别写“已证实”“未证实”“负面结果”和回滚配置。没有实际对照、上线及足够观察，不将 root cause 状态标成已解决。
