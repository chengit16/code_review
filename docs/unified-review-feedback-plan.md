# 评审反馈与发现处理统一规划

关联事项：PI-20261109-008；承接 PI-20261109-007 中“有反馈即已处理”的最新口径。本文保存已批准的规划与原始核对快照；当前实施、验证及部署事实以 PI-20261109-008 的追加台账为准。

## 1. 当前差异已核实

本轮对本机 SQLite 执行只读事务，调用现有 quality_snapshot 和 QUALITY_CTE 核对全部项目、30 天窗口（UTC 2026-10-11 至 2026-11-10，左闭右开）。以下与用户截图一致，仅表示核对时的快照。

| 维度 | 计数 |
| --- | --- |
| 当前发现反馈 | 有帮助 8、误报 11、忽略 2、未评价 30，总计 51 |
| 同一批发现映射的跟进状态 | 待处理 46、已修复 2、已忽略 0、误报 3，总计 51 |
| 按发现反馈定义处理进度 | 已处理 21、待处理 30，总计 51 |

其中 11 条误报反馈对应的跟进问题均仍为开放；2 条忽略反馈分别对应开放和误报跟进状态；8 条有帮助反馈中 6 条对应开放、2 条对应人工修复。代码确认反馈存于 review_feedback / review_finding_feedback，跟进状态来自 review_issue_states，两者不会自动互改。因此截图的两个“51”虽相同，分类读取的是不同事实，不能期望误报、忽略自动相等。本轮证据支持数据口径不一致，不支持认定反馈丢失或自动改写历史。

另外，“问题变化”统计新问题与人工修复，按问题事件及唯一问题汇总；“待跟进问题”当前也按问题编号和独立处置筛选。简单删除首页两个页签仍会留下这些入口的含义差异。

## 2. 建议统一规则

用户当前要完成的任务是阅读、判断并反馈每条评审发现。主要页面统一使用当前有效发现及其已保存反馈：

| 已保存反馈 | 反馈名称 | 发现处理状态 |
| --- | --- | --- |
| helpful | 有帮助 | 已处理 |
| false_positive | 误报 | 已处理 |
| ignored | 忽略 | 已处理 |
| 无当前三类反馈 | 未评价 | 待处理 |

三种选择互斥，撤销后回到未评价、待处理。历史 fixed 反馈继续按未评价处理，不猜测为有帮助；原记录保留。发现已处理不表示代码已修复，也不更新评审执行状态、飞书或 GitLab 投递状态。

## 3. 首页只保留一个反馈视图

将“评审质量与处置”改为“评审反馈”，移除“问题状态 / 反馈价值 / 问题变化”切换，直接展示现有反馈价值内容：

- 四项主要数量：有帮助、误报、忽略、未评价。
- 同一集合的处理进度：已处理 21/51、待处理 30/51；处理完成率按三类反馈之和计算，本快照为 41%。
- 保留反馈趋势和精确数据表；点击数量进入同范围发现列表，携带项目、时间窗口、反馈和处理筛选。
- 移除本区“当前问题 · 不限时间”处置计数带，以及样本中的独立处置状态列和筛选，避免再次出现同名不同数。
- 有效评价占比和误报占比放在可展开的统计口径中。有效评价占比仍为 19/51，误报占比仍为 11/19；不能把前者称为处理完成率。忽略不算有效评价，但算已处理。

首页其他入口也要一起核对：当前待处置指标、严重级别分布、项目概况中的开放问题数，应改为按同范围未评价发现展示，并命名为“待反馈发现”“待反馈严重级别”等。若仍展示历史跨任务修复信息，应进入明确标注的历史记录入口，不继续混在主要待办指标中。项目和时间范围共用同一条件，不把本期待反馈与不限时间开放问题混加。

## 4. 待跟进问题改为评审发现列表

推荐将导航和页名调整为“评审发现”，默认显示待处理，支持全部、待处理、已处理；另用“反馈”筛选有帮助、误报、忽略、未评价。列表中的一行对应当前有效版本的一条 finding，反馈和首页逐条对齐，不再以去重问题编号作为主计数单位。

建议列：发现摘要 / 文件、任务 / 项目、提交人、严重级别、处理状态、价值反馈、发现时间。详情沿用现有问题描述与修复建议分区，提供同样的三个反馈按钮与撤销。修复记录和跨任务出现历史作为辅助内容查看。

必须统一数据读取和写入：

1. 首页、任务详情和发现列表共用当前有效发现集合及反馈优先规则。初审镜像只算一次，有效补审按主身份统计，不展开 also_seen_in，不复活旧尝试或未提升候选。
2. 筛选、分页、导航与计数均在服务端按同一集合执行；不能拉取当前页后按反馈过滤，再声称总数一致。首页全量数量与默认待处理列表数量通过明确筛选对应。
3. 不同页面修改同一 finding 的反馈，保存后同步刷新详情、列表、首页及任务反馈计数；按版本校验，409 保留操作目标和输入，提示重新核对，不自动重试。
4. 同一跟进问题关联多条发现时，每条各有反馈。出现有帮助、误报混合时按原发现保留，不以最后一次反馈覆盖整个问题，也不复制为其他发现的反馈。
5. 批量反馈只作用于显式勾选的发现，提交前展示数量、目标和新反馈；保存失败项保留，成功项刷新。原批量修复/忽略跟进状态动作从新主流程移出，不将其暗中改成批量价值反馈。

## 5. 历史与旧入口

- 不删除旧 review_issues、处置事件、人工修复说明和审计；原始事实继续可查，不进行“把开放全部关掉”的批量回填。
- 旧问题编号可能对应多条发现，旧问题链接应打开带说明的关联发现/原问题历史，不能随意选一条代表整组。
- 旧 status=open/ignored/fixed 等处置筛选不直接映射成新反馈值；保留历史只读入口或明确提示筛选已停用。已修复不自动映射有帮助，已忽略不自动映射忽略。
- 当前反馈记录在新展示中直接生效，所有来源均须按同一版本和范围读取；找不到来源时显示待核实，不补造反馈或完成状态。
- 方案以复用现有反馈事实为主。新增列表契约、批量反馈能力和旧入口兼容需要单独实施验证，不因已有质量样本接口就宣称可以直接替换全部跟进功能。

## 6. 推荐实施顺序与验收

建议在同一改造阶段完成首页精简和发现列表统一，避免只隐藏图表而保留冲突待办。

1. 先定义共享当前发现读取、处理状态和筛选契约，补充只读汇总与分页的一致性验证。
2. 改造首页、样本和评审发现列表，贯通反馈修改、撤销、版本刷新及旧链接；保留历史修复记录入口。
3. 核对所有待办、严重级别、项目概况与任务筛选入口，不遗留读取独立修复状态的主要“待处理”入口。
4. 用合成数据覆盖三类反馈、撤销、历史修复、混合多来源、合并问题、多次尝试、有效补审、版本冲突、只读权限及分页；浏览器核对桌面、窄屏和来源跳转。发布后再核对真实页面，不能用本地测试代替部署生效。

本快照的验收例子：在同一项目和窗口下，首页误报 11，进入误报发现列表应为 11 条；忽略 2 应为 2 条；默认待处理为 30 条，全部已处理为 21 条。有帮助反馈撤销后，已处理减一、待处理加一，各页面同步更新。该例子不要求把原 46 个开放问题改写成 30 个，也不以消除数字差异为由删除历史处置。
