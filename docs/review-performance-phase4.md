# 评审优化第四阶段：有界调度解耦

> 实施日期：2026-11-06。按用户要求先完成本地代码和隔离验证；不是本机业务服务已切换的声明。模型任务总并发仍为 1，不启动第二个 Worker，不提高 OCR 内部文件并发，不自动重跑旧任务。

## 1. 本期交付范围

此前 `run_once` 同步串行执行，长评审、事件展开、预审、连接诊断、通知互相阻塞；持续有事件或预审时，低优先级类别也可能长期没有机会。本期正式 Worker 入口改为单协调器与三个固定执行槽，SQLite 仍是唯一业务队列。

| 执行槽 | 每槽在途上限 | 类别与规则 |
| --- | --- | --- |
| `model` | 1 | 合并后评审、合并前审查、模型诊断成功领取后轮转；模型诊断也不能绕过配额。 |
| `ingress` | 1 | 事件展开、补审扫描、Git/GitLab 诊断、规则预览轮转。规则查询不访问模型。 |
| `delivery` | 1 | 飞书通知、GitLab 行内发布、飞书诊断轮转；不与大仓库 fetch 共用线程。 |

协调器只做短事务领取、提交执行和心跳；执行单元各自通过 Store 新建 SQLite 连接，外部调用期间不持数据库写事务。没有进程内第二业务队列，也不一次性领取一批等待中的模型任务。`run_once` 保留作既有同步调用与测试辅助，正式 `python -m ocr_manager.worker` 使用新调度器。

事件和通知不再等待正在运行的 OCR 结束，但每个槽内仍可能等待当前 Git、网络调用或发布结束，不承诺立即响应。合并后/合并前评审的 Git 准备仍属于模型槽的一部分，本期不并行准备第二个评审。

## 2. 顺序、公平与副作用

- 同仓库事件不能越过更早的 queued/running 事件，即使前者处于重试退避。合并后任务保留事件与 MR 内提交顺序，后续无文件/纯换行跳过仍须等前序评审结束。
- 事件、合并后评审和预审分别维护仓库游标，按仓库编号循环选择下一可运行仓库。不是只避开上一仓库；三个仓库持续积压时也都有机会。游标重启可重置，不改变持久化事实和顺序约束。
- 原子领取统一使用短 `BEGIN IMMEDIATE` 事务；事件、诊断、规则预览、补审、飞书、行内发布与既有评审领取均不跨网络持锁。
- 飞书和行内发布在工件锁内重读 sending、任务状态和评审尝试身份；正在发送时重审返回冲突，不能删除旧投递记录后复用身份。项目已删除的结果不会复活。
- 已发出的网络请求不能撤回。飞书仍是至少一次投递，响应丢失后的重试可能重复；不宣称 exactly-once。GitLab 沿用现有任务/尝试/发现标记去重。

## 3. 身份、心跳与恢复栅栏

独立迁移 `37 → 38` 新增 `worker_execution_slots`，记录 owner、代次、槽、任务类型/ID、仓库、进程、开始/结束和心跳。迁移不恢复任务、不修改历史策略，也不伪造旧 Worker 的执行槽。

1. 正式入口先取得 `worker.lock`，再迁移和恢复旧业务记录，之后登记新的执行身份。
2. 心跳约每秒由协调器写入，耗时执行不会阻塞续写。旧 owner 或旧代次不能释放新执行槽。
3. **心跳不是可抢占租约。** 过期只提示待核实，不解除进程锁、不重发任务。运维页 30 秒刷新，显示的是最近一次查询的持久化事实。
4. Git/OCR 启动前建立专用进程组栅栏，先确认组长就绪再启动命令。组长继承 Worker 及当前仓库/工件锁；即使 OCR 启动器关闭锁描述符或提前退出，组长仍持锁。
5. 协调器被 SIGKILL 后控制管道断开，组长终止整个受控命令组；在此之前第二个 Worker 无法取得锁，API 也不能越过工件锁清理目录。正常停止会先通知执行单元，再终止命令组并等待线程结束，最后释放 Worker 锁。
6. 中断保留业务 running，由下次独占恢复记录“中断，结果未确认”，沿用原有有界次数，不把正常停机伪装成用户取消或重置重试预算。

栅栏使用本机 POSIX `flock` 与进程组，适用于当前 macOS/Unix 运行方式；不提供跨主机共享数据库或 Windows 多进程支持。固定 OCR 启动链必须留在受控进程组，主动 daemonize/`setsid` 的第三方扩展不属于已验证契约。进程组长若被单独暂停，恢复采取失败关闭而不是根据心跳抢占；不能手工删除活跃锁文件来“解锁”。

## 4. 仓库、工件、删除与清理

- clone/fetch/MR fetch/worktree 增删使用仓库级锁，放在仓库目录外的 `repositories/.locks`；不同仓库不会被一个全局 Git 锁阻塞。模型运行期间不持仓库锁。
- HTTPS askpass 辅助脚本按仓库区分，避免多个仓库并行写同一路径；令牌仍通过受控环境传递，不进入脚本正文。
- 合并后执行与投递持有既有工件锁，清理先尝试取得该锁并重查数据库；删除项目后目录先保留，执行单元退出后再清理。
- Worker 停止可能留下 worktree，恢复使用独立尝试目录，不复用未确认的运行目录。本期不新增自动全盘 Git prune，不清空仓库缓存。
- 取消、项目删除和预审失效沿用业务检查；Git/OCR 命令增加 Worker 停止检查。GitLab 分页在每个请求前检查停止，不因补审或发布继续扫描后续百页。已经开始的 HTTP 调用等待既有超时边界，不能承诺信号到达后立即退出。

## 5. 监控入口

“运行监控 → Worker 调度与执行槽”展示模型并发、三个槽的任务与心跳。未启动新 Worker 或旧 API 未提供数据时，明确显示无法确认本机已生效；停止不显示为运行，超过 15 秒的非停止心跳显示待核实，不提供抢占或增加并发按钮。接口仍受管理员权限保护。

## 6. 自动化验证

本轮使用临时 SQLite、临时本机 Git、合成执行器和合成子进程；未调用真实 GitLab、模型或飞书。专门验证：

- 长评审阻塞期间事件、通知和心跳推进，第二个模型任务仍 queued。
- 合并后、合并前和模型诊断轮转且同时模型执行数不超过 1；Git/飞书诊断不占模型槽。
- 三仓库持续积压轮转、同仓库事件退避不越序；并行连接对事件、预审、诊断、补审、飞书和行内发布只能领取一次。
- 停止与两次预算恢复、旧身份迟到释放、未捕获执行异常停止调度。
- 删除项目不复活结果，清理等待工件锁，发送中重审冲突；已领取通知等待锁时删除项目，解锁后不发送旧快照。
- OCR 启动器提前退出且后代关闭锁描述符后强杀协调器：栅栏暂停时锁仍阻止新 Worker 与工件清理，继续栅栏后后代被终止；Git/OCR 正常停止也终止受控命令组。
- 37 版旧库失败迁移整版回滚、重试及幂等升级，旧 running 证据保留；监控接口未授权拒绝访问。
- 真实 Worker 模块入口在空临时库初始化三个槽并续写心跳，拒绝第二进程，SIGTERM 后记录停止并释放锁；GitLab 四类分页在停止后不再发起下一请求。
- 前端旧 API/空记录、执行中、已停止和过期心跳，以及桌面和 390/320 像素布局。
