# 自研代码评审 Agent 项目建议书

2026-11-19 · 供项目负责人和开发者评审 · PI-20261116-002

## 一、建议先做什么

**建议先在一个仓库试点。保留阿里 Alibaba Open Code Review（OCR）作为正式评审，由现有 Worker 对同一版本再运行一次自研 Agent。两份报告分别保存，由你裁定发现是否成立。** 试点要回答的业务问题是：多花一次评审的时间和费用，能多发现哪些值得修的问题，给审阅者增加多少无效工作？

首版交付物是任务详情中的一次完整比较。你打开一条 MR，可以看到两侧审了哪些文件、分别报了什么、依据在哪里、花了多少钱，可以补录双方都漏掉的问题。评审结束后即可释放 Worker；你可以稍后回来标注。试点期间飞书和 GitLab 继续消费正式 OCR 结果。

## 二、技术路线与分工

**自研评审方法，使用 LangGraph 编排，在模型和工具接口上按需采用 LangChain。** LangChain 提供模型与工具循环，适合把一组工具交给模型选择；LangGraph 允许将确定性步骤和模型决策编排在同一个工作流中。本项目选择后者作为外层，是因为“检查过哪些文件”“是否引用有效证据”“预算是否耗尽”都需要由程序作答。[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview) · [LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

| 选择 | 在本项目中如何使用 | 取舍 |
| --- | --- | --- |
| 全部自写 Python 执行循环 | 直接调模型 SDK，自行处理消息、工具、终止和恢复 | 适合只有少量固定步骤的原型。恢复与重放也要自己维护。若技术验证中图运行时的成本超过收益，这是备用路线。 |
| 使用 LangChain 标准 Agent | 给模型一组只读工具，由它循环取证，再输出报告 | 适合快速检验模型会不会使用工具。逐批覆盖、证据验收和预算仍要由我们落实。 |
| 自定义 LangGraph 流程 | 程序固定评审范围和必经检查，模型在批次内决定还需读什么 | **首选试点路线。** 多投入一次状态与节点设计，换取每个批次的结果、缺口和中断位置都能解释。 |

平台继续负责事件、排队、同仓库互斥、费用、结果与投递。LangGraph 只运行一次 Agent 尝试；图保存点用于恢复内部进度。外部模型可能已计费但本地尚未收到确认，这时保存调用编号并标记费用未知，由 Worker 根据预算决定重试。模型实现通过小接口替换，选型时先验证工具调用、结构化结果和用量返回，再固定模型与依赖版本。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## 三、一条变更怎样被评审

1. **冻结输入。** Worker 固定仓库、基准 SHA、目标 SHA、差异文件清单、排除原因、规则和背景版本。两路独立读取快照。若模型不同或 Agent 额外读取了业务文档，对比页注明差异。
2. **生成计划。** 平台给每个审查单元编号，按语言与变更类型加载 Skill。模型可以提出检查重点，平台掌握覆盖分母。首版同仓库串行，先交付正式 OCR 结果。
3. **按需取证。** Agent 可读该 SHA 下的 diff、文件片段、调用方和测试断言。原生工具负责精确代码读取；首个只读 MCP 只提供有版本的团队规范。每条证据带代码位置或文档版本，两个引擎均看不到另一侧本次报告。
4. **验证判断。** Skill 规定要找的反例，程序检查引用是否真实存在。模型须解释触发条件、已有保护为何不足以及实际后果。证据不足时允许有限补查；预算用完后保留已验证发现和未审清单。
5. **分别保存。** SQLite 关联输入、引擎、配置、执行尝试、覆盖、发现和费用，原始报告存入受限工件目录。一次比较固定两份具体结果。只重跑 Agent 会产生新比较版本，旧报告和你的旧评价仍可查询。

**示例（虚构）。** 一个 MR 给订单同步任务新增超时重试。Agent 怀疑同一订单可能被重复处理。`retry-idempotency` Skill 要求它核对超时发生在哪一步、重试是否沿用同一业务键、写入侧是否有唯一约束。Agent 使用代码搜索定位调用方，再读取对应版本的写入逻辑。若已有约束覆盖这条路径，就撤销候选；若超时发生在写入成功之后且重试会产生第二条记录，就在报告中列出触发顺序与两处代码位置。若 OCR 也报了同一根因，你只需核对一次，并分别评价两侧说明是否准确。该例可作为首个合成验收用例，分别准备“有保护”和“无保护”两个版本。

## 四、首版范围

| 首版交付 | 验收时能看到什么 |
| --- | --- |
| 一个仓库、一个 Agent、一个经验证的模型端点 | 项目支持手动发起双评审。未选项目走原流程。 |
| 固定版本的代码工具、通用证据 Skill、一个项目高频问题 Skill | 可从发现跳到对应 SHA 与行号，查看所用 Skill 版本；先选一个专题积累正反样本。 |
| 一个只读规范 MCP | 返回内容有来源和版本。必要规范不可用时，报告指出受影响的检查项。 |
| 独立状态、限额、取消与单侧重跑 | 一侧失败时另一侧结果仍可读；未覆盖文件单列。费用包含失败尝试，缺失值显示未知。 |
| 任务内对比与人工裁定 | 分组查看共同发现、各自独有及人工补录的问题；支持纠正匹配、标注证据不足并保留历史。 |

试点只需一个模型角色。自动修复、自动发布 Agent 评论、多 Agent 并行和全量历史回跑放在试点决策之后。这样第一轮反馈能直接用于改善检查方法。

## 五、怎么判断值不值得继续

建议选 **20～30 条变更**作为首轮试点，含正常变更、已知缺陷和跨文件修改。历史问题用修复前提交，隔离后续修复和评论。预留一部分样本，仅在修改 Skill 后验证。这个数量用于发现典型错判和估算人工负担，不能支持全项目准确率承诺。

每个样本以同一输入版本内的独立问题为单位。先核对代码，裁定“成立／不成立／证据不足”，再单独记录“是否值得处理”。对独立抽取的一部分变更，先由人读代码写出基准问题，再揭示两份报告，才能看到双方共同漏报。重跑结果另列，防止挑选表现最好的一次进入统计。

试点报告至少回答四件事：

- **报得准吗？** 分别展示已裁定精确率，即成立数 ÷（成立数＋不成立数），同时列出原始计数、未标注数和证据不足数。
- **多找到了什么？** 按根因列出“仅 Agent 找到且人工确认”“仅 OCR 找到且人工确认”和双方均报告的问题，注明严重性和处理价值。仅在独立人工基准内计算召回。
- **花费是否值得？** 列出额外模型费用、等待时间和人工复核耗时。用 Agent 全部尝试费用除以其独有且值得处理的问题数；分母为零时直接写“本轮没有此类发现”。
- **优势出现在哪里？** 质量对照使用输入一致、覆盖可比的配对样本；失败、部分完成和费用未知的任务也进入运行与成本报告。尽量同模型同预算；若端点或资料权限不同，结论限定为两套实际配置的比较。

**推广决策。** 试点前由负责人填写可接受的单任务费用上限、人工复核时间和正式任务等待上限。若留出样本中能反复找到有价值的独有问题，且运行指标满足这些上限，可扩大到同类仓库。若收益集中在某一类变更，只对该类触发 Agent。若发现主要重复或预算经常耗尽，保留 OCR，暂停自动抽样，先用已标注案例改进对应 Skill。

## 六、交付顺序与投入

以下沿用总方案的粗估，按一名熟悉仓库的开发者计算。第一阶段的 1～2 人日最小图验证已包含在阶段投入中。模型供应商异常、部署排期及持续人工标注时间另计。

| 阶段 | 工程投入 | 进入下一阶段的条件 |
| --- | ---: | --- |
| 1. 冻结输入与运行协议 | 2～3 人日 | 一个合成 diff、一个假模型、一个只读工具能生成独立结果。预算停止、一侧失败和重复触发可区分。 |
| 2. 接真实模型与首批 Skill | 4～6 人日 | 完成正反例验证，结果能追溯到代码；人工取消后迟到响应不能成为有效结论。 |
| 3. 对比与人工评价 | 3～5 人日 | 同一任务能比较两路、补记漏报、单侧重跑并查看旧评价。 |
| 4. MCP 与单仓库试点准备 | 3～5 人日 | 规范有版本，项目有开关和预算，能输出覆盖、增量发现与复核成本报告。 |

**建议批准的第一笔投入是阶段一。** 先交付上述订单重试正反例、两份独立结果和一次异常演示，再决定是否投入完整的约 12～19 个工程人日。若模型或工具契约无法满足要求，调整适配或执行层即可，输入与评价协议可以继续使用。

本文为规划。系统兼容边界与数据模型见[双评审总体方案](dual-engine-review-agent-plan.md)，节点、保存点与恢复细节见[框架详细设计](review-agent-framework-design.md)。
