# 问题台账漏记防护与交付核验

关联事项：PI-20261107-003。此机制降低遗漏概率，不承诺发现所有尚未登记的聊天问题，不自动生成未知业务事实。

## 三个时点

1. **受理**：识别独立新问题后先建 PI 记录，写明真实现象、当前排查状态、未验证和未部署，不等最终答复。旧问题继续用原编号；新问题独立建档并关联旧编号，避免标题与内容不相符。
2. **过程**：阶段完成、失败或准备中断时追加进展。不修改已同步的旧段落，不等全部修复结束才写来源。机器和进程突然退出仍可能造成最后一段进展缺失，因此受理记录不能省略。
3. **收尾**：追加实际修改、检查和生效范围后执行只读命令，明确核对本次编号与期望条数。新问题至少受理、收尾两条；已有问题使用本轮追加后的真实累计条数。

```sh
PYTHONPATH=backend .venv/bin/python -m ocr_manager.improvement_log_check \
  --database .local-data/local/app.db \
  --source-id PI-20261107-003 \
  --minimum-entries 2
```

可以重复 `--source-id`，但不同事项期望条数不同时应分别执行。默认来源为 `docs/problem-improvement-log.md`，可通过 `--source` 显式更换；数据库必须显式指定，禁止用项目根目录的空数据库替代业务实例。

## 检查与退出码

命令以 SQLite URI `mode=ro` 打开已存在数据库，在只读事务中核对并显式关闭连接。不实例化 Store，不迁移、不创建数据库、不强制同步，不修改页面、游标、历史或聊天内容。

| 结果码 | 含义及处理 |
| --- | --- |
| `source_missing_or_progress_incomplete` | 本次编号不存在或未达到要求的追加条数，先补真实受理/进展，不能借其他编号通过。 |
| `not_imported` / `sync_pending` | 来源未同步或有待导入的追加，等待正常 monitor，不能声称页面已更新。 |
| `source_history_conflict` | 旧来源被修改/删除，先核对历史，不覆盖页面。 |
| `page_missing` / `page_changed_or_archived` | 页面与游标不一致、人工编辑或归档，人工核对后处理，命令不修复。 |
| `state_mismatch` | 页面与来源明确状态不一致，不能把代码修改当作验证或部署完成。 |
| `monitor_not_recent_or_error` | 维护检查已超过 120 秒、时间异常或记录错误；核对 monitor，不盲目重复启动。 |
| `check_unavailable` | 来源格式、数据库路径、结构或读取异常；仅输出脱敏错误，不打印正文或私有配置。 |

整体通过才退出 `0`，失败退出 `1`。输出只含编号、来源条数、页面 ID/版本、通过与错误码，不包含模型正文、令牌或私有配置。失败可以如实结束本轮并说明阻塞；不能为了通过而编造部署证据、覆盖人工记录或自动执行业务补审。

## 边界

- monitor 是自动同步器，不是聊天问题识别器；没有来源就无从导入。此次遗漏发生在写来源之前，不能只修改同步轮询间隔来解决。
- 项目规则要求执行命令，但该命令不会自动拦截所有聊天回复；执行者仍需遵守先建档与收尾核验。CI 也无法凭代码推断聊天里是否有未登记的问题。
- 来源条数和摘要一致不证明自然语言事实真实，也不证明运行功能已经部署；证据仍应来自实际命令和业务持久化数据。
- 不增加抓取其他会话的权限、后台服务或通知任务，不修改既有自动归档策略。
