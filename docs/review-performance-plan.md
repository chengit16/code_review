# 评审稳定性与耗时优化方案

> 编制日期：2026-11-05，状态更新：2026-11-06。前三阶段、纯换行过滤验证和项目级开关已完成本地实现（过滤默认关闭）；按用户授权实施第四阶段的并发 1 有界解耦与隔离验证，不以此替代真实试点。业务实例未切换，模型并发 2 未开放。检查与升级边界见各阶段记录及[第四阶段实施记录](review-performance-phase4.md)。
> 最新补充见[纯换行过滤实施记录](review-newline-filter.md)。
> 本方案补充[实施流程](implementation-flow.md)，不替代其提交范围、持久化、鉴权和覆盖判定约束。历史功能进度仍见[项目完善实施路线](implementation-roadmap.md)。

## 1. 目标与实施结论

本轮优先解决三个问题：失败原因被掩盖、大范围任务反复消耗模型额度、列表耗时不能解释实际等待。先做错误处理和输入保护，再完善展示，最后根据指标决定是否引入调度并发。

推荐顺序：

1. 第一阶段：修复错误处理、超时证据和重试分类。
2. 第二阶段：增加范围预检、换行差异识别和项目预算保护。
3. 第三阶段：展示排队、逐次执行、累计耗时和跳过原因。
4. 第四阶段：在前三阶段验收后，评估长评审与轻量任务解耦。
5. 后续能力：分批评审、断点续审和更高并发，单独评估，不作为首版承诺。

首版以第一至第三阶段为交付范围。所有阶段默认不自动重新评审历史失败任务、不修改原始提交、不切换生产模型、不擅自提高并发。

## 2. 已确认的问题与证据边界

以下为本次本地排查时读取的 SQLite、OCR 工件及 Git 对象事实，不代表所有项目或后续运行均如此。

| 现象 | 已确认事实 | 结论 |
| --- | --- | --- |
| #369 一小时失败、三次尝试 | OCR 预览有 1,460 个可审查文件；三次均为 `OCR result 超时`；单次预算 3,600 秒 | 累计执行约三小时，而非列表显示的一小时；范围中混有大量换行变化 |
| #366 一小时失败、三次尝试 | 预览有 1,462 个可审查文件；提交用于统一 LF；Git 忽略行尾 CR 后仅剩 3 个变更文件、增删各 9 行 | 大量纯换行变更进入模型，整批超时重试进一步放大成本 |
| #360、#361 两秒失败 | OCR 的 `retry_report` 记录模型请求 HTTP 404，结果 `comments: null`；平台投影遍历该值再次触发 `TypeError` | 原始模型故障被平台异常掩盖；404 的具体端点或模型路由原因仍需连接诊断 |
| #362、#370 跳过 | 仅修改 `.vscode/settings.json`，OCR 预览排除该文件 | 约一秒完成预览，未调用模型；跳过不等于通过 |
| #373 跳过 | 固定范围的 OCR 预览为零个变更文件 | 约一秒执行，但排队约五小时 |
| #372 显示已取消 | 第一次尝试完成，第二次尝试被用户停止 | 不应归类为跳过或覆盖历史成功记录 |
| #368 完成但耗时约二十一分钟 | 覆盖 177 个文件，约 674 个逻辑请求、2,624 万总 Token | 部分长任务有真实工作量，不能统一降到几分钟超时 |

补充边界：

- #369 忽略行尾 CR 后仍约有 598 个变更文件，不能把整个范围认定为纯换行，也不能整批跳过。
- Git 全量统计与 OCR 预览统计存在范围筛选差异，两者必须分别标记，不能混为同一计数。
- 超时任务缺少正式评审 stderr 工件，目前不能确定具体卡在哪个文件、模型请求或工具调用。
- 超时结果缺失不等于没有产生模型费用；费用未知时必须显示未知，不能记为零。

## 3. 不可破坏的约束

1. GitLab webhook 只鉴权和落库，Git、预检、OCR 与通知仍在独立 Worker 执行。
2. Push 使用已冻结的 `before..after`，MR 和合并前审查继续遵守各自的固定提交或基准语义；不改成当前分支 HEAD，不通过临时提交伪造输入。
3. 不修改 checkout 的代码或换行符来迎合过滤器；预检只读取受控 Git 对象，不执行被评审仓库的脚本、安装命令、过滤器或外部 diff。
4. 所有排除、限额、重试与恢复都有 SQLite 记录和工件证据。未审查、豁免、预算耗尽和失败不能被包装为完整成功。
5. 评审、飞书通知和 GitLab 发布分别重试；不得因通知失败再次调用模型。
6. 保留原始 OCR JSON；数据库和普通日志只保留安全投影。密钥、完整外部响应、代码正文和模型推理不进入错误摘要。
7. 新策略进入配置快照和任务身份计算；不能给已入队任务静默替换规则。历史记录不改写成新策略的结果。

## 4. 分阶段实施

### 第一阶段：错误可解释，重试有边界

**目标：**修复已复现的错误掩盖，避免相同输入因笼统异常分类反复执行。

实施内容：

- 对 OCR 结果建立统一的边界校验和安全投影。允许失败结果的 `comments: null` 作为空发现保存，但不把任意错误类型强制转换为空列表；可信结论仍取决于 schema、输入 SHA 和覆盖集合。
- 从受支持版本的 `retry_report` 提取错误类别、HTTP 状态和阶段等允许字段。保留“HTTP 404”和“结果格式错误”的区别，给出修复建议；不直接转发外部响应或未经处理的 `message`。
- 用明确的错误类别替代“所有 `RuntimeError` 都是临时故障”。返回 `failed` 的可信 OCR 结果也进入分类器，而不只处理抛出的 Python 异常。
- 评审错误分类与 GitLab 事件、通知分类隔离，避免修改共享函数时误伤其他重试链路。
- 超时和取消时先收集、脱敏并限量保存已有 stdout/stderr，再终止整个进程组；无输出时仍记录阶段、时间和退出原因。
- OCR 语言和 provider 配置命令也使用整体剩余预算，避免各自得到完整一小时。进程终止宽限单独记录，不隐瞒预算后的清理时间。
- 为超时但无可信最终 JSON 的尝试保留可诊断状态；存在部分文件不等于可以直接发布为有效覆盖结果。

建议的首版重试策略：

| 错误类型 | 自动处理 | 人工恢复 |
| --- | --- | --- |
| 模型 HTTP 400、401、403、404；配置、规则和输入错误 | 立即失败，不自动重试 | 修复配置后按当前快照重新评审 |
| JSON/schema 不兼容、输入 SHA 或覆盖集合冲突 | 立即失败，保留工件 | 核对 OCR 版本及适配代码 |
| 连接瞬断、HTTP 429 或可重试 5xx | 最多两次完整尝试，即额外重试一次；退避加入抖动，在预算内尊重 `Retry-After` | 连续失败后检查服务状态 |
| 正式评审用尽整体预算、超大范围被拒绝 | 默认不整批自动重跑 | 调整范围治理或预算，明确确认后重评审 |
| 用户取消、版本失效、项目删除 | 不重试 | 沿用现有对应操作流程 |
| 未识别错误 | 保守失败，不因基类是 `RuntimeError` 自动重试 | 带关联 ID 诊断 |

OCR 内部请求重试与平台整批重试须同时记录，避免两层相乘。配置内部重试前核对实际安装版本支持；不假定平台能直接控制所有 OCR 内部重试。

主要涉及：`ocr.py`、`worker.py`、`storage.py`、`attempt_history.py`、`premerge.py` 及相应测试。共享 OCR 入口的改动要同时验证合并后与合并前评审，后者的最新版本校验和取消语义不变。

验收标准：

- 合成 HTTP 404 + `comments: null` 结果保持 `failed`，可见 HTTP 404，保存完整失败尝试，不再出现二次 `TypeError`。
- 429/5xx 的允许重试、退避与次数边界可用受控时间验证；404、schema 冲突和整体预算耗尽不整批自动重试。
- 模拟挂起进程能在预算及终止宽限内退出，脱敏日志存在，没有残留子进程和重复投递。

### 第二阶段：输入治理和预算保护

**当前状态：**已按下述第 6 项降级路径交付严格分析与限额保护。OCR 简单相对路径在合成预览可排除，但任意路径及正式 manifest 一致性未验收，自动过滤关闭；未修改生产 `max_files` 或 Token 参数。

**目标：**尽早拦截上千文件的异常范围，避免纯换行文件消耗模型额度。

先完成 OCR 兼容性验证，再启用换行过滤：

1. 核对部署的固定 OCR 版本，确认范围预览、路径筛选、排除规则和 manifest 的实际行为；只使用已验证的入口，不预设存在某个 CLI 参数。
2. 预检从原始 base/head 读取变更路径与文件内容，分别记录原始范围、OCR 候选范围和策略排除范围。
3. 纯换行判定只将 `CRLF` 转为 `LF` 后做精确字节比较，不忽略其他空格、缩进、大小写或编码差异。必须排除新增、删除、重命名、类型和执行权限变化；二进制、符号链接、子模块及读取失败均不据此免审。
4. 为预检设置文件、字节和时间上限，不把千文件比较变成新的无界任务。无法确认时保持纳入或因规模限制明确失败，不猜测豁免。
5. 如实际 OCR 能安全排除这些路径，预览与正式评审必须使用同一份冻结策略；校验实际选中集合与预期集合一致，并原样保留 OCR manifest。
6. 如 OCR 不支持可靠排除，首版只展示换行分析和超限提示，不伪称已经减少模型输入，不擅自改写仓库规则或 manifest。该能力阻塞项单独登记。

对于“同一文件既转换换行又修改逻辑”的情况，首版仍纳入评审，不承诺消除该文件内部的全部换行噪声。全范围仅有纯换行时，也必须确认不存在其他需审查的变更后才能按已启用策略跳过，并明确说明未调用模型。

覆盖展示保留两层：原始变更与策略排除的范围说明，以及 OCR 实际选中文件的覆盖结果。只完成过滤后的范围时使用“按策略完成，存在排除”，不能宣称原始所有文件都经模型审查。

预算保护：

- 优先复用现有项目级 `timeout_seconds`、`max_files`、`max_tokens_budget`，不把已有 UI 和能力重新实现一遍。
- `max_files` 首版仍是正式 OCR 选中范围的上限，不是“只评审前 N 个文件”。超过上限以 `failed` 结束，附带明确的规模超限类别和人工操作建议；首版不新增 `needs_attention` 任务状态。
- 若准备引入变更行数、差异字节上限，增加独立配置、快照和迁移；不能把未实现的字段作为现有功能配置。
- 配置阶段建议整体上限 30 秒，范围预览建议 60 秒，均受本次任务总预算约束；冷启动 Git clone/fetch 单独设有界预算并展示，不混为模型超时。
- 正式评审超时按项目和规模配置。首轮可用 Web 项目 `max_files=200` 作为试点候选，超时先保持原项目设置，通过输入治理和不盲目重试先止损；这不是自动修改生产参数的指令。
- Token 预算用代表性成功任务的输入、输出及成本校准，试点必须填写有限值；数值在采样后记录，不凭单个任务给所有项目统一套用。OCR 预算若仅在请求边界检查，应明确并发在途请求可能带来超额，不能宣称是精确费用硬上限。

主要涉及：`git_repo.py`、`ocr.py`、`project_limits.py`、`worker.py`、配置快照及规则预览页面；预检建议新建独立模块，避免继续扩大现有大文件。

验收标准：

- 合成批量 CRLF/LF 转换不进入模型；混有逻辑修改的文件仍被选中，权限、路径和文件类型变化不被当作纯换行遗漏。
- `max_files=200` 时，201 个实际选中文件在模型调用前失败；不能截取前 200 个后报告完成。
- 不支持可靠过滤的 OCR 版本明确禁用该优化，仍有规模拦截，不回退到不安全的参数或改写提交。
- 固定 SHA、规则优先级、快照幂等、部分覆盖和配置变化后的重评审均有自动化回归。

### 第三阶段：耗时、原因和成本可追溯

**当前状态：**合并后列表、详情、逐次报告和近七天分组已本地实现并回归；旧数据未知不回填，生产指标改善尚未验证。合并前逐次数据库历史表未纳入本轮。

**目标：**列表可以直接解释“等多久、跑多久、为什么失败或跳过”。

统一时间口径：

| 指标 | 定义 |
| --- | --- |
| 首次排队时长 | 首次尝试开始时间减任务创建时间；未开始任务显示当前等待时间 |
| 本次或最后一次执行 | 当前尝试开始至当前时间，或最后一次尝试的开始至结束 |
| 累计执行时长 | 所有已结束尝试耗时之和；运行中加当前尝试，避免重复计入 |
| 重试退避时长 | 上次尝试结束至允许再次领取的时间段，终态不计虚设的下次运行时间 |
| 重试就绪后等待 | 允许再次领取后至实际领取的时间，不与退避重叠 |
| 总历时 | 创建至当前时间或最终结束时间，包含排队、执行和重试间隔 |

当前和历史 `next_run_at` 不足以恢复所有过去退避区间。新增逐次调度时间记录；缺失的旧指标显示“未知”或“部分历史可计算”，不能用零代替或用总历时简单冒充执行时间。

实施内容：

- 复用 `review_attempts.started_at/finished_at`，补充必要的错误类别、调度时间和阶段计时；API 明确区分当前尝试与历史尝试，时间由服务端按 UTC 计算。
- 列表主文案展示状态原因和累计执行，辅助展示排队或总历时；详情给出逐次开始、结束、阶段、错误和重试决定，避免在窄屏塞入更多横向列。
- 跳过显示“空差异”“配置目录被排除”“仅换行变化”等原因；失败、取消或跳过不能统一用“0 条发现”暗示已完成无问题。
- 优先实现稳定的原因码与中文映射，未知码有可诊断兜底；不直接把原始工件暴露给列表。
- 重试成本尽可能汇总各次可信用量，历史尝试没有用量则标记成本不完整；保留原有单价快照，不用当前价格重算旧任务。
- 运维指标按项目、规模和状态拆分，统计成功执行及排队 P50/P95、超时率、整批重试次数、输入规模、Token 和未知用量数量；跳过耗时不混入正常模型评审均值。
- OpenAPI 快照、前端类型、报告导出与历史尝试对比同步更新，保留旧接口字段兼容路径。

主要涉及：`tasks.py`、`storage.py`、`attempt_history.py`、`monitoring.py`、`model_pricing.py`、前端 API 类型及任务列表、详情和运维页面。

验收标准：

- 三次各一小时的合成记录展示累计约三小时，最后一次约一小时；排队六小时但执行一秒的任务不混淆两者。
- #372 类场景可查看第一次完成与第二次取消，不以最后状态覆盖历史报告。
- 历史字段缺失、运行中、退避中和取消时的时间计算有测试；列表查询不为每行单独读取工件或发起数据库查询。
- 桌面和 390/320 像素窄屏可读，状态原因不依赖鼠标悬浮才能获取。

### 第四阶段：按指标决定调度解耦

**启动条件：**前三阶段通过，试点仍存在明显的轻量任务或跨仓库排队，并且模型额度、限流与机器资源有余量。

2026-11-06 按用户授权先实施本地单模型槽版本：通知、事件与评审有界解耦；尚无真实试点吞吐和 P95 数据，不据此提高模型并发。实现、隔离验收及本机生效边界见[第四阶段实施记录](review-performance-phase4.md)。

建议架构：仍由单一协调 Worker 负责 SQLite 领取和调度，将长时间 OCR 执行交给受控执行单元；先保持 OCR 总任务并发为 1，让通知、事件和预检在有界配额下获得调度机会，再评估提升到 2。不能简单启动第二个现有 Worker。

必须补齐：

- SQLite 原子领取、执行身份、心跳或租约及崩溃恢复；不因协调器重启把存活 OCR 当成新任务重复运行。
- 仓库 fetch、worktree 和工件锁，与项目删除、清理、取消、预审失效协同。
- 同仓库事件、同 MR 的评审顺序与跨仓库公平；合并前审查、补审、连接诊断也受配额约束，不能永久饿死某类任务。
- 可以提前计算后续任务的预览，但是否提前结束跳过任务要明确顺序语义；首版不以优化为由让后续任务静默越过前序评审。
- 每个执行单元使用独立 SQLite 连接，OCR 期间不持数据库写事务；通知和发布保持独立幂等。

新增验收包括并行领取、租约恢复、进程组终止、项目删除、清理竞争、重复通知和公平调度。有限并发的提升必须用实测吞吐和 P95 支撑，不能只证明同时启动了两个进程。

### 后续能力：分批与续审

只有在实际 OCR 版本能可靠指定路径子集、固定输入、恢复会话和生成可信覆盖时才推进。父任务保持原始 SHA 和策略快照，批次结果必须验证覆盖集合互斥且并集完整，聚合发现、用量和失败；未完成批次仍为 `partial` 或 `failed`。

不把“日志中存在 session ID”当成已验证支持断点续审，也不在本轮承诺可以恢复现有超时任务。该能力需要单独的数据模型、幂等、版本兼容和成本验收。

## 5. 实施安排与交付物

按一名开发者连续投入估算，开发日包含编码和隔离回归，不含外部服务排障、等待审批及试点观察，不是自动执行排期。

| 阶段 | 工作量估算 | 依赖 | 交付物 |
| --- | --- | --- | --- |
| 第一阶段 | 1～2 个开发日 | 无 | 结果兼容修复、分类重试、超时工件、自动化用例 |
| 第二阶段 | 2～4 个开发日 | 第一阶段；OCR 筛选能力验证 | 范围预检、策略快照、限额保护、试点参数和兼容结论 |
| 第三阶段 | 1～2 个开发日 | 第一阶段字段口径；第二阶段原因码 | 列表与详情、累计耗时、指标、报告和接口更新 |
| 首版合计 | 4～8 个开发日 | 第一至第三阶段 | 可独立发布的稳定性与可观测性版本 |
| 第四阶段 | 额外 3～5 个开发日 | 首版试点数据与架构评审 | 轻重任务解耦、恢复与并发回归；默认不提高 OCR 并发 |
| 分批与续审 | 能力验证后单独估算 | OCR 支持及聚合模型设计 | 单独方案，不纳入首版工期 |

每阶段单独提交、单独验收，不把不同风险的改动捆成一次生产切换。第二阶段若发现 OCR 无法安全过滤，先交付预检报告和规模保护，过滤功能保持关闭并重新估算，不以改写 SHA 的方式赶进度。

## 6. 自动化验证与工程检查

新增测试使用合成 OCR、GitLab 和飞书响应、临时 Git 仓库和临时 SQLite。只读取历史工件进行本机只读复核，不把真实代码、模型推理、密钥或原始响应复制进测试夹具或 Git。

每项实现至少覆盖以下风险：

- 结果：`comments` 缺失、`null`、空列表和错误类型；有效失败、部分覆盖、冲突 manifest 和失败摘要脱敏。
- 重试：404 不重试，429/5xx 有界重试，整体超时不盲目重跑，内部重试与整批重试可区分，重启不重置预算或丢失尝试。
- 范围：纯换行、换行混合逻辑修改、缩进变化、无末尾换行、增删/重命名、权限变化、二进制、子模块、空差异和文件上限。
- 生命周期：取消、预审失效、项目删除、配置变化、重复 webhook、通知失败独立重试和历史成功后取消。
- 数据与界面：空库与代表性旧库迁移、字段未知、逐次时间与成本汇总、分页性能、只读权限和窄屏布局。

## 7. 灰度、历史任务和回滚

1. 实施在隔离测试数据中完成。上线前确认部署的 OCR 版本，对 SQLite 和私有主密钥配置做成对备份，并在副本验证迁移与恢复。
2. 先发布第一阶段修复；生产 Worker 的停止或重载安排在没有活动 OCR 时，若需中断由管理员确认。API 和 Worker 的变更兼容顺序在迁移测试后确定。
3. 第二阶段先以只分析、不排除的模式观察一个测试项目，再启用已验证的过滤与有限预算。策略、阈值、实际 OCR 版本和配置摘要进入任务快照。
4. 排队中的旧快照不被原地改写。配置变化按既有机制处理旧任务并由管理员选择按新配置重评审，不能批量改数据库来绕过校验。
5. 第一至第三阶段完成后，观察 3～7 天或累计足够的代表性任务；记录样本数及冷启动、模型故障等条件，样本不足时不宣称 P95 已稳定。
6. 历史 #366/#369 不自动再次执行；待过滤和预算通过后，由管理员确认是否生成新策略任务。#360/#361 只在模型连接确认后人工重评审，不篡改旧错误和原始工件。
7. 过滤异常时关闭新策略，只影响之后创建的快照；已经执行的记录保留并可追溯。并发试点回退到 OCR 并发 1，不删除租约和尝试证据。
8. 数据库优先采用向前兼容的增量迁移。若必须回退到不兼容旧代码，先停相关进程，在新目录恢复配对备份并核对切换后新增业务记录的补偿方案；不得直接覆盖活跃 `app.db` 或丢弃上线后的记录。

## 8. 首版效果判定

首版必须满足的正确性目标：

- 失败原因不再被空评论异常覆盖，跳过、失败、取消和完整成功不混淆。
- 千文件异常范围在模型调用前被限额保护，纯换行过滤只有通过版本与范围验证后才启用。
- 同一整体超时任务不再默认整批执行三次；未知费用明确标记未知。
- 可以解释每个任务的排队、执行、重试和总历时，旧数据缺口如实披露。
- 原始提交范围、配置快照、覆盖、鉴权、取消、通知幂等和历史结果没有回归。

改善幅度通过相同规模、相同模型和策略条件下的合成基准及试点数据比较，记录过滤前后选中文件数、实际 Token、失败率与排队 P95。当前不承诺固定的成本下降比例，也不承诺单 Worker 下所有跳过任务都能立刻结束；持续的调度阻塞由第四阶段解决。
