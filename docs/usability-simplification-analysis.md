结论区分“源码确认”“本机页面观察”和“建议方案”。已有规划的历史状态不直接作为当前事实；本机发布页面与当前源码也不能默认完全一致。本轮临时检查输出和截图位于 `/tmp/ocr-ux-analysis-20261110`，不将其中的项目内容、地址或配置详情复制进本文。

## 核心判断

当前项目已经有列表筛选、URL 定位、窄屏摘要、配置分区、草稿保护及独立通知重试等基础。最有价值的改进是收拢使用路径、降低首次接入门槛，并让用户在每一步都清楚“现在是什么状态、下一步做什么”。

优先处理接入引导的完成条件、仓库重复填报、模型与通知测试入口，再精简导航和信息密度。延续现有灰白蓝视觉和 Ant Design 采用规则即可。

## 已确认的主要问题

### 1. 接入引导缺少可以走完的路径

- 源码确认：接入进度只由四项计算，最后“验证连接”固定 `done: false`，因此最多达到 4/5。当前保守处理是因为模型、飞书测试未关联当前配置版本，不能直接改为历史测试通过即完成。
- 源码确认：三个后续步骤都跳到项目列表，没有携带目标项目和编辑分区；用户到达后还要自行寻找入口。
- 源码确认：Webhook 完成项要求所有已启用项目都有历史接收记录，新增项目可能使全站引导重新显示未完成，不能清楚表达哪个项目卡住。
- 源码确认：仓库允许“暂不关联”飞书，但引导把飞书配置列为固定完成项，缺少“本项目不需要通知”的完成语义。
- 建议：区分一次性的“平台准备”和逐项目的“接入清单”；只显示当前项目的下一步。通知按实际选择成为可选项，完成项分别依据已保存配置、当前版本连接验证和真实业务记录判断。
- 建议：后端补齐测试目标与配置版本关联后，再定义真实完成条件；证据不足时展示具体待核实项。用户明确试评审时才产生模型调用，展示费用和外部通知影响。

证据：`frontend/src/pages/OnboardingPage.tsx:31`、`frontend/src/pages/OnboardingPage.tsx:32`。

### 2. 添加仓库要求用户重复整理已存在的信息

- 源码与页面确认：创建表单包含仓库名称、项目数字 ID、仓库路径、目标分支、Clone URL、GitLab Token、飞书配置及两个事件开关。
- 其中名称、路径和 Clone URL 相关，项目 ID 和分支通常还要回 GitLab 查找；字段并列出现，没有“先粘贴地址、再补充信息”的顺序。
- 建议：首先填写仓库地址和访问令牌，经管理员显式操作，由受控后端查询项目元数据，带出名称、数字 ID、路径和默认分支，允许核对修改。失败保留现有手动填写路径。
- 建议：事件类型优先提供“合并后评审”“默认分支提交评审”的中文业务说明；高级参数在创建后按需配置。
- 实施边界：元数据获取需要独立读取契约与主机、权限和凭据保护，不能仅从 URL 猜测数字 ID，也不能把令牌交给浏览器直接请求 GitLab。不得把简化表单等同于扩大凭据共享范围。

证据：`frontend/src/pages/RepositoriesPage.tsx:224`。

### 3. 模型保存、测试与启用的顺序增加理解成本

- 源码与页面确认：新增模型同时展示 Provider、Base URL、API Key、模型标识和计价字段；较长窗口需要滚动才能看到后续字段和保存操作。
- 源码确认：允许保存不完整信息，保存后提示到列表启用；连接测试只针对当前全局已启用模型，无法从目标配置直接完成“先验证、再作为默认模型”的路径。
- 页面观察：桌面配置名称列被长端点和计价列挤压，模型标识出现频繁折行；三个配置也需要先扫完整张表才能比较。
- 建议：基础区只保留显示名称、服务商或兼容协议、API Key 和模型；自定义端点及计价按需展开，现有自定义端点必须明显可见、可编辑。
- 建议：增加针对目标配置版本的测试，成功后再提供“设为全局默认”；区分保存草稿、配置完整、测试结果、全局默认和项目指定使用。未全局启用不能直接解释为没有项目在使用。
- 建议：列表优先展示名称与模型、使用情况和最近验证；完整端点、价格详情移入展开区。计价未配置继续显示未知费用，不按零处理。

证据：`frontend/src/pages/SettingsPage.tsx:57`、`frontend/src/pages/SettingsPage.tsx:123`、`frontend/src/pages/ProjectReviewLimits.tsx:16`。

### 4. 飞书通道测试依赖仓库关联，首次配置容易绕路

- 源码确认：测试入口只在编辑现有通道且找到关联仓库时出现；新增通道窗口没有测试入口，未关联仓库的通道编辑窗口也不显示测试。
- 用户因此要先保存通道、去项目中关联，再回通道编辑测试，与首次引导“先配置飞书”的顺序不连贯。
- 建议：通道保存后提供该通道的独立测试入口，以及“关联项目”的明确下一步；列表直接展示最近测试状态和时间。
- 实施边界：需要支持通知目标身份的后端测试契约，由 Worker 执行；显式说明会向真实群发送测试消息，不能打开页面就自动发送。
- 后续兼容：若实施应用机器人，通知设置先选择接入类型，再显示对应字段；应用凭据集中管理、项目复用通知目标。此能力仍属于 PI-20261110-002 的后续方案，本轮没有接通。

证据：`frontend/src/pages/FeishuHooksPage.tsx:99`、`frontend/src/pages/FeishuHooksPage.tsx:132`。

### 5. 导航把使用频率不同的功能放在同一层

- 源码与页面确认：管理员侧栏有 12 个入口，分别属于工作台、运维与审计、接入配置；只读角色当前仅展示工作台组。
- 日常使用者主要查看任务和发现，首次引导、配置历史等低频页面长期占据固定位置；“评审发现”和“问题与改进”也需要额外解释所属对象。
- 建议：按日常评审、项目接入和平台管理重排，先减少固定露出的低频入口。保留路由、深链接和原有角色可读能力；移动合并事件不能使当前可访问它的只读用户丢失入口。
- 建议：“问题与改进”明确为“平台改进记录”；对当前维护者若属于高频功能，保留固定或收藏入口，不因其他用户低频就一律隐藏。

证据：`frontend/src/app/App.tsx:37`、`frontend/src/app/App.tsx:114`。

## 建议的菜单结构

建议从 12 个固定入口收拢到约 7～8 个，具体取决于是否保留平台改进快捷入口；这是一种推荐结构，不是必须追求的数量指标。

| 一级入口 | 主要内容 | 迁移说明 |
| --- | --- | --- |
| 工作台 | 当前待反馈、异常、正在运行和最近评审摘要 | 保留现有反馈统计与项目时间范围；趋势分析按需展开。 |
| 评审任务 | 任务列表、合并前审查入口、事件记录次级入口 | 高频使用合并前审查时，保留其独立菜单，避免增加步骤。 |
| 评审发现 | 当前发现、反馈、历史问题与修复记录入口 | 继续复用统一反馈集合，保留历史修复事实。 |
| 项目配置 | 项目列表、项目接入清单、评审参数、接入诊断 | 仍为管理员能力；不因名称缩短而扩大权限。 |
| 系统设置 | 评审模型、通知通道、审核规则、访问权限、接入帮助 | 规则维护和用户管理保持独立分区与权限校验。 |
| 运行监控 | 现有四分区、配置历史及平台改进次级入口 | 不把所有工具塞进同一个默认屏幕。 |

上述表格按合并前审查是否单列、平台改进是否固定，形成约 7～8 个实际侧栏入口。首次接入完成后，把引导收进项目接入和帮助；新用户或未接通项目仍显示醒目的引导提示。合并事件、配置历史与平台改进保持可检索、可直接打开。

## 配置还应分清的三个层级

1. **部署配置**：入口地址、数据目录、认证模式、OCR 可执行文件等由运维维护；主密钥不在普通页面回显。现有运行监控已能核对部分生效地址，不另建重复设置。对仍分散的信息补脱敏只读摘要，说明改动是否需重启及尚未核实的状态。
2. **平台共用配置**：模型、通知目标和全局规则由管理员集中维护；用户从已保存配置中选择，避免每个项目重复录入相同内容。
3. **项目覆盖配置**：继承全局作为常规路径，覆盖项展示实际值和来源。仓库规则文件与页面规则按既有优先级解释，不能简单说全部合并生效。

尤其需要区分 Worker 的“同时运行任务数”与 OCR 的“单任务内部并发”，以及保存、已应用、测试通过和真实评审完成四种事实。提示应就近解释用户当前要作的决定。

## 推荐实施顺序与验证目标

| 批次 | 范围 | 主要收益及验收目标 |
| --- | --- | --- |
| 第一批：路径和文案 | 菜单低频入口收纳、准确保存按钮、目标项目/分区定位、下一步提示、列表与详情信息折叠。 | 功能仍可发现，旧链接和权限不退化，草稿及筛选返回保留；成功任务减少无关阅读，异常恢复仍醒目。 |
| 第二批：接入闭环 | 仓库元数据获取、逐项目引导、目标模型/通知测试、配置版本与测试结果关联。 | 使用新项目可走完接入；当前配置未验证时明确指出原因，通知可选择跳过；测试不会替换线上默认或无提示外发。 |
| 第三批：配置管理 | 实际生效配置摘要、项目继承与覆盖说明、后续通知接入类型。 | 能回答正在用哪个模型和规则、为什么生效、修改影响哪些后续任务；应用机器人只在独立实现与联调后宣称可用。 |

第二、三批包含后端契约及权限、凭据、版本和异步测试语义，工作量高于纯页面调整，应独立实施与自动化验证。不能用隐藏字段或一键跳转代替这些能力。

后续实施建议用四个实际任务验证：新人接入一个项目；日常找到并反馈一条发现；管理员定位一次通知失败并独立重发；管理员确认某项目正在使用的模型、规则和参数。记录完成率、页面切换、填报次数和用时，以改造前后相同条件比较。本轮没有招募真实用户或测量这些指标，不宣称已缩短任何比例的用时。
