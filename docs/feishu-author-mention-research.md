# 飞书评审卡片按提交人提及方案

调研日期：2026-11-10（北京时间）。关联台账：PI-20261110-004；关联应用机器人研究：PI-20261110-002。本轮为源码与公开资料分析，未实现、未部署、未实发消息。

## 1. 结论与推荐

可以在评审卡片中生成真实的 @ 提及。当前群自定义机器人支持通过有效的 `open_id` 或 `user_id` 提及所在群的成员，不要求为了提及本身迁移到应用机器人。普通 `@姓名` 文本不等于真实提及。

建议分两阶段：先保留现有 webhook，增加管理员维护的提交身份与飞书成员映射；若后续实施原卡状态同步，再统一接入公司持有的应用机器人，补自动解析与缓存。两阶段复用同一身份映射和通知策略，不重复配置每个仓库的每个成员。

## 2. 当前项目的事实

- `backend/ocr_manager/git_repo.py` 的 `commit_author` 使用 `git show -s --format=%an`，只取得作者姓名。
- `backend/ocr_manager/worker.py` 将姓名写入 `review_jobs.commit_author`；当前没有可供此链路使用的作者邮箱或 GitLab 用户 ID 到飞书成员的映射。
- `backend/ocr_manager/feishu.py` 的 `build_review_card` 在普通文本区域显示提交人，`_plain_section` 使用 `plain_text`；当前不会解析 @ 标签。
- 发现内容继续用 `plain_text` 是现有的可信输入边界。不能为了 @ 把全部发现、代码或作者姓名改成任意 Markdown。
- 仅有目标 SHA 的姓名不足以表达多作者 Push 范围；merge commit 作者也可能是执行合并的人。MR 作者、提交作者、推送人、合并人必须分开定义。

## 3. 两种路线

| 路线 | 配置与实现 | 适用与限制 |
| --- | --- | --- |
| 现有 webhook + 人员映射，第一阶段推荐 | 管理员录入经核对的 GitLab 身份或提交邮箱与飞书 ID，Worker 匹配后在卡片单独加入提及区域 | 改动较小，无需自动读取通讯录；需要由有权限的人取得 ID 并验证目标成员在群内 |
| 应用机器人 + 自动解析，长期推荐 | 公司应用身份发送，配置权限后通过已确认的用户邮箱查询 ID、缓存并允许人工覆盖；可和原卡反馈同步一起实施 | 有应用发布、数据可见范围和权限成本；邮箱必须对应飞书用户邮箱，查不到时仍需映射兜底 |

卡片中单独的提及区域可采用官方旧版卡片示例结构：

```json
{
  "tag": "div",
  "text": {
    "tag": "lark_md",
    "content": "请查看本次评审：<at id=ou_example></at>"
  }
}
```

`ou_example` 仅为占位符。实际 ID 只能来自经校验的映射，不从发现文本或用户输入中拼接标签。标题和其他普通文本结构无需改变。

## 4. 身份和匹配规则建议

1. **明确通知责任人**：建议 MR 默认通知经 GitLab API 确认的 MR 作者；普通提交模式可选提交作者；多人 Push 根据实际 `before..after` 范围去重提取作者，超过人数上限时使用显式配置的项目负责人或显示成员列表。是否提及所有作者由管理员选择，不静默只取最后一次提交。
2. **先稳定身份，后邮箱别名**：GitLab 身份以实例地址和数字用户 ID 为键；原始 Git 提交没有天然可信的 GitLab 用户 ID，未关联时按管理员核对的精确提交邮箱映射。一个人可配置多个提交邮箱，避免不同机器和 noreply 地址造成漏配；禁止按同名或邮箱前缀模糊匹配。
3. **限定飞书身份作用域**：保存租户或通知域、ID 类型、取得 ID 的应用身份及映射来源。`open_id` 随应用变化，`user_id` 随租户变化，不当成跨应用、跨租户通用标识；更换发送应用后重新解析或验证。当前 webhook 所在群内的实际可用性须在授权测试群确认。
4. **自动查询需要显式接入**：使用 `POST /open-apis/contact/v3/users/batch_get_id`，传 `user_id_type=open_id`，申请 `contact:user.id:readonly` 并配置所需用户的数据可见范围。官方明确该接口不支持企业邮箱字段，必须是用户邮箱；不能假设 Git 提交邮箱或公司邮箱一定可查询，不为此自动申请全量通讯录权限。
5. **人工覆盖优先且可审计**：映射仅管理员维护，显示生效目标、来源与最后验证情况；重复映射、未知或失效目标应提示。Git 作者姓名和邮箱可自行填写，映射只用于通知，不用于登录、权限、归责或自动修改发现。

## 5. 使用体验与发送规则建议

- 在通知设置中提供默认关闭的“按提交身份 @ 成员”，复用集中成员映射；项目仅覆盖策略，避免每个项目重复录入人员。
- 第一阶段建议默认“有发现时 @”，并允许选择最低严重级别和全量评审通知。完整零发现不提及；执行失败或覆盖不完整可单独通知配置的维护人，避免混同开发者处理职责。
- 映射缺失、冲突或成员离群时保留普通提交人说明，并在管理页显示未匹配或待验证原因；不自动 @所有人。群内显示姓名不证明真实提及生效，用户侧提醒还受飞书设置影响。
- 在初审卡、补审卡和未来动态进度卡中分别规定提醒策略；同 MR 多提交按窗口聚合，避免每条发现都 @。更新原卡是否再次触达不能凭推测作为可靠提醒手段。
- 通知意图与解析结果持久化，Worker 处理解析、发送和重试；HTTP 接收端不调用飞书。重试复用同一投递的目标快照，保留后续人工修正后的显式重发能力；超时仍可能产生外部重复消息，不宣称 webhook 绝对幂等。
- 若飞书因无效提及拒绝整张卡，可根据明确错误记录降级并有限重试普通摘要；网络超时不能直接视为无效成员，不能无限补发。评审和反馈业务不因提及失败而回滚或重新消耗模型。

## 6. 后续实施与验收范围

实施需增加持久化成员映射、作者身份事实、通知策略与解析快照，并更新配置接口、Ant Design 配置界面和 Worker。初审与补审均需覆盖；旧任务缺少身份时显示未知，不把历史姓名猜测成成员。

相称自动化覆盖精确匹配、邮箱别名、同名不同人、多租户与应用作用域、MR 合并人差异、多作者 Push、映射缺失、离群、限流、超时、重复投递与补审提醒。真实联调须在用户明确授权的测试群内核对 @ 对象可点击及实际触达；本轮未做此验证。

## 8. 只按名字操作与底层身份的区别

用户不必手动查找或输入飞书 ID，但当前自定义机器人发送真实提及时必须使用有效的 `open_id` 或 `user_id`，不能将姓名当作 ID。手打 `@姓名` 仅为普通文本；飞书客户端输入姓名后选择候选成员的操作，实际也会绑定成员身份。

产品可以设计为“搜索姓名并选择飞书成员”，后台保存对应 ID。此体验需要有权限的应用获取所需范围的成员信息，或已有经管理员核对的人员目录；现有 webhook 本身不能查询群成员。重名时展示可区分的账号信息，由管理员确认，不自动取第一个；候选目录和匹配规则不等于已经实现。

若团队约定 Git 作者姓名一致，也可以在首次确认后维护“提交姓名别名 → 已绑定飞书成员”的规则，适用范围应限定到仓库或 GitLab 实例，并在重名或冲突时停止自动匹配。更稳妥的自动关联仍使用 GitLab 用户身份或经过核对的提交邮箱；姓名用于搜索和展示。核心体验应是“只选人，不填 ID”，而非把后台标识的维护负担交给使用者。
