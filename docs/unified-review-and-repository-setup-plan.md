# 统一评审任务与仓库接入改造方案（重新规划）

日期：2026-11-13。事项：PI-20261113-007。状态：完整实施及本机配套发布完成；真实 GitLab 业务事件和飞书送达不在本轮合成验收结论内。

本文替代此前同名规划的方案正文。需求依据是用户四项改造要求及补充澄清：**同一 MR 的同一版本已经触发合并前任务，合入目标分支时复用该任务；其他 Push 正常审查。** 本文记录已实施的目标和验收约定；当前操作方式见配置指南，实际部署证据见台账。

后续变更（PI-20261113-009，schema 54）：仓库配置改为合并前 MR 与目标分支 Push 两种自动触发，旧合并后 MR 订阅迁至 Push；新增、编辑目标分支支持远程搜索多选，合并前开关统一到基础接入。以下三个选项与单分支示意保留为 53 版实施历史，当前用法以[配置指南](configuration-guide.md#3-新增仓库)及[54 版迁移说明](deployment.md#多分支与触发配置升级54-版)为准。

## 2. 页面与交互

### 2.1 设计方向

使用者是接入 GitLab 项目并查看评审结论的开发者和项目管理员。页面首要任务是看清“哪个版本正在审查、结论是否完整、飞书是否送达”。

- 业务词汇：MR、目标分支、代码差异、版本、覆盖范围、发现、触发事件、投递。
- 色彩来源：代码阅读界面的白色内容面、灰色元信息、蓝色链接与运行提示、绿色完成提示、橙色部分覆盖提示、红色失败提示。颜色必须配文字，不只依靠颜色区分状态。
- 特征交互：任务详情中用一条触发时间线表达“MR 创建 → 本次版本评审 → 合入目标分支 → Push 关联原任务”，解释为什么只审了一次。
- 需要避免的默认做法：各来源各建菜单改为统一列表来源筛选；给每个事件一张任务卡改为同任务关联时间线；让用户手工维护项目身份改为后台识别。
- 延用项目主题、字体和间距变量。任务与结果优先展示；短 SHA 等定位信息使用既有等宽样式；不增加装饰性统计卡。新设计的通用控件统一使用 Ant Design。

### 2.2 评审任务

移除“合并前审查”导航，保留“评审任务”。现有查询、分页和返回位置继续可用，增加来源筛选：全部／合并前 MR／合并后 MR／目标分支 Push。

列表沿用现有布局，补足来源、MR／版本和飞书状态。任务状态与 MR 生命周期独立：例如“运行中 · MR 已合并”是合法组合，“已合并”不能替代“评审完成”。每个任务只占一条记录，关联的 Push 不生成另一条假完成任务。

详情沿用现有结果、问题反馈、覆盖、日志、费用、报告、重试及补审入口，增加版本和触发记录。用户能看到“Push 已关联任务 #123，未重复评审”和原任务实际结论。人工重试是同任务的新尝试；代码或实际审查输入更新形成新版本任务。旧版本和费用保留，当前有效发现避免重复统计。

旧菜单地址重定向到来源筛选；历史合并前详情通过旧 ID 到新任务 ID 的映射跳转，不能直接拿相同数字定位普通任务。首页、统计、监控和飞书链接同步调整。

### 2.3 新建与编辑仓库

表单按三组组织，新增和编辑共用字段结构、校验及分支搜索能力：

| 分组 | 展示字段 | 交互 |
| --- | --- | --- |
| 仓库连接 | GitLab 项目或 HTTPS Clone 地址、GitLab Token | 输入完整后自动识别；提供重新获取入口；识别失败保留草稿 |
| 评审设置 | 目标分支、三个触发选项、按需展开的审查背景 | 分支可搜索；背景保留现有描述与文档配置能力 |
| 通知设置 | 飞书配置 | 从已有通道选择；未配置时明确提示无法发送飞书 |

名称、项目数字 ID、仓库路径和 GitLab 实例地址不再作为新增／编辑表单字段。后台仍保存这些身份数据；仓库列表继续显示名称，编辑标题继续帮助识别当前项目。


“默认分支提交评审”改名为“目标分支 Push 评审”，与选择 test 等非默认分支一致。编辑时 Token 留空使用已保存凭据；远程加载失败保留已保存分支，不自动切换默认分支。改变仓库主机时要求新输入 Token，不把旧凭据自动发送到新主机。

## 3. 触发与去重的明确规则

### 3.1 自动触发前提

平台启用项目及合并前审查，GitLab Webhook 配好平台回调地址和项目 Secret，并勾选 Merge request events；MR 的目标分支匹配项目设置，Worker 和仓库访问凭据可用。满足这些条件后，MR 新建、重新打开或更新会触发版本核验和入队。仅打开平台开关不能代替 Webhook 配置；已有未产生新事件的 MR 不自动全量补扫，保留手动触发入口。

需要直接提交评审时额外勾选 Push events。这里的合并前评审提供反馈；本次不新增 GitLab 强制合并门禁。草稿 MR 沿用当前触发语义，本轮不额外引入草稿过滤规则。

### 3.2 场景决策表

| 场景 | 处理规则 |
| --- | --- |
| MR 版本 V1 已有合并前任务，V1 合入目标分支 | Push 和已启用的合并事件关联原任务，不重复执行初审或建立初审通知 |
| 原任务排队／运行时合并 | 同版本任务继续执行；MR 已合并不能单独成为失效或取消理由 |
| 原任务完整完成 | 复用结果，保留执行时间、费用、发现和反馈 |
| 原任务失败／部分／取消／跳过 | 关联原任务并保留实际状态；Push 不隐式重跑，不将其标为已审通过；重试或补审仍走原任务入口与既有策略 |
| V1 审过，后来提交 V2 | V2 是新版本；V1 不能替代 V2，优先关联 V2 的合并前任务；没有则按相应已开启的合并后／Push 配置评审 |
| 开启合并前开关，但这个 MR 没有对应版本任务 | 正常按已开启的事件配置评审，不能仅凭项目开关跳过 |
| 直接 Push 到目标分支 | 正常评审 |
| 一次 Push 包含已审 MR 和其他新增代码 | 只复用有充分证据的范围，未审代码继续评审；不能按文件名排除 |
| 普通 merge、fast-forward、squash、rebase | 核验实际版本和范围后决定；不能仅比较一次 SHA 或 MR 编号 |
| 重复投递、事件乱序、Worker 重启、并发到达 | 依赖数据库关联和唯一约束复用任务，不依赖前端防重 |

去重的目标是避免相同输入由自动事件重复执行。人工重试、补审仍会增加真实执行次数和费用。配置改变或描述等实际输入变化继续遵守既有版本失效策略；Push 关联不额外引入另一套配置重审规则。实施时统一版本判定和合并后终态处理，防止隐式重复入队。

### 3.3 无法确认范围时怎么办

Worker 先查持久化关联，再核验 GitLab 和固定 Git 范围。短暂 API 不一致先有限重试；初始建议最多等待约两分钟，间隔与超时纳入统一调度配置。

超过窗口仍无法确认时，事件保留为“待核实”，附仓库、分支、范围、原因及恢复入口，并能从任务页进入相应事件详情；它不算已完成任务，不能静默丢弃。操作入口复用现有人工范围评审或补触发能力；如当前接口无法表达该范围，需先补齐接口，不能仅做一个无效按钮。

对已审／未审代码能用连续 commit 或 from-to 范围安全隔离的混合 Push，自动审查未审范围。无法隔离、同范围交错修改或证据不足时，明确待核实，由管理员选择重新核验，或查看范围并确认完整重审；后者明确告知会重新覆盖部分已审代码。这样异常有处理出口，同时不虚构 OCR 支持任意差异片段扣除。

## 4. 飞书行为

合并前任务接入普通任务已有的通知通道和独立投递队列。审查结论与待投递记录事务保存，Worker 发送。卡片包含仓库、来源、MR／版本、目标分支、实际评审状态、覆盖与发现摘要、统一详情链接。

- 同版本关联 Push／merge 不创建第二份初审投递。排队或运行中合并，仍待原任务结论后发送。
- 完成、部分、失败与跳过分别描述；失败不是通过。人工补审按既有语义产生补充通知。
- 通知失败只重试投递，不重新审查代码；页面分别展示任务状态和通知状态。
- 已被新版本替代且尚未投递的通知取消并保留原因；已经发送的旧卡片不自动撤回，详情说明版本状态。
- 旧历史迁移不补发飞书。未配置通道可保存项目，但必须清楚提示无法发送通知。
- 外部已接收而回执丢失仍可能造成重投，数据库去重不等于跨网络严格只发送一次。

## 5. 仓库识别与分支搜索

自动识别返回名称、GitLab 项目身份、标准仓库路径、默认分支和无凭据地址。前端只保存当前草稿关联的结果引用，正式保存由服务端验证引用、项目与所选分支。结果过期、来源变化或凭据变化重新识别，旧响应不能覆盖新草稿。

分支使用 Ant Design 可搜索 Select：首次加载一批，输入防抖约 300ms 后远程搜索，分页加载更多。服务端搜索整个远程分支集合，关闭前端仅过滤第一页的行为。支持加载中、空结果、无权限、失败重试、键盘操作；不允许凭空创建候选分支。

现有项目识别采用 HTTP 加密入队、Worker 远程读取，查询完成后清除临时 Token。为支持多次分支搜索，新增有时效、绑定当前管理员会话、仓库主机和凭据版本的短期查询会话；临时凭据加密、取消或过期清除，限制并发和响应体。查询不占模型执行槽，慢操作不进入 HTTP 保存事务。缓存不跨授权或凭据复用。

新增时项目身份、目标分支验证、触发配置、审查背景及飞书绑定一次事务保存。编辑同一项目可读取已保存 Token 发起查询；替换成另一个项目仍遵守有历史时的身份保护。修改来源或目标分支时保留在途任务保护，409 保留草稿。未变更来源、Token 和分支时，远程故障不阻止保存无关设置。

默认分支只在新增且用户未选择分支时建议填入；编辑绝不覆盖已有值。远端没有分支时说明需先在 GitLab 创建分支；保存前由 Worker 复核分支并提供绑定结果，HTTP 消费验证结果。远端随后删除分支仍需执行时检查。

## 6. 后端改造与历史兼容

本次重新核对的本地实现依据：

| 当前实现 | 必须处理的变化 |
| --- | --- |
| premerge.py 保存独立 premerge_reviews；普通任务使用 review_jobs | 将合并前版本接入统一任务主体和结果链路，不只拼接两个列表 |
| worker.py 的 review_premerge 在执行前后要求 MR 为 opened | 支持已合并同版本继续，区分关闭未合并、输入变化和正常合并 |
| premerge.py 的 invalidate_premerge 使旧记录失效 | 合并生命周期与代码版本失效分开处理 |
| 现有 repository_discovery.py 完成后清除临时 Token | 增加短期查询会话供后续远程分支搜索 |
| RepositoryCreateForm.tsx 仍显示身份字段和自由输入分支 | 新增编辑共用精简表单与搜索组件 |

建议统一到 review_jobs，增加明确任务来源、MR 版本、固定 base/head、输入配置及背景快照。建立事件与任务的多对多关联、覆盖判定证据及旧合并前 ID 映射。HTTP 只鉴权、校验和落库，Worker 执行 GitLab、Git、OCR 和飞书调用；SQLite 是事件、任务和投递事实来源。

并发去重不能只按 repository + head SHA：需要可信项目、MR、目标分支及可核验输入版本。merge／squash／rebase 的提交身份可能变化，关联 MR 与合并产物只是证据的一部分；不得仅按设置开关、文件名或 MR IID 跳过。任务删除后按明确保留期限维护最小关联留痕，避免事件重放复活任务。

保留普通任务编号，为历史合并前记录分配统一编号并保存映射；历史结果、工件、已知费用和发现可追溯，缺失数据保持未知。反馈、补审、报告、行内发布的既有授权和版本定位保护继续有效；合并前适配需要逐项验收，无法定位时明确跳过。迁移不重跑 OCR、不补发历史通知、不伪造合并事实。

## 7. 实施顺序与验收

| 阶段 | 交付内容 | 必须通过的验收 |
| --- | --- | --- |
| 一：统一任务基础 | 数据迁移、旧 ID 映射、统一领取和结果落库、合并同版本继续执行 | 编号与外键正确；运行中合并不中断；普通任务功能不退化；旧消费者停止重复领取 |
| 二：事件关联去重 | MR／merge／Push 复用、并发与乱序、混合范围、待核实出口 | 相同自动输入仅认领一次；直接 Push 和新增代码不漏审；失败状态不假报完成；三种合并方式及 fast-forward 有覆盖 |
| 三：统一任务体验和通知 | 移除菜单、统一列表详情与操作、飞书、统计及旧链接 | 任务能力逐项对齐；来源可筛选；关联可追溯；通知重试不审代码；统计不双计；权限正确 |
| 四：仓库表单 | 身份自动识别、短期查询会话、远程分支搜索、新增编辑原子保存 | 搜到第二页分支；迟到结果不覆盖草稿；编辑留空 Token 可查询；主机变化不泄露旧凭据；失败与冲突不丢输入 |
| 五：配套发布 | 隔离数据库迁移演练、备份、API／Worker／前端配套切换与实际入口验收 | 历史链接可用；无双消费者；回滚不丢新增事实；实际运行版本和通知结果有证据 |

四的开发可与前几阶段并行安排，但不要求多代理执行。整套验收前不单独上线“去掉菜单”制造能力已统一的假象。
